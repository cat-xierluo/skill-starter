# 任务拆解与迭代

这篇文档只回答一个问题：

**怎样让 AI 先搞清现状、再定计划、分一小批一小批地实现，每批都留一个能退回去的点，而不是一口气大改一通？**

[从需求到验收标准](./05-从需求到验收标准.md) 解决了「需求怎么讲清楚」；[验证 AI 的工作](./06-验证-AI-的工作.md) 解决了「做完了怎么逐条核对」。可还有一个很多人栽过的坑：需求也清楚了，验收也列了，却把整个任务一口气丢给 AI——结果一出问题，分不清是哪一步坏的，想退也退不干净。本篇就专门讲这一步：**拿到一个清楚的需求后，怎么把它拆开、分批做、步步留回退点。**

---

## 本篇目标

读完这篇，你应该能做到：

1. 说清「一次性大改」为什么难验证、难回退、难定位，从而理解为什么要拆。
2. 按一个固定的 **4 阶段流程**——先调查、再计划、分批实现、保留回退点——驱动 AI 推进。
3. 用 `todo.py` 把一个需求拆成可独立验收的批次，每批做完即验证、即提交。
4. 在某一批发问题时，用 Git 回退点只重做那一批，而不是整体推倒重来。

本文不教代码实现，只教「怎么把任务拆给 AI」。示例沿用 [从需求到验收标准](./05-从需求到验收标准.md) 的本地待办脚本 `todo.py`。

## 核心概念

### 为什么不能「一口气全改完」

把整个任务一次性丢给 AI，看起来省事，实际上埋下三个麻烦：

- **难验证**：一次产出太多，你很难一条条核对。光是 `todo.py` 的 `add` / `list` / `done` 三件事，一口气交给你，你就得分头测三遍，还容易测漏边界。
- **难回退**：所有改动堆在一次里，一旦某处坏了，你想退回「上一个能用的状态」都找不到——因为根本没存过中间状态。
- **难定位**：三件事一起改，某个行为错了，你不知道是 `add` 存错了、`list` 读错了，还是 `done` 更新错了，只能逐个猜。

所以更稳的做法是把任务拆小：**一次只做一件能独立验收的事，做完立刻验证、立刻存档**。这样每一步都是「已知良好」的，出问题也只影响当前这一小步。

### 4 个阶段各做什么

把一个需求从「丢给 AI」到「稳妥交付」，走这 **4 个阶段**。每个阶段都有一份该落进文件的产出——否则在长会话里被压缩后，AI 会忘了自己调查过什么、计划怎么定的（详见 [上下文生命周期](./07-上下文生命周期.md)）。

| 阶段 | 做什么 | 该留下的产出 |
|------|--------|-------------|
| 1. 先调查 | 让 AI 先读现有代码、相关文档、验收清单，搞清现状和约束再动手 | 对现状的理解（口头简述即可，复杂时写进 `DECISIONS.md`） |
| 2. 再计划 | 基于调查，把任务拆成可独立验收的批次，排出顺序和每批的验收点 | 一份分批计划，写进 `DECISIONS.md`；批次作为待办进 `TASKS.md` |
| 3. 分批实现 | 一次只做一批，每批做完立刻验证、验证通过就提交一次 | 每批的验证证据 + 一个 Git 提交 |
| 4. 出问题能退回 | 某批坏了，用阶段 3 留下的提交退到上一批继续 | 回退到的 commit（「保留回退点」贯穿阶段 3，不是独立的收尾步骤） |

下面用一个完整例子把这 4 个阶段走一遍。

## 实例分析

仍然用 `todo.py`（见 [从需求到验收标准](./05-从需求到验收标准.md)）。假设需求已经写清楚了：第一版只做 `add` / `list` / `done` 三件事，存成 `todos.json`，只用 Python 标准库。下面看怎么把它**拆成 3 批**，一步步推进，而不是一口气全改。

### 阶段 1：先调查——别凭空动手

动手前，先让 AI 搞清两件事：

- **现状**：项目里现在有没有 `todo.py`？有没有 `todos.json`？数据结构长什么样？
- **约束**：验收清单要求了什么（输入输出、退出码、文件格式）？

调查不是走过场。如果 AI 跳过这步，可能凭「待办一般怎么写」的刻板印象，自作主张用 SQLite 存数据、或装个第三方包——可验收清单明明要求存成 `todos.json`、只用标准库（接 [从需求到验收标准](./05-从需求到验收标准.md) 的约束）。

> 小技巧：你可以直接要求 AI「先读 `todos.json` 的预期结构和验收清单，告诉我你打算怎么做，再动手」。这一句就是逼它先调查、再计划。

### 阶段 2：再计划——把任务拆成可独立验收的批次

基于调查，把三件事拆成 **3 批**，每批都能独立验证、独立提交：

```text
批次 1：搭骨架 + add 命令
  做：建 todo.py、解析命令行参数、实现 add、把待办写进 todos.json
  验收：python todo.py add "买牛奶" 后，todos.json 出现 {"id":1,"title":"买牛奶","done":false}

批次 2：list 命令
  做：读 todos.json、打印带编号的待办列表
  验收：python todo.py list 打印出至少一行带编号的待办

批次 3：done 命令
  做：按编号把对应待办的 done 置为 true 并写回文件
  验收：python todo.py done 1 后，todos.json 里那条 done 变成 true
```

关键在于**每批的验收条件都来自验收清单**，而且每批都能单独跑、单独判定通过。这份计划值得落进 `DECISIONS.md`（记录「为什么这么拆」），3 个批次作为待办写进 `TASKS.md`——否则长会话压缩后，AI 可能忘了自己当初定的顺序，又开始东一榔头西一棒子（接 [上下文生命周期](./07-上下文生命周期.md)）。

### 阶段 3：分批实现——一次一批，做完即验

接下来一批一批做，**每批都走「实现 → 验证 → 提交」**。验证不是「没报错就行」，而是照 [验证 AI 的工作](./06-验证-AI-的工作.md) 的梯度往上走：跑到第 3、4 级（实际运行、核对文件）。

- **批次 1（add）**：AI 实现 `add`。你验证——敲 `python todo.py add "买牛奶"`，打开 `todos.json`，真的多了一条。通过。提交：`feat: add 添加待办并写入 todos.json`。
- **批次 2（list）**：AI 实现 `list`。你验证——敲 `python todo.py list`，亲眼看到带编号的列表。通过。提交：`feat: list 列出待办`。
- **批次 3（done）**：AI 实现 `done`。你验证——敲 `python todo.py done 1`，打开 `todos.json`……（见阶段 4 的反面情况）。

每批一个提交，意味着任何一个时刻，仓库里都有一份「已知能用」的状态。

### 阶段 4：保留回退点——坏了就退回上一批

现在看阶段 4 真正的价值。假设批次 3 的 `done` 撞上了 [验证 AI 的工作](./06-验证-AI-的工作.md) 里那个经典陷阱——**假绿**：AI 给 `done` 写了测试，测试一片绿，可你打开 `todos.json`，发现那条的 `done` 字段**根本没变成 `true`**（函数只返回了一个状态，没把结果写回文件）。

这时如果你当初是一口气全改、一个提交堆到底，处境会很糟：

- 分不清是 `add` 存错了、`list` 读错了，还是 `done` 更新错了；
- 想退，只能整体退，连已经做对的 `add` 和 `list` 也一起被退掉。

可你走的是分批 + 每批提交，处境完全不同：

- `add`（批次 1）和 `list`（批次 2）各有自己的提交，已经验证过、是「已知良好」的，不用动它们；
- 出问题的只是批次 3，你可以让它基于批次 2 的状态重做，只修 `done` 的「写回文件」这一步；
- 修完重新验证（这次记得打开 `todos.json` 看 `done` 真的变了），再提交：`feat: done 标记完成`。

这就是「保留回退点」的含义：**每一步都站在上一步已验证的肩膀上，坏了一步只重做那一步**。

> 如果某批改坏了、想丢弃这一批的改动回到上一批，可以用 Git 的撤销操作（如针对最新提交的回退）回到批次 2 的状态。具体命令和区别见 [Git 入门](../02-工具指南/01-Git-入门.md)，本篇只强调「为什么要这么做」。

## 常见错误

### 错误 1：不调查，凭印象直接写

结果：AI 基于刻板假设动手——用了你没要求的依赖、存成了你没要的格式——验收时才发现跑偏，返工更大。

对策：动手前先让它读现状和约束，复述一遍打算怎么做，再实现。

### 错误 2：一次性把所有功能堆给 AI

结果：产出太多，验证困难、回退困难、出错定位困难（难验证、难回退、难定位三连）。

对策：拆成可独立验收的小批，每批做完即验、即提交。

### 错误 3：一个提交攒一堆改动，不留回退点

结果：某处坏了，想退回「上一个能用的状态」都找不到，只能整体重来，已经做对的部分也白费。

对策：每批一个提交，commit message 写清这批做了什么；任何时候仓库都有一份「已知良好」的状态。

### 错误 4：计划只在聊天里说，不落文件

结果：长会话被压缩后，AI 忘了当初的分批顺序和验收点，又开始零散地改（接 [上下文生命周期](./07-上下文生命周期.md) 的「压缩与遗忘」）。

对策：分批计划写进 `DECISIONS.md`，批次进 `TASKS.md`，让计划成为跨会话可恢复的项目上下文。

### 错误 5：某批做完不验证就急着进下一批

结果：错误叠加。三批都没验证就往下走，最后 `done` 假绿时，你根本不知道是哪一批引入的问题。

对策：每批做完立刻照验收清单验证（至少到「实际运行 + 核对文件」这一级），通过了才进下一批。

## 自测题 / 验收清单

拿你最近一次让 AI 做的小功能，对照下面这份清单，看你的「拆解与迭代」合不合格。每条都答「能」，才算合格：

- [ ] 我是让 AI **先调查**现状和约束，再动手，而不是直接开写吗？
- [ ] 我把任务拆成了**可独立验收的批次**，而不是一口气全改吗？
- [ ] 我的分批计划**落进了文件**（`DECISIONS.md` / `TASKS.md`），而不只留在聊天里吗？
- [ ] 每一批做完，我都**立刻按验收清单验证**（实际运行 + 核对文件）了吗？
- [ ] 每一批验证通过，我都**单独提交**了一次，留了回退点吗？
- [ ] 某批出问题时，我能**只重做那一批**，而不影响前面已验证的批次吗？

小练习：故意让 AI 在批次 3 的 `done` 里漏掉「写回文件」（或自己删掉那行），然后只跑测试——你会看到绿灯。再按阶段 4 的思路，验证后定位到是 `done` 这一批的问题，体会「分批 + 回退点」让你免于整体推倒重来。

## 一句话总结

把一个清楚的需求稳妥交付，靠的是「先调查、再计划、分批实现、每批留回退点」这 4 个阶段——一次只做一件能独立验收的事，做完即验、即提交，坏了一步就退回上一批重做那一步，而不用整体推倒重来。
