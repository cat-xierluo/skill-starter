# 多 Agent 协作入门

这篇文档只回答一个问题：

**当任务大到需要好几个 AI 一起做、或拆开后能同时推进时，怎么分活、怎么避免它们抢同一个文件、怎么交接才不丢信息？**

上一篇 [任务拆解与迭代](./09-任务拆解与迭代.md) 讲了怎么把一个大任务拆成 AI 能分批做的小块。但当任务大到一个人（一个 Agent，指一次独立运行的 AI 会话）拆不动、或拆开后各部分能并行时，就轮到多 Agent 协作了。本篇就用本仓库自己怎么写这套教程的——`.claude/orchestration/` 下那套「PM 拆任务 + 3 个 worker 并行写文章」的真实编排——当活教材，讲清四件事：**角色边界 / 任务所有权 / 并行条件 / 交接格式**。

---

## 本篇目标

读完这篇，你应该能做到：

1. 说清为什么多 Agent 不是「越多越好」，而是要先划清每个 Agent 负责什么、不负责什么。
2. 用「角色边界 / 任务所有权 / 并行条件 / 交接格式」这 4 件事，规划一次多 Agent 协作。
3. 判断一批任务能不能并行（看有没有文件冲突、有没有依赖），不能并行时该怎么排顺序。
4. 用结构化产物（STATUS 文件、RESULT、补丁摘要）做 Agent 之间的交接，而不是口头描述。

本文不教具体怎么搭 tmux 或调用某个 Agent 框架，只教「怎么把活分给多个 Agent 又不打架」。示例全部来自本仓库真实的 OTA（Orchestration with Task Agents，一套「PM 拆任务 + 多个独立 worktree worker 并行执行」的编排模式）。

## 核心概念

先界定一个总称：**多 Agent 协作**，指把一个任务交给多个独立的 AI 会话（每个会话就是一个 Agent）分工完成，而不是塞进一个会话里一口气做完。它要解决的不是「让 AI 更聪明」，而是「让多个 AI 不打架」。

下面 4 件事，是多 Agent 协作能不能成型的关键，缺哪一件都会出乱子。

### 1. 角色边界：每个 Agent 负责什么、不负责什么

角色边界回答「你管哪一段」。最危险的不是没分工，而是分工模糊——两个 Agent 都觉得自己「顺手帮一下」对方的活，结果改出两套互相打架的实现。

多 Agent 协作里通常有两类角色，边界要划死：

| 角色 | 负责什么 | 不负责什么 |
|------|---------|-----------|
| PM（Project Manager，负责拆任务和收口的协调 Agent） | 拆任务、分派、巡检、review、决定合并 | 不直接写业务内容，避免「既是裁判又是选手」 |
| worker（执行 Agent，实际干活的会话） | 在自己范围内实现、自测、提交 | 不动别人的文件、不开 PR、不做产品判断 |

注意「不负责什么」这一列，和「负责什么」同样重要。本仓库的 OTA 规则里明确写了 PM「不直接写业务内容」，worker「不开 PR（由 PM 负责 push/PR/merge）」「不领取其它任务」——这些否定式约束，恰恰是防止越界的硬边界。

### 2. 任务所有权：每个子任务有且只有一个 owner

任务所有权回答「这件事归谁」。规则很简单：**每个子任务有且只有一个 owner**。

没有 owner 的任务会被两个 Agent 都忽略（「以为对方会做」）；有多个 owner 的任务会被两个 Agent 同时改（「以为归自己」）。两种情况都致命。本仓库 OTA 给每个 worker 都划了独立目录：

```text
W1 → 01-概念入门/
W2 → 02-工具指南/
W3 → 03-AI协作与上下文/
```

三个 worker 各占一个目录，互不重叠。这就是「一个 owner 一块地」的写法。判断所有权划得对不对，最简单的检验是问一句：

> 这个文件 / 这件事，会不会有两个 Agent 同时去动？

会，就得重新切分。

### 3. 并行条件：什么时候能一起跑，什么时候不能

并行条件回答「能不能同时开」。多 Agent 的「快」来自并行，但并行不是无条件的。能并行的前提是这两条都满足：

- **任务互相独立**：一个 Agent 不需要等另一个 Agent 的产出才能开工（没有依赖）。
- **无文件冲突**：两个 Agent 不会改同一个文件（没有写写冲突）。

反过来，只要命中下面任何一条，就**不能**并行，得排成先后：

| 不能并行的信号 | 含义 | 解法 |
|---------------|------|------|
| 有依赖 | B 要用到 A 的产出才能动 | 先跑 A，A 完成再跑 B |
| 改同一文件 | 两个 Agent 都会写 `README.md` | 把文件拆开，或合并成一个任务交给一个 Agent |
| 共享契约变了 | 两个 Agent 都依赖某个接口/文档，而它本身也在被改 | 先稳定契约，再并行下游 |

本仓库 Wave 1 之所以能 3 worker 并行，正是因为三块目录彼此独立、互不引用对方的产出——满足「独立」和「无冲突」两条。

### 4. 交接格式：Agent 之间怎么传递信息

交接格式回答「我做完之后，怎么让下一个 Agent（或 PM）知道我做了什么」。这是 4 件事里最容易偷懒、也最容易出事的一件。

口头交接（「我写完了，挺顺利的」）在多 Agent 里几乎等于没交接。可靠的交接必须落成**结构化产物**——固定的文件、固定的字段，让信息能被下一个 Agent 或 PM 机械地读到，而不依赖人去转述。本仓库 OTA 规定的交接产物有三种：

| 产物 | 记什么 | 给谁读 |
|------|--------|--------|
| STATUS 文件（如 `STATUS.json`） | 当前状态、所在分支、当前阶段、下一步、是否有阻塞 | PM 巡检、判断要不要纠偏 |
| RESULT（如 `RESULT.md`） | 做了什么、验证结果、留下哪些证据 | PM 收口 review |
| PATCH_SUMMARY（补丁摘要） | 改了哪些文件、关键改动 | PM 判断有没有越界 |

交接要落文件的根本原因在 [上下文生命周期](./07-上下文生命周期.md)：会话上下文会消失、会被压缩，只有写进文件的内容才跨会话可恢复。PM 不可能记住 3 个 worker 各自聊到哪一步，全靠这些结构化产物。

> 为什么要定死 `status="done"` 这种字面值？本仓库 OTA 规则特意强调「不要用 completed/finished 同义词」——因为 PM 用一个哨兵进程机械地扫描这个字段来唤醒，写错了字面值，哨兵就识别不了，PM 永远等不到「完成」信号。这就是交接格式必须严格的代价。

## 实例分析：本仓库的 OTA 编排

把上面 4 件事放进一个真实样本看。`.claude/orchestration/` 下的文件，记录了本仓库这套教程是怎么写出来的：一个 PM 拆任务，3 个 worker 在各自的 worktree（Git 工作目录的独立副本，让多个 Agent 在同一仓库的不同分支上互不干扰地工作）里并行写文章，PM 最后收口 review。这正是多 Agent 协作的活样本。

### 角色边界：PM 只拆只 review，worker 只写只测

目标文件里写得明明白白：

- PM 的边界——「PM 不直接写业务内容」。PM 拆 Wave、分派 worker、跑 writing-reviewer 自动 review、决定合并，但不动文章正文。这条否定式约束很关键：如果 PM 也下场写，它就成了自己 review 自己的选手，收口就失了意义。
- worker 的边界——「不要领取其它任务」「不开 PR（PM 负责 push/PR/merge）」。worker 只在自己的范围内写、自测、提交，把合并和对外判断留给 PM。

这套边界对应了核心概念里那张角色表：PM 管「为什么做、做哪些、合格没」，worker 管「怎么做出来」。

### 任务所有权：一个 worker 一个目录

Wave 1 把待写的 6 篇地基文章分给 3 个 worker，所有权按目录切：

```text
W1 → docs/concept-skill-mcp      → 01-概念入门/（新增 05、06 两篇）
W2 → docs/tools-terminal-env     → 02-工具指南/（新增 06、07、08 三篇）
W3 → docs/collab-acceptance      → 03-AI协作与上下文/（新增 05 一篇）
```

每个 worker 占一个独立分支、一个独立 worktree、一个独立目录。所有权清晰到「文件级」：`05-从需求到验收标准.md` 的 owner 只有 W3，W1 和 W2 连读都读了，但绝不会去改它。三个 worker 同时开工，互不踩脚。

### 并行条件：三块目录互不引用，满足独立 + 无冲突

为什么这 3 个 worker 能同时跑？回到并行条件那两条：

- **独立**：`01-概念入门/` 的文章不依赖 `02-工具指南/` 的产出，`02-工具指南/` 也不依赖 `03-AI协作与上下文/`。各写各的，不需要互相等。
- **无文件冲突**：三个 worker 改的是三套不同的文件，没有共享的待写文件。每个 worktree 是仓库的独立副本，物理上就隔离了写写冲突。

CHANGELOG 里 Wave 1-4 的记录能验证这套并行是真的在跑——「3 个 tmux worktree worker × glm-5.2 并行」「Wave 4（OTA 3 worker × glm-5.2 并行）产出 7 篇」。这不是理论设想，是仓库自己经历过的真实批次。

### 交接格式：STATUS / RESULT / PATCH_SUMMARY + 哨兵

worker 干完活怎么让 PM 知道？靠三件结构化产物：

- 每个进程的 Session Context 目录下写 `STATUS.json`，记当前阶段、所在分支、有没有阻塞。规则还强制「每 10 分钟刷新一次心跳」（即使没进展也写 `phase=thinking-deep`），让 PM 能判断 worker 是「还在想」还是「卡死了」。
- 写完文章后产出 `RESULT.md` 和 `PATCH_SUMMARY.md`，PM 收口时照着读，看做了什么、验证过没、改了哪些文件。
- 最终 STATUS 必须设成字面值 `status="done"`——PM 用哨兵机制（一个机械扫描该字段的进程）来识别「这个 worker 完成了」，写错字面值哨兵就不退出、PM 不被唤醒。

这套交接格式对应了 [上下文生命周期](./07-上下文生命周期.md) 的核心结论：**会话会消失，只有写进文件的内容才跨会话可恢复**。PM 不靠记忆，全靠这些固定字段做判断。

> 一个真实教训：CHANGELOG 记录 Wave 1 时提到「W1 worker 因限流中断漏 commit，PM 按 Hard Fail 规则手动补 commit」。交接格式定得再严，也会遇到 worker 异常中断；这时结构化产物的价值在于——PM 一看 STATUS 卡在某个阶段、commit 又没落，就能精准定位「W1 漏了哪一步」，而不是对着 3 个会话的聊天记录瞎猜。

## 常见错误

### 一个 worker 顺手改了别人的文件

结果：两个 worker 都改了同一文件，合并时冲突，或者后改的把先改的覆盖掉，前面白做。

对策：每个子任务只指派一个 owner；开工前明确「允许动的文件清单」和「禁止动的文件清单」（本仓库 OTA 每个 worker 的 prompt 里都列了 Allowed / Forbidden files）。有疑问宁可问 PM，不要「顺手帮忙」。

### PM 也下场写内容，自己 review 自己

结果：PM 既当裁判又当选手，收口的独立性丢了——它的 review 偏向自己的写法，问题更难被发现。

对策：PM 只拆任务、分派、巡检、review、决定合并，业务实现全部交给 worker。把「谁写」和「谁判」分给不同 Agent，是收口可信的前提。

### 把有依赖的任务硬塞进并行

结果：B 在等 A 的产出，却被同时启动，B 只能猜着做，最后接不上 A 的真实产出，全部返工。

对策：先画依赖关系——凡是「B 要用 A 的产出才能动」的，排成先后，先跑 A 再跑 B。只把真正独立、无依赖的任务放进同一 Wave 并行。

### 交接只靠聊天，不写结构化产物

结果：PM 记不住 3 个 worker 各自进展，开新会话就全丢；worker 之间也无法机械读取对方状态，只能靠人转述，信息越传越歪（接 [上下文生命周期](./07-上下文生命周期.md) 的「压缩与遗忘」）。

对策：交接必须落进固定文件、固定字段（STATUS / RESULT / PATCH_SUMMARY）。判断一条信息要不要落文件，用 [上下文生命周期](./07-上下文生命周期.md) 的标准：「下次开新会话还需要它吗？」需要，就写。

### 验收清单只在脑子里，没分到每个角色头上

结果：worker 自己觉得「差不多了」就提交，PM 收口时才发现没达到 [从需求到验收标准](./05-从需求到验收标准.md) 的可观察条件，反复返工。

对策：每个 worker 的任务里都带一份明确的「完成条件」（本仓库 OTA 的 worker prompt 里写了 Verification 段：`bash scripts/check.sh` 退出 0、新链接有效、长度结构合规）。验收标准要在开工前就分到每个 owner 头上，不是事后补。

### 状态字面值不统一，哨兵识别不了

结果：worker 写了 `status="completed"`（而不是规定的 `status="done"`），PM 的哨兵进程扫不到，永远不被唤醒，整个 Wave 卡在「等不到完成」的状态。

对策：交接格式里的关键字段（尤其是终态标识）必须用约定的字面值。本仓库 OTA 特意强调「不要用 completed/finished 同义词」，就是为了被机械扫描的进程可靠识别。格式约定越严，自动化越稳。

## 自测题 / 验收清单

拿你手头一个「需要多个 Agent / 多个会话一起做」的任务，对照下面这份清单，看你的多 Agent 协作合不合格。每条都答「能」，才算合格：

- [ ] 我给每个角色都划清了**负责什么**和**不负责什么**，PM 不下场写业务、worker 不开 PR 吗？
- [ ] 每个子任务都有**且只有一个 owner**，没有「两个 Agent 会同时改同一文件」的情况吗？
- [ ] 我区分了**能并行的任务**（独立、无冲突）和**不能并行的任务**（有依赖、改同一文件），分别排成并行和先后了吗？
- [ ] Agent 之间的交接是**结构化产物**（STATUS / RESULT / PATCH_SUMMARY 之类），而不是只靠聊天吗？
- [ ] 每个 worker 的任务里都带了一份**可观察的完成条件**（来自 [05](./05-从需求到验收标准.md)），开工前就分好了吗？

小练习：挑一个你最近一次「想让 AI 并行做」的任务，按本篇 4 件事各写一句话——角色边界、任务所有权、能不能并行（为什么）、交接用什么文件。如果你卡在其中任何一件上，说明那块协作设计还没到位，先别急着启动多个 Agent。
