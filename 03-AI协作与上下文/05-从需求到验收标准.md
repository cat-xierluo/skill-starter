# 从需求到验收标准

这篇文档只回答一个问题：

**怎样把脑子里一个模糊的想法，变成 AI 能稳定执行、你也能稳定验收的需求。**

如果你读 [Vibe Coding 入门](./01-什么是-Vibe-Coding.md)，会发现它的失败原因几乎都指向同一件事：

> 需求不清、边界不清、验收不清。

本篇就是专门解决「验收不清」这一条——它是这三者里最值钱、也最容易被新手跳过的一环。

---

## 本篇目标

读完这篇，你应该能做到：

1. 把一句「帮我做个 XX」拆成 7 个具体要素。
2. 区分「模糊描述」和「可验收标准」。
3. 用一个固定模板，把任何小需求写成 AI 能直接照做的版本。
4. 给需求写出「可观察的完成条件」，让 AI 输出的结果你能当场判断对错。

本文不教代码本身，也不教怎么写提示词技巧，只教「需求怎么讲清楚」。

## 核心概念

### 什么是「验收标准」

验收标准就是一句话：

> 什么样子的结果，算「做完了」。

它不是「希望 AI 做得好一点」这种感觉，而是：

- 能用眼睛看到、用命令跑出来、用文件内容核对的东西。
- 任何人在不问你、不猜你的情况下，都能判定「达到 / 没达到」。

### 为什么模糊需求会让 AI 失控

AI 没有「读心术」。它只能根据你**说出来**的内容工作。你说得越模糊，留给它自由发挥的空间越大，结果就越随机。

同一个「待办功能」，不同模糊说法会让 AI 走向完全不同的方向：

| 你说的 | AI 可能的理解 |
|--------|--------------|
| 「做个待办」 | 一个网页 App？一个手机界面？一个命令行脚本？ |
| 「能记事就行」 | 存内存里关掉就丢？还是存文件？还是存数据库？ |
| 「好看一点」 | 加图标？加颜色？加动画？ |

每一个模糊点，都是一次「AI 替你做的随机决定」。需求越模糊，随机决定越多，最后的结果离你想要的就越远。

### 验收标准的 7 个要素

把一个模糊想法变成可验收需求，要补齐这 7 块。**缺任何一块，AI 都可能跑偏**：

| 要素 | 回答的问题 | 举例（待办脚本） |
|------|-----------|------------------|
| 1. 目标 | 做一个什么东西？ | 一个本地命令行待办工具 |
| 2. 用户 | 给谁用？ | 只有我自己（单机） |
| 3. 范围 | 第一版做哪些？ | 添加、列出、标记完成 |
| 4. 非目标 | 第一版**不做**哪些？ | 删除、提醒、分类、多用户、网页界面 |
| 5. 约束 | 必须用什么 / 不能用什么？ | Python 3 标准库；不联网；存成 `todos.json` |
| 6. 输入输出 | 用户敲什么、看到什么？ | `add "买牛奶"` → 显示「已添加 #1」 |
| 7. 可观察的完成条件 | 怎么判定做完了？ | 见下文，每条都能直接核对 |

其中最关键、也最常被省略的是**第 4 项「非目标」**和**第 7 项「可观察的完成条件」**。很多人只写「要做什么」，不写「不做什么」，AI 就会自作主张地多加功能；不写「怎么算完成」，AI 就会自己猜一个「差不多了」交给你。

### 模糊想法 vs 可验收标准

❌ 模糊版本：

> 帮我写一个待办功能，能记事、能查看、能标记完成，最好简单一点。

问题：没说给谁用、没说运行在哪、没说数据存哪、没说「完成」长什么样。

✅ 可验收版本（后续「动手步骤」会一步步推出来，先看全貌）：

> 做一个本地命令行待办脚本 `todo.py`。
> 用户只有我自己，单机使用。
> 第一版只做三件事：`add` 添加、`list` 列出、`done` 标记完成。
> 不做删除、编辑、截止日期、提醒、分类、多用户和网页界面。
> 用 Python 3 标准库实现，不装第三方包，不联网；数据存在当前目录的 `todos.json`。
> 完成条件见下文验收清单，每一条都能用命令或文件内容核对。

同一个想法，从「随机发挥」变成「可照做、可验收」，靠的就是把 7 个要素补齐。

## 动手步骤

接下来用一个贯穿全文的小项目——**本地命令行待办脚本 `todo.py`**——把上面 7 个要素一步步落实。**下面 7 步和上面 7 个要素是一一对应的，只是换成「怎么填」的视角**：上面告诉你「要补哪 7 块」，下面告诉你「每一块具体怎么写」。如果你已经理解 7 要素、只想要验收清单，可直接跳到第 7 步；想看每块怎么落地，就跟着步骤走。你可以照着这个流程，套到自己的任何小需求上。

### 第 1 步：写下目标和用户

先回答两个最基本的问题：

- **目标**：做一个本地命令行待办脚本，能记录、查看、完成待办事项。
- **用户**：只有我自己，单机使用，不考虑多个人同时用。

「用户」这一步别跳过。给一个人用和给一百个人用，设计差别极大。明确「只有我自己」，AI 就不会去设计登录、权限、并发这些第一版用不上的东西。

### 第 2 步：圈定范围和非目标

明确「第一版做」和「第一版不做」：

- **范围（做）**：`add` 添加、`list` 列出、`done` 标记完成。
- **非目标（不做）**：删除、编辑、截止日期、提醒、分类、多用户、网页界面。

「非目标」是新手最容易漏的，也是最能省时间的一项。**每多写一条「不做」，就少一次 AI 的自由发挥**。你可以在心里问自己：

> 这个功能，如果第一版没有，我会不能用吗？

如果答案是「能凑合用」，就先放进非目标。

### 第 3 步：明确约束

约束告诉 AI「手脚被绑在哪」，避免它引入你不想要的东西：

- 语言：Python 3。
- 依赖：只用标准库，**不装第三方包**（避免 `pip install`，降低环境风险）。
- 网络：**不联网**。
- 存储：数据存在当前目录的 `todos.json` 文件里。

这一步直接决定了 AI 会不会给你塞一堆你没要求的依赖。养成习惯：凡是「不想要的东西」，都在约束里点名禁止。

### 第 4 步：定义输入输出

把「用户敲什么、屏幕显示什么」写成具体例子。这一步能让模糊的「能记事」变成明确的命令契约：

```text
python todo.py add "买牛奶"   →  打印：已添加 #1：买牛奶
python todo.py list           →  打印：带编号的待办列表
python todo.py done 1         →  打印：已完成 #1
```

把输入输出写成「左命令、右结果」的对照，AI 就知道每个命令的形状，你也知道验收时该敲哪条命令。

### 第 5 步：把「完成」翻译成可观察条件

这是整篇的核心。**「可观察」的意思是：能用命令跑出来、能用文件内容核对，而不是凭感觉说「看着不错」**。

把上面三步的内容，落成一份能逐条勾选的验收清单：

```text
[ ] 1. 运行 python todo.py add "买牛奶" 后，当前目录出现 todos.json，
       且其内容包含 {"id": 1, "title": "买牛奶", "done": false}
[ ] 2. 运行 python todo.py list，能打印出至少一行带编号的待办
[ ] 3. 运行 python todo.py done 1 后，todos.json 里第 1 条的 done 变成 true
[ ] 4. todos.json 不存在时，首次 add 能自动创建文件而不报错
[ ] 5. 不传子命令（只运行 python todo.py）时，打印用法说明并以非 0 退出码退出
```

注意每一条都是**可检验**的：

- 第 1、3、4 条——去看 `todos.json` 的内容。
- 第 2、5 条——去敲命令、看输出和退出码。

没有任何一条是「代码写得优雅」「体验流畅」这种没法核对的话。这些可以留到后续迭代，但**不该出现在第一版的验收标准里**。

> 小技巧：判断一条标准是否「可观察」，就问自己——「换一个人，不问我，能不能照这条判定通过？」能，就是好标准；不能，就还要再具体。

### 第 6 步：写成一个可复用的需求模板

把 7 个要素固定成一个模板，以后每个需求都照着填，省得每次从头想。这个模板可以直接抄：

```text
# 需求：<一句话名字>

目标：
  做一个什么东西？

用户：
  给谁用？

范围（第一版做）：
  - 做哪些？

非目标（第一版不做）：
  - 不做哪些？

约束：
  - 必须用什么？
  - 不能用什么？（语言 / 依赖 / 网络 / 存储）

输入输出：
  <命令>  →  <结果>
  <命令>  →  <结果>

可观察的完成条件：
  [ ] 条件 1（怎么核对）
  [ ] 条件 2（怎么核对）
  [ ] ...
```

用这个模板把待办脚本填完整，就是前面「核心概念」里那个可验收版本。模板本身也是一条 [Rules](./04-Rules-编写指南.md)——一旦固定下来，你和 AI 每次都按同一套结构对齐，需求就不会忽长忽短、漏东漏西。

### 第 7 步：交给 AI，并按清单验收

需求写好后，把它整体丢给 AI，再让它先出方案、再实现。验收时，**不要只看代码、只看运行没报错**，而是回到第 5 步的清单，逐条核对：

1. 真的敲 `python todo.py add "买牛奶"`，去看 `todos.json` 里有没有那一条。
2. 真的敲 `python todo.py list`，看输出是不是带编号的列表。
3. 真的敲 `python todo.py done 1`，再打开 `todos.json` 看 `done` 是不是变了。

每一条都核对过，才算「做完了」。这套「定义清楚 → 让 AI 做 → 按清单核对」的节奏，和 [Vibe Coding 入门](./01-什么是-Vibe-Coding.md) 里「提需求、验结果、再迭代」的工作流是完全一致的——本篇只是把其中「需求」和「验收」这两端讲透了。

> 想更稳，可以把每轮的结果连同这次的需求模板一起用 Git 存下来（见 [Git 入门](../02-工具指南/01-Git-入门.md)），方便回退和比较。

## 常见错误

### 错误 1：只写「要做什么」，不写「不做什么」

结果：AI 自作主张加了一堆你没要的功能，你还得花时间删。

对策：永远配一份「非目标」清单。

### 错误 2：把「可观察」写成「可感觉」

❌ 「界面好看、体验流畅、代码优雅」——这些没法核对。

✅ 「`list` 输出每行带编号」「首次 add 自动建文件」「`done` 后文件内容变化」——这些能核对。

对策：每条标准都要能回答「用什么命令 / 看哪个文件来核对」。

### 错误 3：验收清单写得太满

第一版就要求「完整、完美、上线」，通常是项目做散的开端。

对策：第一版只放「没有它就不能用」的条件；优雅、性能、扩展性留到后续迭代。

### 错误 4：不亲自跑，只信 AI 说「已完成」

AI 有时会自信地报告「已实现」，但实际没跑通或行为不符。

对策：照着第 5 步的清单逐条敲一遍，眼见为实。这也是为什么条件必须「可观察」。

### 错误 5：需求散落在聊天里，不落文件

只在对话里说一遍，下次开新会话就丢了，AI 又从零猜。

对策：把填好的需求模板写进项目的任务文档（参考 [上下文工程入门](./03-上下文工程入门.md)），让它成为稳定的项目上下文。

### 错误 6：约束留白，让 AI 自由引入依赖

不说「不装第三方包」，AI 可能就给你 `pip install` 一堆东西，污染环境、埋下安全风险。

对策：在约束里点名禁止你不想要的东西（依赖、联网、写敏感目录等）。

## 自测题 / 验收清单

用下面这份清单检查你写出来的需求，能不能算「可验收」。每条都答「能」，才算合格：

- [ ] 我写清楚了**目标**（做一个什么东西）吗？
- [ ] 我写清楚了**用户**（给谁用）吗？
- [ ] 我列出了**范围**（第一版做哪些）吗？
- [ ] 我列出了**非目标**（第一版不做哪些）吗？
- [ ] 我写清楚了**约束**（语言、依赖、网络、存储）吗？
- [ ] 我写清楚了**输入输出**（敲什么命令、看到什么）吗？
- [ ] 我的**完成条件**每一条都是可观察的（能敲命令或看文件核对）吗？
- [ ] 换一个人不问我，能照着完成条件判定通过吗？

小练习：拿你最近一个真实的小需求，套用第 6 步的模板写一遍，再过一遍这份清单。凡是有哪一条卡住，就说明那块需求还不够清楚。

## 一句话总结

验收标准不是「希望 AI 做得好」，而是「能用命令或文件核对、换个人也能判定通过」的可观察条件——把 7 个要素补齐，模糊想法就变成了 AI 能稳定执行的需求。
