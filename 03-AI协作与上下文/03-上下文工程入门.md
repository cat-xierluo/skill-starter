# 上下文工程入门

## 本篇目标

读完这篇，你应该能做到：

1. 用一句话说清「上下文工程」是什么，以及它和「提示词写得好不好」不是一回事。
2. 说出上下文的主要来源（7 层），并判断一条信息该落文件还是只留聊天。
3. 按工作流把项目级规则、当前任务、关键决策分别放进正确的文件。
4. 识别 4 类最常见的上下文管理错误，并给出对策。

本篇是概念总览篇，把「AI 依据什么做判断」这件事讲清；具体规则怎么写是 [Rules 编写指南](./04-Rules-编写指南.md) 的事。

## 前置知识

读这篇前，建议你已经了解：

- [什么是 Vibe Coding](./01-什么是-Vibe-Coding.md)：理解「人描述目标、AI 推进实现」的分工。
- [什么是 AGENTS.md 和 CLAUDE.md](./02-什么是-AGENTS和-CLAUDE.md)：知道 `CLAUDE.md` / `AGENTS.md` / `SKILL.md` 这些文件分别管什么。

不需要会写代码。本系列示例用一个贯穿小项目——本地命令行待办脚本 `todo.py`，本篇会用它说明「哪些信息该落文件」。

---

这篇文档讲的是：

**在 AI Coding 里，怎样让 AI 持续拿到正确上下文，而不是每次都从零猜。**

如果说 Git 解决的是“版本怎么管”，那么上下文工程解决的是：

**AI 到底依据什么做判断。**

---

## 1. 什么是上下文工程

一句话理解：

> 把 AI 做事需要的关键信息，稳定、分层、可维护地组织起来。

很多人以为 AI Coding 的核心是“提示词写得会不会花哨”，其实更关键的是：

- 项目规则有没有写出来
- 目录结构是不是清楚
- 任务状态有没有沉淀
- 历史决策能不能找到
- AI 当前是否拿到了正确文件

这些合起来，才是上下文工程。

---

## 2. 为什么 Vibe Coding 很依赖上下文工程

Vibe Coding 的问题不在于“AI 不会写”，而常常在于：

- AI 不知道项目规则
- AI 不知道哪些文件重要
- AI 不知道这次任务的边界
- AI 不知道之前为什么这么设计

所以更准确地说：

**Vibe Coding 的稳定性，取决于上下文工程的质量。**

没有上下文工程，AI 很容易：

- 每轮都重复问同样的问题
- 输出风格漂移
- 改坏原来的约定
- 把临时想法当成长期规则

---

## 3. 在这个项目里，上下文主要来自哪里

你可以把上下文来源理解成 7 层：

| 层级 | 文件或来源 | 作用 |
|------|------------|------|
| 1 | 当前对话 | 当前任务和临时要求 |
| 2 | 仓库结构 | AI 理解项目边界和模块分工 |
| 3 | `CLAUDE.md` | Claude Code 的项目级记忆 |
| 4 | `AGENTS.md` | 团队协作规则和文档协议 |
| 5 | `SKILL.md` | 某类任务的专用流程 |
| 6 | `TASKS.md` / `DECISIONS.md` / `CHANGELOG.md` | 当前状态、决策原因、变更历史 |
| 7 | `references/`、官方文档、外部资料 | 按需加载的补充知识 |

这也是为什么一个成熟项目不能只靠聊天记录。

---

## 4. `AGENTS.md`、`CLAUDE.md`、Rules 之间是什么关系

可以这样记：

- `CLAUDE.md`：Claude Code 的项目记忆入口
- `AGENTS.md`：团队写给代理的协作章程
- Rules：这些文件里真正约束行为的规则内容

也就是说：

- `AGENTS.md` 和 `CLAUDE.md` 是“载体”
- Rules 是“内容”

例如这几句都算 Rules：

- 提交前先看 `git diff`
- 只用中文写文档
- 不要提交 `.env`
- 任务完成后必须更新 `TASKS.md`

---

## 5. 什么信息应该写进文件，而不是只留在聊天里

更适合写进文件的内容：

- 长期有效的项目规则
- 目录结构和命名约定
- 提交流程
- 常用命令
- 当前任务状态
- 重要决策原因
- 可复用模板

只适合留在聊天里的内容：

- 这一次临时的小修改
- 还没确认的试探想法
- 很快就会过期的中间讨论

一个简单判断标准：

> 下次开新会话还需要它吗？

如果答案是“需要”，大概率就该落文件。

---

## 6. 新手最实用的上下文工程工作流

### 第一步：先定义项目级规则

至少明确：

- 文档语言
- Git 工作流
- 命名规范
- 敏感信息规则
- 任务结束要更新哪些文件

### 第二步：把规则放进固定文件

推荐分工：

- `CLAUDE.md`：精简项目记忆
- `AGENTS.md`：完整协作协议
- `SKILL.md`：某个 Skill 的专用规则

### 第三步：把“变化中的上下文”单独管理

不要把这些混进 `CLAUDE.md`：

- 当前任务
- 今日进展
- 临时 blocker

这些更适合写进：

- `TASKS.md`
- `DECISIONS.md`
- `CHANGELOG.md`

### 第四步：每次任务结束都更新

上下文工程不是“项目启动时写一次”，而是每轮都维护。

## 7. 一个最小可用结构

对一个 AI Coding 项目，最低配可以是：

```text
project/
├── CLAUDE.md
├── AGENTS.md
├── CHANGELOG.md
├── TASKS.md
└── DECISIONS.md
```

如果是 Skill 项目，再加：

```text
skills/my-skill/
├── SKILL.md
├── CHANGELOG.md
├── ROADMAP.md
├── TASKS.md
├── DECISIONS.md
├── scripts/
├── references/
└── assets/
```

## 8. 上下文工程里最常见的错误

下面 4 条是上下文管理里最高频的坑，每条都配一句对策。

### 把所有规则都堆进 `CLAUDE.md`

结果就是又长又乱，真正重要的规则反而不明显。

对策：`CLAUDE.md` 只放每次都需要的项目说明，长规则分进 `AGENTS.md` / `SKILL.md` / 单独文档，按需引用。

### 没有区分长期规则和当前任务

长期规则应稳定，当前任务应独立更新。

对策：长期规则进 `AGENTS.md` / `CLAUDE.md`；当前任务、今日进展、临时 blocker 进 `TASKS.md` / `DECISIONS.md` / `CHANGELOG.md`。

### 文件很多，但没有明确职责

不是文件越多越好，而是每个文件回答的问题要明确。

对策：每个文件只回答一类问题（项目说明 / 协作规则 / 当前状态 / 变更历史），用本篇「最小可用结构」对照。

### 只新增文档，不维护文档

过期文档比没有文档更危险。

对策：每轮任务结束都同步更新相关文件（见下方工作流第四步），而不是只在开始时写一次。

---

## 9. 对 Vibe Coding 最有帮助的几个动作

1. 把项目规则写进 `AGENTS.md` 或 `CLAUDE.md`
2. 把当前任务写进 `TASKS.md`
3. 把关键决策写进 `DECISIONS.md`
4. 把专用流程写成 `SKILL.md`
5. 每轮结束后同步文件，而不是只在聊天里说

## 10. 自测题

下面 3 题检验你是否理解了「上下文该放哪一层」。答案要点附在每题后。

1. 用本系列的「7 层上下文」判断：下面这几条信息，分别属于哪一层？
   - A：「这次任务先把 `todo.py` 的 `done` 命令修好」
   - B：「文档统一用中文」
   - C：「上次为什么用 `todos.json` 而不是 SQLite」

   **答案要点**：A → 第 1 层「当前对话」+ 落 `TASKS.md`（当前任务）；B → 第 4 层 `AGENTS.md`（长期项目规则）；C → 第 6 层 `DECISIONS.md`（决策原因）。

2. 判断对错：「上下文工程的核心，是把提示词写得越花哨越好。」

   **答案要点**：错。上下文工程的核心是「把关键信息稳定、分层、可维护地组织起来」，让 AI 每轮都拿到正确文件；提示词花哨是次要的。

3. 下面三条内容，哪些该落文件、哪些只留聊天？
   - A：「`todo.py` 的提交规范是 `type: summary`」
   - B：「这一版先不接登录，等下版再说」
   - C：「刚才那次生成结果有点怪，我再想想」

   **答案要点**：A → 落文件（`AGENTS.md` 长期规则）；B → 落文件（写进本次需求的「非目标」或 `TASKS.md`，下次开新会话还要用）；C → 只留聊天（还没确认的试探想法，短期过期，判断标准是「下次开新会话还需要它吗」）。

## 一句话总结

上下文工程的本质不是“多写几个规则文件”，而是让 AI 在每一轮都能拿到正确、稳定、可追溯的项目信息。
