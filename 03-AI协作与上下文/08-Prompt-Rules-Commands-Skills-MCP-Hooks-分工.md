# Prompt / Rules / Commands / Skills / MCP / Hooks，各自负责什么？

这篇文档只回答一个问题：

**你脑子里的一条「要求」，到底该塞进 Prompt、写进 Rules、做成 Command、Skill、接 MCP，还是配成 Hook？**

[什么是 AGENTS.md 和 CLAUDE.md](./02-什么是-AGENTS和-CLAUDE.md) 讲的是「载体」（规则写在哪些文件里）；[Rules 编写指南](./04-Rules-编写指南.md) 讲的是「内容」（怎样写一条好 Rule）。本篇讲的是更上一层：**Claude Code 提供的几类机制各自解决什么问题**。一句话——同样是「希望 AI 这么做」，放进不同机制，触发方式、能活多久、适合承载什么都完全不同。放错地方，要么每次都要重说一遍，要么长期污染上下文。

---

## 本篇目标

读完这篇，你应该能做到：

1. 说清 Prompt、Rules、Commands、Skills、MCP、Hooks 这 **6 类机制**各自负责什么、谁触发、能活多久。
2. 拿到一条需求，能照一张对照表判断它该放进哪一类、为什么。
3. 识别最常见的放错场景：把长期规矩写进 Prompt、把一次性任务塞进 Rules、想要「自动执行」却只用 Prompt 等。
4. 理解 Rules 与 MCP 的一条关键区别：Rules 约束行为，不提供能力。

本文不教某一种机制的写法细节（Command 怎么建、MCP 怎么配），只教「需求往哪一类放」。示例仍然沿用 [从需求到验收标准](./05-从需求到验收标准.md) 里的本地待办脚本 `todo.py`，保持连贯。

## 核心概念

### 一句话区分这 6 类

先给一张总表，后面再逐条展开。判断一条要求该放哪里，看三个维度：**谁触发它**（是你主动喊、AI 自己判断、还是事件自动跑）、**它能活多久**（只这一次、还是跨会话长期）、**它承载的是行为约束还是新能力**。

| 机制 | 负责什么 | 谁触发 | 能活多久 | 信息落在哪 |
|------|---------|--------|---------|-----------|
| Prompt | 这一次具体要让 AI 做什么 | 你每次发消息时主动输入 | 会话级（关掉就基本没了） | 直接写在对话输入框 |
| Rules | 项目长期稳定的规矩 | 会话开始时被自动读取（被动常驻） | 跨会话长期 | `AGENTS.md` / `CLAUDE.md` / `.claude/settings.json` |
| Commands | 把一段固定的多步指令封装成 `/名称` 一次调用 | 你输入 `/名称` 时主动触发 | 文件级长期，内容按需调用 | `.claude/commands/*.md` |
| Skills | 一类完整任务的可复用流程（带描述、脚本、资源） | AI 按 `SKILL.md` 描述自动触发，或在对话里说出 Skill 名让它用 | 文件级长期，按需加载 | Skill 目录下的 `SKILL.md` |
| MCP | 让 AI 调用仓库和对话里没有的外部工具或数据 | AI 在需要某项外部能力时发起调用 | 服务级常驻配置 | `.mcp.json` / MCP server 配置 |
| Hooks | 「每次发生 X 就自动做 Y」的事件自动化 | 工具调用或会话事件发生时自动触发 | 配置级长期 | `.claude/settings.json` 的 hooks 段 |

下面逐条说清「负责什么」和「别拿它干什么」。

### 1. Prompt：这一次的具体任务

Prompt 就是你在对话框里打的每一句话。它负责表达**这一次**的诉求，比如「给 `todo.py` 加一个 `done` 命令」。

- 谁触发：你自己。
- 能活多久：只在当前会话有效；换一次会话，它就消失了（详见 [上下文生命周期](./07-上下文生命周期.md)）。
- 适合放：一次性的、具体的目标和上下文。
- 别拿它放：长期规矩。如果你发现自己在每个会话开头都要重打一遍「这个项目只用中文」，说明它该升级成 Rule 了。

### 2. Rules：项目长期稳定的规矩

Rules 是你希望 AI **在项目里稳定遵守**的明确规则，比如「文档统一用中文」「commit 用 `type: summary`」「不提交 `.env`」。它们通常写在 `AGENTS.md` / `CLAUDE.md` / `.claude/settings.json` 里（详见 [什么是 AGENTS.md 和 CLAUDE.md](./02-什么是-AGENTS和-CLAUDE.md) 和 [Rules 编写指南](./04-Rules-编写指南.md)）。

- 谁触发：会话开始时被工具自动读取，AI「被动」知道，你不用每次提醒。
- 能活多久：跨会话长期保留。
- 适合放：长期、稳定、全项目适用的工作方式。
- 别拿它放：当前这一次的具体任务。把「今天把 done 命令写完」塞进 `CLAUDE.md`，就是 [上下文生命周期](./07-上下文生命周期.md) 里说的「临时任务污染长期规则」。

### 3. Commands：把重复的复杂指令封装成 `/名称`

Command（自定义斜杠命令）是存放在 `.claude/commands/` 下的 Markdown 文件，输入 `/名称` 就能把一整段预设指令插进对话。

- 谁触发：你主动输入 `/名称`。
- 能活多久：文件级长期，但内容是「你要用才加载」。
- 适合放：你**频繁**输入的同一段复杂、多步的指令。比如「读相关文件 → 改 → 跑验证 → 按规范提交」如果每次都手打一遍，封装成 `/done-flow` 就只打一个词。
- 别拿它放：一次性的指令（直接打 Prompt 更快），以及「希望 AI 自动做」的事（Command 仍要你手动喊，自动执行该用 Hook）。

### 4. Skills：一类完整任务的可复用流程

Skill 是一个可复用的能力包：用 `SKILL.md` 说清「我在什么场景触发、按什么步骤做」，再带上需要的脚本和资源。它和 Command 的差别在于**自洽程度**——Command 是一段指令模板，Skill 是一整套带脚本和说明的流程（Skill 怎么建、怎么工作，见 [基于模板创建](../04-创建Skill/03-基于模板创建.md)）。

- 谁触发：AI 根据你的需求和 `SKILL.md` 的描述**自己判断**要不要用，也可以由你显式调用。
- 能活多久：文件级长期，按需加载（不触发就不占上下文）。
- 适合放：一类**完整、可复用**的任务，比如「按模板新建一个 skill」「给一段代码写 review」。
- 别拿它放：只有你自己偶尔用一次的指令——那种做成 Prompt 或 Command 就够了，做成 Skill 反而要维护一套目录。

### 5. MCP：给 AI 接外部工具和数据

MCP（Model Context Protocol，模型上下文协议，一种让 AI 连接外部工具与数据源的标准协议）解决的是「AI 的能力面」。对话和仓库里没有的东西——比如公司内部知识库、某个数据库、一个只有网页入口的服务——靠 MCP 接进来，AI 才能去查、去调。

- 谁触发：AI 在需要某项外部能力时，作为一次工具调用来使用。
- 能活多久：服务级常驻，配置一次，会话里按需调用。
- 适合放：提供**对话之外的能力通道**（读外部数据、调外部接口）。
- 关键辨析：Rules **约束**行为（「不许联网」），MCP **提供**能力（「能查这个库」）。光在 Rules 里写「请参考公司知识库」是没用的——Rules 改变不了 AI 能调用的工具面，它只是嘴上被要求了却拿不到东西。要让 AI 真能查，得用 MCP 把那个库接进来。

### 6. Hooks：「每次发生 X 就自动做 Y」

Hook（钩子，在特定事件发生时自动执行的命令）做的是事件驱动自动化。Claude Code 在工具调用前后、会话开始结束等节点（如工具调用前 `PreToolUse`、工具调用后 `PostToolUse`、会话开始 `SessionStart` 等事件）会触发你配置的命令。

- 谁触发：**自动**触发，不需要你每次记得手动做。
- 能活多久：配置级长期。
- 适合放：「每次 X 就做 Y」这类**必须自动**的事。比如「每次提交前自动跑一遍链接检查」「会话开始时自动加载当前任务」。
- 别拿它放：需要你判断时机的事——Hook 是机械触发的，不该承担「要不要做」的决策。

## 实例分析

抽象的对照表看完了，下面用 `todo.py` 这个小项目，把 6 类常见需求挨个归类。每个需求先说「放哪」，再说「放别处会怎样」。

### 需求 1：「这次给 todo.py 加个 `done` 命令」 → Prompt

这是一次性的具体任务，活在当前会话里就够了。直接打在对话框，做完这一版就翻篇。

- 别放 Rules：它会污染长期规则，下个项目还以为「永远在加 done」。
- 别放 Skill：只做一次的事不值得维护一个能力包。

### 需求 2：「这个项目永远只用中文、commit 一律 `type: summary`」 → Rules

这是全项目、长期、稳定的工作方式。写进 `AGENTS.md` 或 `CLAUDE.md`，会话开始就自动加载，你不用每次重申。

- 别放 Prompt：否则每个会话开头都要背一遍，漏一次 AI 就漂移（见 [上下文生命周期](./07-上下文生命周期.md)）。

### 需求 3：「我每次都让 AI 按『读文件 → 改 → 验证 → 提交』走一遍」 → Command

你**频繁**重复的同一段复杂指令，封装成 `/dev-flow`，下次只打 `/dev-flow`。省得每次手打还容易写漏某步。

- 别放 Rules：Rules 是约束「该怎样」，不会替你把这段多步指令一次性灌进去。
- 别放 Prompt：每次重打太累，而且容易漂移。

### 需求 4：「团队经常要『按模板新建一个 skill』」 → Skill

这是一类完整、可复用的任务，自带模板和步骤说明。做成 Skill，AI 根据你的需求自己判断触发，或你显式调用。

- 别放 Command：Command 只是一段指令，带不上模板文件和配套脚本；这种自洽流程更适合 Skill。

### 需求 5：「让 AI 能直接读公司内部知识库再回答」 → MCP

这是「能力」需求，AI 当前够不着的外部数据，靠 MCP 把知识库接进来它才能查。

- 别放 Rules：在 Rules 里写「请参考公司知识库」是空的——AI 嘴上被要求了，实际拿不到那个库。能力要用 MCP 提供，行为约束才用 Rules。

### 需求 6：「每次提交前自动检查有没有漏更新 CHANGELOG」 → Hook

这是「每次 X 就自动做 Y」，必须自动触发，不能指望你每次记得手动喊。配成 Hook（比如 `PreToolUse` / 提交相关事件里跑一段检查脚本）。

- 别放 Prompt：Prompt 是你说了才做，不会自动。想要「自动」，就得交给 Hook。

### 一张「需求 → 该放哪里」决策表

把上面六条收敛成一张可以直接照着查的表。以后拿到一条要求，先问自己一句：**这是「这一次」还是「长期」？是我喊才做，还是要自动？是约束行为，还是提供能力？** 答案落在哪一行，就放进哪一类。

| 你想要的是…… | 放进哪类 | 一句话理由 |
|--------------|---------|-----------|
| 这一次的具体任务 / 问题 | Prompt | 一次性的，不该污染长期上下文 |
| 全项目都要遵守的长期规矩 | Rules | 自动常驻、跨会话稳定 |
| 频繁输入的同一段复杂指令 | Command | 一次定义、`/名称` 复用，免得每次重打 |
| 一类可复用的完整任务流程 | Skill | 按需触发、自带脚本与资源，适合打包 |
| 调用对话之外的外部系统 | MCP | 提供新能力通道（能力由 MCP 提供） |
| 「每次 X 就自动做 Y」 | Hook | 事件驱动，无需你记得手动 |

> 注意一个常被混的边界：**Rules 约束行为，MCP 提供能力，Hook 负责自动**。三件事不互相替代——想让 AI「自动」地「调用外部能力」并「遵守某条规矩」，往往要同时配 Hook + MCP + Rules，而不是指望其中一类包打天下。

## 常见错误

### 把长期规矩写进 Prompt

结果：每次开新会话都要重说一遍，漏一次 AI 就风格漂移；你还以为它「记得」。

对策：长期、稳定、全项目适用的规矩，升级成 Rule，写进 `AGENTS.md` / `CLAUDE.md`，让它自动常驻。

### 把一次性任务塞进 Rules / `CLAUDE.md`

结果：临时任务污染长期规则，文件越堆越乱，真正重要的规矩被淹没（详见 [上下文生命周期](./07-上下文生命周期.md) 的「上下文污染」）。

对策：当前这一次的任务留在 Prompt 或 `TASKS.md`；`CLAUDE.md` 只放长期稳定的内容。

### 想要「自动执行」，却只写在 Prompt 里

结果：Prompt 是你说了才做。你以为「以后每次都会自动检查」，其实你不喊它就不动。

对策：「每次 X 就做 Y」这类必须自动的事，配成 Hook；别指望 Prompt 替你自动。

### 用 Rules 去命令 AI「调用某个外部工具」

结果：AI 被要求了，却拿不到那个工具——Rules 改变的是行为约束，不是能力面。最后它要么坦白「我没有这个工具」，要么编一个看起来像的结果（接 [验证 AI 的工作](./06-验证-AI-的工作.md) 里的「幻觉」）。

对策：要让 AI 真能调外部系统，用 MCP 把能力接进来；Rules 只用来约束「该怎么用」。

### 同一件事写进好几类、互相打架

结果：Rules 写一版、Command 里又写一版、Prompt 里再强调一遍，三处口径不一致，AI 不知道信哪个——这正是 [上下文生命周期](./07-上下文生命周期.md) 说的「文件互相打架」型污染。

对策：守住单一事实源。一件事在一个权威地方维护，其它地方用链接或一句话指向它。

## 自测题 / 验收清单

拿你手头一个真实项目，把下面的需求逐条归类（每条只选最合适的一类），再对照理由：

- [ ] 「这个仓库永远不提交 `.env`」 → 你选了哪一类？为什么？
- [ ] 「今天把 README 的快速开始补完」 → 哪一类？为什么不能放进 Rules？
- [ ] 「我每次都要让 AI 按固定结构生成一份周报」 → Command 还是 Skill？两者差别在哪？
- [ ] 「让 AI 能查我们内部的 API 文档站」 → 为什么 Rules 不够、必须 MCP？
- [ ] 「每次工具调用后自动记录一条日志」 → 为什么必须是 Hook 而不是 Prompt？
- [ ] 你能说清 Rules、MCP、Hook 三者的边界（约束行为 / 提供能力 / 自动执行）吗？

小练习：翻一下你自己常对 AI 说的三句话，判断它们现在是被你当成 Prompt 每次重打、还是已经落进了正确的机制。如果有哪句你每周都要重复说一遍，多半它该升级成 Rule 或 Command 了。

## 一句话总结

同样一句「希望 AI 这么做」，放进 Prompt、Rules、Commands、Skills、MCP、Hooks 中的哪一类，决定了它由谁触发、能活多久、适合承载什么——拿到要求先问「这一次还是长期、我喊还是自动、约束行为还是提供能力」，答案落进哪一行，就放进哪一类。
