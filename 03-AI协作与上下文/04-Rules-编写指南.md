# Rules 编写指南

## 本篇目标

读完这篇，你应该能做到：

1. 说清一条「好 Rule」和一条「坏 Rule」的区别（具体 / 可执行 / 有边界 / 可验证 / 稳定）。
2. 用一个固定模板把一条规则写具体，而不是停在「注意质量」这种空话。
3. 判断一条规则该写进 `CLAUDE.md`、`AGENTS.md`、`SKILL.md` 还是 `.claude/settings.json`。
4. 识别新手最常犯的规则编写错误，并能给出改法。

本篇是方法论篇（讲「怎么写」），配合 [上下文工程入门](./03-上下文工程入门.md)（讲「放哪一层」）一起读效果最好。

## 前置知识

读这篇前，建议你已经了解：

- [什么是 AGENTS.md 和 CLAUDE.md](./02-什么是-AGENTS和-CLAUDE.md)：知道 `CLAUDE.md` / `AGENTS.md` / `SKILL.md` / `.claude/settings.json` 各管什么。
- [上下文工程入门](./03-上下文工程入门.md)：知道规则属于上下文的哪一层、该落文件还是只留聊天。

不需要会写代码。本系列示例用一个贯穿小项目——本地命令行待办脚本 `todo.py`，本篇会用它出几道改写题。

这篇文档只回答一个问题：

**项目里的 Rules 到底怎么写，AI 才更容易稳定执行。**

---

## 1. 什么是 Rule

Rule 就是：

> 你希望 AI 在项目里稳定遵守的明确规则。

比如：

- 文档统一用中文
- commit message 使用 `type: summary`
- 不要提交 `.env`
- 改完文档后要更新 `CHANGELOG.md`

Rule 不一定非要叫 Rule，它可以写在：

- `AGENTS.md`
- `CLAUDE.md`
- `SKILL.md`
- 模板说明文档

---

## 2. 好的 Rule 长什么样

好的 Rule 通常有 5 个特点：

### 具体

不要写：

```text
写得专业一点
```

更好写法：

```text
commit message 使用 `type: summary` 格式，type 仅限 `feat`、`fix`、`docs`、`refactor`、`chore`、`test`
```

### 可执行

不要写：

```text
尽量清晰
```

更好写法：

```text
每次修改完成后，先运行链接检查，再更新 `TASKS.md` 和 `DECISIONS.md`
```

### 有边界

不要让一条 Rule 既管文档、又管代码、又管发布。

### 可验证

看完之后应该知道怎么检查是否做到。

### 稳定

长期规则才适合写进项目规则文件，临时要求不要硬塞进去。

---

## 3. 坏 Rule 和好 Rule 对比

### 例子 1

坏：

```text
注意代码质量
```

好：

```text
修改前先阅读相关文件；修改后至少做一次与改动直接相关的验证，并在最终说明中写明是否已验证
```

### 例子 2

坏：

```text
文档写完整一点
```

好：

```text
文档使用中文；新增教程时至少包含“适用场景、步骤、常见问题、继续阅读”四个部分
```

### 例子 3

坏：

```text
规范提交
```

好：

```text
commit message 使用 `type: summary`；一次提交只表达一件主要事情；push 前先查看 `git diff --staged`
```

## 4. Rules 应该写到哪里

### 写进 `CLAUDE.md`

适合放：

- 项目目标
- 长期有效的工作规则
- 常用命令
- 关键目录说明

### 写进 `AGENTS.md`

适合放：

- 协作协议
- 文档更新要求
- Git 工作流
- 命名规范
- 完成标准

### 写进 `SKILL.md`

适合放：

- 这个 Skill 在什么场景触发
- 这个 Skill 的操作步骤
- 这个 Skill 的输入输出要求

### 写进 `.claude/settings.json`

适合放：

- 权限限制
- 环境变量
- 工具行为配置

也就是说：

**不是所有 Rule 都该写在 Markdown 里。**

---

## 5. 一个推荐的 Rule 写法模板

你可以直接套这个结构：

```markdown
## 规则标题

- **目的**：这条规则解决什么问题
- **适用范围**：什么时候适用
- **要求**：必须做什么
- **禁止项**：不要做什么
- **验证方式**：怎么确认执行到了
```

例如：

```markdown
## Commit 规则

- **目的**：让提交历史可读、可追溯
- **适用范围**：所有 Git 提交
- **要求**：commit message 使用 `type: summary`
- **禁止项**：不要使用 `update`、`final`、`fix bug`
- **验证方式**：`git log --oneline` 可一眼看出每次提交的类型和对象
```

---

## 6. 规则不要写得太多

常见误区是：一上来写 100 条规则。

结果通常是：

- AI 不容易抓住重点
- 人也不会维护
- 很多规则互相重复

更好的做法是：

1. 先写最关键的 5 到 10 条
2. 先覆盖高频问题
3. 以后根据真实踩坑再补

---

## 7. 什么规则最值得优先写

如果你是新项目，优先写这几类：

- 语言与文档规则
- Git / commit / 分支规则
- 敏感信息规则
- 测试与验证规则
- 任务完成后要更新哪些文件
- 目录与命名规范

这几类通常比“代码风格哲学”更先产生实际价值。

---

## 8. 什么时候要改 Rule

这几种情况最值得更新规则：

- 同一个错误重复出现了两次以上
- 不同协作者对同一件事理解不一致
- 项目结构已经变了
- 原规则太模糊，导致执行结果漂移

更新规则时，建议同步更新：

- `AGENTS.md` 或 `CLAUDE.md`
- `DECISIONS.md`
- 必要时更新 `CHANGELOG.md`

---

## 9. 一个适合 starter 项目的基础 Rule 清单

可以作为最低配参考：

- 文档统一使用中文
- 相对路径必须可检查、可跳转
- 修改前先阅读相关文件
- commit message 使用 `type: summary`
- 不提交密钥、Token、`.env`
- 任务完成后更新 `TASKS.md` 和 `DECISIONS.md`
- 对外可见变更更新 `CHANGELOG.md`

## 常见错误

下面 5 条是写 Rule 时最常踩的坑，每条都配一句改法（和前面「坏 Rule / 好 Rule」对比一脉相承）。

### 规则停在形容词，不可执行

坏例子：「注意代码质量」「写得专业一点」。

对策：把形容词换成具体动作。比如改成「修改前先阅读相关文件；修改后至少做一次与改动直接相关的验证，并在最终说明中写明是否已验证」。

### 规则没有边界，一条管所有事

后果：一条 Rule 既管文档、又管代码、又管发布，AI 不知道何时适用，执行结果漂移。

对策：每条 Rule 写清「适用范围」，让一条规则只回答一件事。

### 规则不可验证，做完不知道对不对

后果：「文档写完整一点」这种规则，AI 做完了你也判不了是否达标。

对策：每条 Rule 配一句「验证方式」——能用命令跑出来、能用文件内容核对。比如「文档使用中文；新增教程至少包含『本篇目标 / 前置知识 / 常见错误 / 自测题』四段」。

### 规则全堆进 `CLAUDE.md`，没分文件

后果：`CLAUDE.md` 越来越长，权限该进 `settings.json` 的也写成了说明文字，工具并不强制执行。

对策：按「写到哪里」分工——项目说明进 `CLAUDE.md`、协作协议进 `AGENTS.md`、Skill 专用流程进 `SKILL.md`、权限/环境变量进 `.claude/settings.json`。

### 一上来写 100 条，没人维护

后果：规则太多，AI 抓不住重点，人也不会维护，很多还互相重复。

对策：先写最关键的 5 到 10 条，先覆盖高频问题（语言/文档、Git/commit、敏感信息、测试验证、任务收尾），以后按真实踩坑再补。

## 自测题

下面 3 题考的是把「坏 Rule」改写成「好 Rule」。参考答案附后。

1. 把这条坏 Rule 改成可执行版本：「规范提交」。

   **参考答案**：「commit message 使用 `type: summary` 格式，type 仅限 `feat`/`fix`/`docs`/`refactor`/`chore`/`test`；一次提交只表达一件主要事情；push 前先看 `git diff --staged`。验证方式：`git log --oneline` 可一眼看出每次提交的类型和对象。」

2. 下面两条规则，哪条更好？为什么？
   - A：「`todo.py` 的代码写得优雅一点」
   - B：「`todo.py` 只用 Python 3 标准库，不引入第三方包；数据存成 `todos.json`」

   **答案要点**：B 更好。B 具体、可执行（限制依赖、指定存储）、可验证（看 `requirements` 和文件后缀）；A 是形容词，AI 无从下手，你也判不了。

3. 这条规则应该写进哪个文件？给出理由：「禁止 Claude 读取 `.env`、`.env.local`」。

   **答案要点**：应写进 `.claude/settings.json`（这是要工具强制执行的权限/行为配置），而不是 `CLAUDE.md`（那只是给 Claude 看的说明，不会强制执行）。理由：规则是「机器要执行」的配置，不是「给人/模型看」的说明。
