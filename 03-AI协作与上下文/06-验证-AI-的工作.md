# 验证 AI 的工作

这篇文档只回答一个问题：

**AI 说「我做完了」，你怎么确认它真的做完了、而且做对了？**

如果你读过 [从需求到验收标准](./05-从需求到验收标准.md)，会记得它反复强调一句话：需求不清、边界不清、验收不清是 Vibe Coding 失败的三大原因。其中「验收不清」这一条，本篇专门展开——上一篇讲的是「怎么把验收标准写清楚」，本篇讲的是**标准写好之后，你怎么一条一条地去核对 AI 的产出**。

---

## 本篇目标

读完这篇，你应该能做到：

1. 说清「验证」为什么是一条从「看起来对」到「真的对」的梯度，需要逐级往上走。
2. 拿到 AI 的产出后，按一个固定流程逐条验证，让结果经得起复核。
3. 识别两种最坑人的失败：**假绿**（测试全过但功能其实用不了）和**幻觉**（AI 自信地编出不存在的接口）。
4. 把验证证据留下来，让「完成」这件事换个人也能复核。

本文不教代码本身，只教「怎么验」。示例仍然沿用 [05](./05-从需求到验收标准.md) 那个本地待办脚本 `todo.py`，保持连贯。

## 核心概念

### 什么是「验证」

验证就是一句话：

> 拿到 AI 的产出后，用眼睛看、用命令跑、用文件核对，独立确认它确实达到了验收标准。

关键词是**独立**。验证的关键在于亲自核对：别只问 AI「做完了没有」，因为它一定会自信地回答「做完了」。AI 的「已完成」只是一份**待核实的声明**，要等你自己确认之后，才算结论。

### 为什么不能只靠 AI 的自我报告

AI 在报告进度时有两类典型问题：

- **过度自信**：它常常把「我写了代码」直接说成「功能已完成」，跳过「我到底有没有真的跑通」这一步。
- **幻觉**（AI 自信地说出并不存在的东西，比如一个根本不存在的函数名、API 参数或库版本）：它可能给出一个看起来很合理、但实际跑不起来的用法。

所以有一条很实用的经验：

> 你拿到的，只是一份**待验证的草稿**；它算不算「已通过的结果」，要等你验证完才说了算。

### 验证梯度：从「看起来对」到「真的对」

验证不会一步到位，它更像一条梯度。越往上越可信，但也越费事：

| 等级 | 你做了什么 | 能挡掉什么问题 |
|------|-----------|----------------|
| 1 | 代码能通过语法/编译检查 | 拼写错误、明显语法错 |
| 2 | 自动化测试通过（单元测试、lint） | 逻辑错、约定违反 |
| 3 | **实际运行**，看到预期输出 | 「能编译，但跑起来是错的」 |
| 4 | 对照验收清单**逐条人工核对** | 测试没覆盖到的边界和需求 |
| 5 | **留下证据**并能复现 | 「我说改好了」却拿不出证明 |

很多人卡在第 2 级就停了——「测试是绿的，应该没问题」。可第 2 级恰好是**假绿**最爱藏身的地方。真正可靠的完成，至少要做到第 4 级，最好再补上第 5 级。

### 两个最该警惕的陷阱

- **假绿**（所有自动检查都显示通过、但功能其实并不可用）：绿灯只代表「被测到的部分没错」，代表不了「功能整体能用」。如果测试根本没覆盖到那条改动路径，绿灯就是个假象。
- **幻觉**：AI 可能让你去调用一个不存在的接口。比如它会建议「用 `json.write()` 保存数据」——可 Python 标准库里只有 `json.dump()`，并没有 `json.write()`。照着写，代码一跑就报错。

光看「测试绿不绿」这两类问题都发现不了，必须实际运行加人工核对。

## 动手步骤

下面用 `todo.py`（来自 [05](./05-从需求到验收标准.md)）走一遍完整验证。假设 AI 刚报告：「`add` / `list` / `done` 都已完成」。下面这 **7 步**，就是你把它从「声明」变成「已验证」的过程：

### 第 1 步：把验收清单摆在手边

先把 [05](./05-从需求到验收标准.md) 第 5 步那份清单拿出来。验证要**对着清单逐条勾**，避免漫无目的地「点点看」。没有清单，你会不自觉地只测顺手的那几条，漏掉难验证的。

### 第 2 步：逐条跑命令，对照预期输出

照着清单里的输入输出契约敲命令，看屏幕**实际**打印了什么：

```text
python todo.py add "买牛奶"   期望：已添加 #1：买牛奶
python todo.py list           期望：带编号的待办列表
python todo.py done 1         期望：已完成 #1
```

每一条都要**眼见**到预期输出，「没报错」并不等于「对了」。`list` 到底有没有打印出 `#1 买牛奶`？`done` 之后提示对不对？

### 第 3 步：打开数据文件，核对真实内容

命令的打印只是表面，**真实状态在文件里**。打开 `todos.json` 看：

- `add` 之后，文件里是不是真的多了一条 `{"id": 1, "title": "买牛奶", "done": false}`？
- `done 1` 之后，那条的 `done` 是不是真的变成了 `true`？

这一步能挡住「命令打印对了、数据却没写进去」这类假绿。

### 第 4 步：专门测边界和异常

正常路径往往是对的，问题藏在边界。至少试这几条：

- 还没 `add` 过任何待办时，`list` 会不会崩？
- `done` 一个**不存在**的编号（比如 `done 99`），是给出友好提示，还是直接抛一堆报错？
- 不传子命令（只敲 `python todo.py`），是不是按清单要求「打印用法并以非 0 退出码退出」？

退出码（程序结束时返回给系统的一个数字，0 表示成功、非 0 表示出错）很容易被忽略，可它恰恰是脚本「有没有按约定失败」的关键证据。

### 第 5 步：用 `git diff` 检查有没有多余改动

验证既要看「该做的做了没」，也要看「**不该做的有没有偷偷做**」。用 Git 查看改动（Git 基础见 [Git 入门](../02-工具指南/01-Git-入门.md)）：

- AI 有没有顺手 `pip install` 了 [05](./05-从需求到验收标准.md) 里明确禁止的第三方包？
- 有没有改了你没要求动的别的文件？
- 有没有把临时调试用的 `print` 留在代码里？

任何超出验收清单的改动，都是一次「AI 替你做的随机决定」，要么删掉、要么明确接受。

### 第 6 步：把验证证据留下来

「我验证过了」如果只是口头一句，下次就说不清。把证据落成可复核的东西：

- 命令的实际输出，贴进任务记录或 PR 描述；
- 关键文件内容（比如验证后的 `todos.json`）一并附上；
- 必要时截图。

留证据的目的，是让「完成」这件事**换个人也能复核**，而不仅靠你的一句话。

### 第 7 步：失败就复盘并落文件

如果第 2~5 步发现了问题，别只在聊天里说「这里不对，再改改」。把失败原因写进项目的决策或任务文档（参考 [上下文工程入门](./03-上下文工程入门.md) 和 [上下文生命周期](./07-上下文生命周期.md)）：

- 这次为什么没过？是验收标准不够清楚，还是 AI 又自由发挥了？
- 要不要补一条 [Rule](./04-Rules-编写指南.md)，把这个坑固定下来，避免下次重犯？

复盘落文件，失败的次数才会真正递减。

## 实例分析

下面两个案例，都是「测试看起来没问题、实际却藏着坑」的典型。

### 案例 1：假绿——绿灯全亮，功能却不能用

AI 给 `done` 写了测试，内容大致是「调用 `mark_done(1)` 后，函数返回值非空」。测试跑过，一片绿。

可你照第 3 步打开 `todos.json`，发现那条待办的 `done` 字段**根本没变成 `true`**——函数只是返回了一个状态字符串，**没把结果写回文件**。

教训：绿灯只证明「被测的函数返回了非空」，证明不了「功能（持久化完成状态）真的生效」。这正是只停在梯度第 2 级的代价——必须再往上走到第 3、4 级，实际运行并核对文件，假绿才会露馅。

### 案例 2：幻觉——照着不存在的接口写代码

AI 告诉你：「保存待办用 `json.write(todos, "todos.json")` 就行。」代码看着很顺，你甚至没怀疑。

可一运行就报错：`AttributeError: module 'json' has no attribute 'write'`。Python 标准库里**根本没有 `json.write`**，正确写法是 `json.dump(todos, f)`。

教训：面对 AI 给的「某个函数、参数或库怎么用」，凡没把握的，**当场查一下官方文档再信**。幻觉最擅长把不存在的接口说得理直气壮。这也是 [05](./05-从需求到验收标准.md) 建议第一版只用标准库的原因——依赖越少，被幻觉带偏的接口面就越小。

## 常见错误

### 错误 1：只听 AI 说「已完成」

结果：把「声明」当「结论」，问题拖到后面才爆，返工更大。

对策：把 AI 的「已完成」当成待办，照第 2~5 步逐条核实。

### 错误 2：只看测试通过，不实际用功能

结果：撞上假绿——测试覆盖不到的路径出问题，你却以为一切正常。

对策：测试只是梯度第 2 级，必须再实际运行、核对真实文件（第 3、4 级）。

### 错误 3：不核对文件真实内容

结果：命令打印对了，数据其实没写进去或写错了。

对策：每个涉及状态的功能，都要打开对应文件看真实内容。

### 错误 4：不留证据、不复盘

结果：「我说改好了」无法复核，同样的坑下次还会踩。

对策：留下命令输出、文件内容或截图；失败原因写进决策或任务文档。

### 错误 5：被幻觉带偏，照着不存在的接口改

结果：代码根本跑不起来，还白白浪费时间去猜错在哪。

对策：对 AI 给的接口、参数、版本特性没把握时，先查官方文档再采用。

## 自测题 / 验收清单

拿你最近一次让 AI 完成的小功能，对照下面这份清单，看你的「验证」合不合格。每条都答「能」，才算真正完成：

- [ ] 我手边摆着一份**验收清单**，正在逐条勾，没有随手点点看？
- [ ] 我**逐条跑过命令**，并亲眼看到预期输出了吗？
- [ ] 涉及数据的功能，我**打开文件核对**了真实内容吗？
- [ ] 我**测过边界和异常**（空列表、不存在的编号、不传参数）吗？
- [ ] 我**检查过退出码**是否符合约定吗？
- [ ] 我用 `git diff` 看过**有没有多余改动或没要求的依赖**吗？
- [ ] 我**留下证据**（输出、文件内容或截图），让别人也能复核吗？
- [ ] 如果失败过，我**把原因落进了文件**，避免下次重犯吗？

小练习：故意让 AI 漏掉 `done` 的「写回文件」那一步（或自己删掉那行），然后只跑测试——你会看到绿灯。再照第 3 步打开文件，体会「假绿」有多容易骗过只看测试的人。

## 一句话总结

验证 AI 的工作，就是把「AI 说做完了」一步步变成「我逐条核对过、实际跑过、证据留得下」。下次验收前，不妨先问自己一句：我是真的核对了，还是只是相信了那句「已完成」？
