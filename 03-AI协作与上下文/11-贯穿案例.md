# 贯穿案例：从模糊想法到提交 PR

上一篇 [任务拆解与迭代](./09-任务拆解与迭代.md) 给了拆任务的方法。这篇把 05 到 09 的方法论用一个真实小项目串起来，完整走一遍从模糊想法到提交 PR 的全过程。

具体说，这篇回答一个问题：

**手里只有一个「我想要个能记录每天做了啥的工具」这种模糊念头时，怎么带着 AI 把它一步步做成一个能跑、能验、能提交的小项目？**

前面五篇（[从需求到验收标准](./05-从需求到验收标准.md)、[验证 AI 的工作](./06-验证-AI-的工作.md)、[上下文生命周期](./07-上下文生命周期.md)、[Prompt/Rules/Commands/Skills/MCP/Hooks 分工](./08-Prompt-Rules-Commands-Skills-MCP-Hooks-分工.md)、[任务拆解与迭代](./09-任务拆解与迭代.md)）各自讲了一个环节。本篇是 AI 协作主线的收尾篇——不引入新方法，而是把那五篇串起来，让你看到它们在一次真实协作里怎么接力。

读完这篇，你应该能做到：

## 核心概念：一次完整协作长什么样

一次完整的 AI 协作，不是「丢需求 → 收代码」两步，而是 **6 个阶段**的接力。每个阶段都有对应的方法论篇做后盾，每个阶段都产出能落进文件的东西：

| 阶段 | 做什么 | 对应方法论篇 |
|------|-------|------------|
| 1. 澄清需求 | 把模糊想法变成可验收需求（补齐目标、范围、非目标、约束、可观察完成条件） | [05 从需求到验收标准](./05-从需求到验收标准.md) |
| 2. 计划 | 拆成可分批实现的任务、排出顺序、留回退点（指可随时退回去的已验证状态） | [09 任务拆解与迭代](./09-任务拆解与迭代.md) |
| 3. 实现 | 分批写代码、每批能独立验证、独立提交 | [09](./09-任务拆解与迭代.md) + [07 上下文生命周期](./07-上下文生命周期.md) |
| 4. 验证 | 事实核验、跑命令、核对文件、识别假绿（测试全过但功能其实用不了） | [06 验证 AI 的工作](./06-验证-AI-的工作.md) |
| 5. 文档同步 | 更新 `CHANGELOG` / `TASKS` / `DECISIONS`，让上下文跨会话可恢复 | [07 上下文生命周期](./07-上下文生命周期.md) |
| 6. 提交 PR | 按规范提交、发起 PR（Pull Request，向仓库发起的一次合并请求，供他人或自己审阅） | [02-工具指南/04 提交规范](../02-工具指南/04-提交到-GitHub-与-Commit-规范.md) |

注意这张表和单篇的关系：05/06/07/09 各管一行（09 甚至管 2、3 两行），08 则贯穿全程——决定每条要求该放 Prompt 还是 Rules（见实例分析阶段 1）。下面用一个真实小项目把这 6 个阶段完整走一遍。

## 实例分析：从「记录每天做了啥」到 PR

设想你是用户，脑子里只有一个模糊念头：

> 我想要个能记录每天做了啥的工具。

下面这 **6 个阶段**（和上面表格一一对应），就是把这个念头变成一个已提交 PR 的全过程。仍然用全系列统一的小项目 `todo.py`（本地命令行待办脚本，Python 3 标准库、存 `todos.json`、`add` / `list` / `done` 三命令）。

### 阶段 1：澄清需求——把模糊想法逼成可验收需求

「记录每天做了啥」这句话几乎什么都可能：网页日记？Excel？手机 App？AI 不知道，于是会替你随机决定一个。所以第一件事不是开写，而是 [05 从需求到验收标准](./05-从需求到验收标准.md) 教的——**逼问自己 7 个要素**，把想法变成一份可验收需求（验收标准：什么样子的结果算「做完了」，能用命令或文件核对）。

你可以直接让 AI 帮你把模糊想法扩成需求草稿，但要你来拍板。来回几轮后，需求收敛成：

```text
# 需求：本地命令行待办脚本 todo.py
目标：做一个本地命令行工具，记录、查看、完成待办
用户：只有我自己，单机使用
范围（第一版做）：add 添加、list 列出、done 标记完成
非目标（第一版不做）：删除、编辑、截止日期、提醒、分类、多用户、网页界面
约束：Python 3 标准库，不装第三方包，不联网；数据存在当前目录的 todos.json
输入输出：
  python todo.py add "买牛奶"  →  打印「已添加 #1：买牛奶」
  python todo.py list          →  打印带编号的待办列表
  python todo.py done 1        →  打印「已完成 #1」
可观察的完成条件：
  [ ] add 后 todos.json 出现 {"id":1,"title":"买牛奶","done":false}
  [ ] list 能打印至少一行带编号的待办
  [ ] done 1 后 todos.json 里那条 done 变成 true
  [ ] todos.json 不存在时首次 add 自动建文件不报错
  [ ] 不传子命令时打印用法、以非 0 退出码退出
```

两个最值钱的字段——「非目标」和「可观察的完成条件」——一个挡掉 AI 的自由发挥，一个把「完成」从感觉变成可核对（详见 [05](./05-从需求到验收标准.md) 的 7 要素）。

> 这一阶段的要求是「这一次」的，按 [08 Prompt/Rules/Commands/Skills/MCP/Hooks 分工](./08-Prompt-Rules-Commands-Skills-MCP-Hooks-分工.md) 应放 Prompt（直接打在对话框），别塞进 `CLAUDE.md` 污染长期规则。

把这份需求存进仓库（比如作为这次任务的 `TASKS.md` 开头），它就是后面所有阶段的依据。

### 阶段 2：计划——拆成可分批实现的任务、留回退点

需求清楚了，但三件事（add / list / done）一口气丢给 AI，正是 [09 任务拆解与迭代](./09-任务拆解与迭代.md) 警告的「难验证、难回退、难定位」。所以先让 AI 调查现状、再拆批。

调查很简单（项目还没代码，现状是空），关键是别让 AI 凭「待办一般怎么写」的刻板印象去用 SQLite 或装第三方包——验收清单已写明只用标准库、存 `todos.json`。

基于调查，把任务拆成 3 批，每批都能独立验证、独立提交：

```text
批次 1：搭骨架 + add 命令
  验收：add 后 todos.json 出现对应条目
批次 2：list 命令
  验收：list 打印出带编号的列表
批次 3：done 命令
  验收：done 1 后文件里那条 done 变 true
```

这份分批计划落进 `DECISIONS.md`（记录「为什么这么拆」），3 个批次作为待办写进 `TASKS.md`——否则长会话压缩后，AI 会忘了自己定的顺序（接 [07](./07-上下文生命周期.md) 的「压缩与遗忘」）。这里就开始累积回退点：每批做完就提交一次，仓库里任何时候都有一份「已知能用」的状态。

### 阶段 3：实现——分批写代码，做完一批验一批

接下来一批一批做，每批走「实现 → 验证 → 提交」。以批次 1 为例，AI 产出 `add` 的核心片段大致是这样（不是完整实现，只示意形状）：

```python
import json
from pathlib import Path

DATA = Path("todos.json")

def add(title):
    todos = json.loads(DATA.read_text()) if DATA.exists() else []
    todo = {"id": len(todos) + 1, "title": title, "done": False}
    todos.append(todo)
    DATA.write_text(json.dumps(todos, ensure_ascii=False, indent=2))
    print(f"已添加 #{todo['id']}：{title}")
```

形状对了不等于做对了——立刻进阶段 4 验证。验证通过再提交：`feat: add 添加待办并写入 todos.json`。批次 2（list）、批次 3（done）同样走一遍。每批一个提交，意味着任何时刻仓库里都有一份「已知良好」的状态——这就是回退点的价值，下一阶段会看到它真正救命的时刻。

### 阶段 4：验证——别信「已完成」，去核对事实

假设批次 3 的 `done` 撞上 [06 验证 AI 的工作](./06-验证-AI-的工作.md) 的经典陷阱——**假绿**：AI 给 `done` 写了测试，测试一片绿，可你打开 `todos.json`，发现那条的 `done` 字段**根本没变成 `true`**（函数只返回了一个状态，没把结果写回文件）。

光看「测试绿」发现不了。照 [06](./06-验证-AI-的工作.md) 的梯度往上走，至少要到第 3、4 级——**实际运行 + 打开文件核对真实内容**：

```text
$ python todo.py done 1
已完成 #1
$ cat todos.json        # 打开看真实内容
[{"id": 1, "title": "买牛奶", "done": false}]   # ← 假绿露馅：done 还是 false
```

命令打印对了、数据却没写进去——这就是为什么 [06](./06-验证-AI-的工作.md) 反复强调「亲自核对、别只信自我报告」。定位到是批次 3 的问题后，因为有阶段 2 留的回退点，你不用整体推倒：让 AI 基于批次 2 的状态只修 `done` 的「写回文件」这一步，重验通过，再提交 `feat: done 标记完成`。

> 另一个该顺手查的是 `git diff`：AI 有没有顺手 `pip install` 了 [05](./05-从需求到验收标准.md) 明确禁止的第三方包？有没有把临时调试用的 `print` 留在代码里？任何超出验收清单的改动，都是一次「AI 替你做的随机决定」。

### 阶段 5：文档同步——让上下文跨会话可恢复

功能做完、验证通过，但还有一步常被跳过：**把这次的过程产物同步进项目文档**。这不是走形式，而是 [07 上下文生命周期](./07-上下文生命周期.md) 讲的核心——会话上下文会消失，只有落进文件才跨会话保留。

按 [07](./07-上下文生命周期.md) 的三分法把信息分进对的文件：

```text
TASKS.md       勾掉 add/list/done 三项；把「删除/编辑」明确记进非目标
DECISIONS.md   记一条「第一版只用标准库、存 todos.json，不引入数据库」
CHANGELOG.md   写一行用户可见的变更：
               - add/list/done 三命令上线，待办存于 todos.json
```

写错文件等于制造上下文污染（过时、错误或本不该长期保留的信息混进了 AI 依据的上下文）。比如把「这次先不写测试」这种临时妥协塞进 `CLAUDE.md`，AI 会当成永久规则——这正是 [07](./07-上下文生命周期.md) 说的「临时当成长期」型污染。该进 `TASKS.md` 的就别进 `CLAUDE.md`。

### 阶段 6：提交 PR——按规范把成果交出去

最后把验证过的改动按规范提交、发起 PR。单人项目也要走这一步——PR 描述本身就是一份「这次做了什么、为什么、怎么验的」的留档。

照 [提交到 GitHub 与 Commit 规范](../02-工具指南/04-提交到-GitHub-与-Commit-规范.md) 的节奏：每批一个 `type: summary` 格式的 commit（commit 即一次提交记录），一个分支只做这一件事：

```bash
git switch -c feat/todo-script
# 批次 1/2/3 各一次提交（已在阶段 3 做过）
git push -u origin feat/todo-script
```

PR 描述照 [02-工具指南/04](../02-工具指南/04-提交到-GitHub-与-Commit-规范.md) 的模板，把验证证据也贴进去——这正是 [06](./06-验证-AI-的工作.md) 说的「留下证据，让完成这件事换个人也能复核」：

```text
## 改动
- 新增 todo.py（add/list/done 三命令）
- 新增 todos.json 数据格式

## 原因
- 记录每天做了啥，第一版只要能添加/列出/标记完成

## 验证
- python todo.py add "买牛奶" → todos.json 出现对应条目 ✓
- python todo.py list → 打印带编号列表 ✓
- python todo.py done 1 → todos.json 中 done 变 true ✓（已修复假绿）
```

到这里，一个模糊念头就走完了从想法到 PR 的全程。

## 常见错误

### 拿到想法直接让 AI 开写

「记录每天做了啥」这种模糊念头直接丢给 AI，它会替你随机决定形态（网页？App？数据库？），结果离你想要的越来越远。对策：先经阶段 1 的 7 要素澄清，把模糊逼成可验收需求，再动手（见 [05](./05-从需求到验收标准.md)）。

### 把整个任务一口气丢给 AI

三件事一起改，难验证、难回退、难定位——某个行为错了，你不知道是 add、list 还是 done 坏的。对策：拆成可独立验收的批次，每批做完即验、即提交（见 [09](./09-任务拆解与迭代.md)）。

### 某批做完不验证就急着进下一批

错误会叠加。三批都没验就往下走，最后发现假绿时，根本分不清是哪一批引入的。对策：每批做完立刻照验收清单验证（实际运行 + 核对文件），通过了才进下一批（见 [06](./06-验证-AI-的工作.md)）。

### 文档只在脑子里，没同步进文件

「我刚才怎么决定的」只留在会话里，开个新会话 AI 又从零猜。对策：决策进 `DECISIONS.md`、待办进 `TASKS.md`、用户可见变更进 `CHANGELOG.md`，让上下文跨会话可恢复（见 [07](./07-上下文生命周期.md)）。

### 把验证全交给 AI 的自我报告

AI 一定自信地说「已完成」，可它常把「写了代码」直接说成「功能可用」。对策：把它的「已完成」当待办，照梯度逐条核实，至少到实际运行 + 核对文件这一级（见 [06](./06-验证-AI-的工作.md)）。

### 一个 PR 塞一堆无关改动

文档、脚本、顺手重构堆在一个 PR 里，review 难看、回退也难。对策：一个分支只做一件事，一个 commit 只表达一件主要事情（见 [02-工具指南/04](../02-工具指南/04-提交到-GitHub-与-Commit-规范.md)）。

## 自测题 / 验收

拿你手头一个真实小需求，照这 6 阶段走一遍，逐条对照：

1. 你的想法经过阶段 1 后，有没有产出一份带「非目标」和「可观察完成条件」的需求？换个人不问你，能照它判定通过吗？
2. 你把任务拆成了可独立验收的批次，每批都有对应的验收点和提交，而不是一口气全改吗？
3. 每批做完，你是实际运行 + 打开文件核对了真实内容，而不只看测试绿灯吗？
4. 这次的过程产物（决策、待办、变更）有没有同步进 `DECISIONS.md` / `TASKS.md` / `CHANGELOG.md`？
5. 你的 PR 描述里，附上了能让人复核的验证证据吗？

小练习：拿「我想要个能记录每天做了啥的工具」这句话，照阶段 1 当场补齐 7 要素；再故意让 AI 在 `done` 里漏掉写回文件，体会阶段 4 怎么靠核对文件抓出假绿。
