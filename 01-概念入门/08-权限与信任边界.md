# 权限与信任边界

## 本篇目标

读完这篇，你能：

- 说清楚 Skill 凭什么能执行命令、读写文件、联网——能力到底从哪来；
- 把「能力来源」和「信任授予」分成两件事来看；
- 指出安装一个第三方 Skill 前，最该检查的四类执行面（脚本、钩子、网络、凭据）；
- 解释为什么默认推荐「项目级试用」而不是「全局静默安装」。

## 核心概念：能力从哪来，信任给到谁

### 第一件事：能力不来自大模型

[工具关系那篇](./05-工具-Skill-MCP-Plugin-Workflow-关系.md) 讲过一个容易被忽略的事实：**大模型本身只会「想」和「说」**。给它一句话，它能接着写下去，但它天生不能联网、不能读你电脑里的文件、不能发消息。

那 Skill 凭什么能做这些？答案在 [Skill 是怎样工作的](./06-一个-Skill-是怎样工作的.md) 的「执行」那一步：Skill 里的 `scripts/` 不是文字，是**真正会被执行的代码**。Agent 决定「现在该调这个脚本」，脚本就在**你的电脑上**跑起来——读文件、跑命令、发网络请求，都发生在你的机器、用着你的权限、带着你的凭据。

> 一句话：大模型决定「调什么」，脚本负责「动手」。真正能碰到你电脑的，是脚本，不是大模型的「聪明」。

### 第二件事：安装 Skill ≈ 授权作者在你电脑上做事

把这个事实推到底：**安装一个带脚本的 Skill，约等于授权它的作者在你的电脑上跑代码**。能力越大，授权越大。这个授权有多大，取决于两件事——你把它装在哪、运行时它拿到了什么。

- **装在哪**：项目级安装只对当前目录生效；全局安装（命令里的 `-g`，global，对你所有项目生效）影响范围最大。
- **拿到什么**：脚本能不能联网、能不能读你的密钥、有没有偷偷加自动执行的钩子。

最危险的是 `-g -y` 这个组合：`-g` 把作用范围拉到全局，`-y`（yes，跳过安装过程中的所有确认提问）把每一步「要不要继续 / 覆盖」都自动回答「是」。叠加起来等于「我完全信任这个作者，请静默、全局地装好，中途别问我」——对没审过的第三方 Skill 默认这么干，等于把钥匙交给陌生人。`-g -y` 本身不是坏命令，你充分信任的官方 Skill 用它也合理；问题在于**不该对没审过的第三方 Skill 默认用它**。

读三个后面反复出现的词：

- **凭据（credentials）**：能换权限的东西——API Token、密码、SSH 私钥、`.env` 里的密钥。被脚本读到并外传，就等于交出钥匙。
- **项目级 vs 全局**：项目级只对当前目录生效，全局（`-g`）对你所有项目生效。审查阶段默认用项目级，把爆炸半径限制在一个目录里。
- **钩子（hooks）**：一种「在你每次工具调用前后自动执行命令」的机制，通常写在宿主程序（你用的那个 AI 客户端）的 `settings.json` 配置文件里。如果某个 Skill 的安装脚本偷偷加了钩子，它就能在你不知情时、每次你用工具时自动跑命令——这是最隐蔽也最该警惕的执行点。

> 审查第三方 Skill，本质是先回答一个问题：**我愿意让这个作者，在我的电脑上拥有多大的执行权？** 答案越小越好。

## 实例分析：装之前该检查的四类执行面

既然「能力 = 被授权执行的代码」，那装一个 Skill 之前，就该先看它的代码到底会动手做什么。把可能出事的地方归成四类，正好覆盖所有「能碰到你电脑」的入口：

| 执行面 | 它能干什么 | 风险在哪 | 重点查什么 |
|--------|-----------|----------|-----------|
| 脚本 | `scripts/` 里执行任意代码 | 能做任何代码能做的事 | 读 `SKILL.md` 正文，逐个打开 `scripts/`，重点盯 `install.sh` / `update.sh` 等安装脚本 |
| 钩子 | 每次工具调用前后自动跑命令 | 在你不知情时静默执行 | 查安装脚本有没有偷偷改 `settings.json` 加钩子 |
| 网络 | 联网请求 | 外传你的数据，或拉回恶意内容 | 找 `curl` / `wget` / `requests.post` / `fetch` 这类调用 |
| 凭据 | 读取密钥文件 | 泄露 = 交出钥匙 | 找有没有读 `~/.ssh`、`.env`、`~/.aws`、token 文件的代码 |

四类执行面，对应四类检查动作。看到任何一类，都停下来问一句：「这一步有必要吗？它访问的东西，和这个 Skill 声称要干的活，对得上吗？」

### 同一个需求，执行面天差地别

同样是「待办管理」这个需求，两种实现的执行面完全不同：

- **纯说明型 Skill**：只有一个 `SKILL.md`，告诉 AI「待办该怎么管理」，没有 `scripts/`。它本身不执行代码，执行面几乎为零——风险主要集中在它会不会误导你手动敲一条危险命令。
- **带脚本的 Skill**：`scripts/` 里有一个 `todo.py`，负责真正读写 `todos.json`。这个脚本会在你的电脑上跑，能碰你的文件系统——执行面明显大得多，装之前必须读懂它到底碰了什么。

规律很直接：**Skill 带 `scripts/` 越多、调的子进程越多，执行面越大，审查就越不能省**。

> 四类执行面是「看哪里」的框架。具体「怎么一步一步查、查完怎么试运行和退出」，看 [第三方 Skill 安全审查](../04-创建Skill/05-第三方-Skill-安全审查.md) 的 7 步清单——这篇只建立概念，不重复那套清单。

## 常见错误

### 错误 1：以为 Skill 只是一段提示词

很多人把 Skill 想成「一段给 AI 看的文字」。但只要它带 `scripts/`，那就是会在你电脑上跑的真代码。正确做法：先看它有没有 `scripts/`，有的话，把它当「要在我机器上执行的程序」对待。

### 错误 2：照搬 `-g -y` 全局静默安装

看到 README 这么写就照敲，把全局静默授权交给陌生人。正确做法：审查阶段默认项目级试用，作用范围限在一个目录，出问题删掉目录就干净。

### 错误 3：只看 README，不读 `SKILL.md` 正文和 `scripts/`

README 是广告，`SKILL.md` 正文和 `scripts/` 才是合同。正确做法：读 `SKILL.md` 正文看它指示 AI 偻什么，逐个打开 `scripts/` 看实际动手做什么。

### 错误 4：漏掉钩子（hooks）

忘了检查安装脚本有没有偷偷改 `settings.json` 加自动执行的钩子——这是最隐蔽的执行点。正确做法：装完检查 `settings.json` 有没有多出你不认识的钩子配置。

### 错误 5：把「上游公开」当成「安全」

公开仓库也可能没 LICENSE、脚本里也可能藏网络调用。正确做法：公开 ≠ 安全，也 ≠ 允许复用。许可证看 [什么是许可证？](./02-什么是-许可证.md)，凭据一旦被读怎么处理看 [环境变量与密钥安全](../02-工具指南/09-环境变量与密钥安全.md)。

## 自测题 / 验收

1. 用自己的话说：大模型本身能联网、能读你的文件吗？那 Skill 凭什么能做这些？（讲清「决定调什么」和「动手」是两件事。）
2. 四类执行面是哪四类？每一类各举一个「在代码里长什么样」的信号。
3. `-g` 和 `-y` 分别授权了什么？为什么不该对没审过的第三方 Skill 默认叠加使用？
4. 纯说明型 Skill 和带脚本的 Skill，执行面有什么差别？这会怎么影响你装之前的审查力度？
5. 钩子（hooks）为什么是「最隐蔽」的执行点？

第 1、2 题能用自己的话讲清，说明「能力来源」和「四类执行面」你已经吃透了。
