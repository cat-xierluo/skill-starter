# 什么是 GitHub？

## 本篇目标

读完这篇你能：

- 你能一句话说清 Git 和 GitHub 的区别，不再把两个词混着用。
- 你能说清 Repository、Commit、Branch、Pull Request、Issue、Fork 这几个核心概念分别指什么。
- 你能照着一条最小工作流把本地改动推到 GitHub（clone → commit → push → 开 PR）。
- 你能区分 Public 和 Private 仓库、HTTPS 和 SSH 两种连接方式各自的适用场景。
- 你能避开「上传 GitHub = 已上线」「Push = 协作完成」「删本地 = 从 GitHub 删干净」这几个新手误区。

## 前置知识

- 建议先读 [`01-什么是-Skill.md`](01-什么是-Skill.md)，了解 Skill 仓库大致长什么样；再读 [`02-什么是-许可证.md`](02-什么是-许可证.md)，因为仓库一旦放到 GitHub Public，许可证是否写清楚就直接关系到别人能不能复用。
- 本文是概念入门，不要求你已经会用 Git 命令，命令行操作留给下一篇工具指南。

## 核心概念

GitHub 不是单纯”放代码的网站”。

你可以把它理解成：

**代码仓库 + 协作平台 + 版本入口。**

## 先分清 Git 和 GitHub

很多新手一开始最容易混淆这两个词。

| 名称 | 是什么 | 主要作用 |
|------|--------|----------|
| Git | 本地版本控制工具 | 记录改动、提交历史、分支 |
| GitHub | 云端托管和协作平台 | 存仓库、协作、PR、Issue |

一句话：

- `Git` 负责“怎么记版本”
- `GitHub` 负责“把仓库放到网上并和别人协作”

## GitHub 能做什么

### 1. 托管仓库

你可以把本地 Git 仓库同步到 GitHub。

这样做的好处：

- 云端备份
- 换电脑不丢
- 可以和别人协作

### 2. 管理协作

GitHub 不只是上传代码，还可以：

- 开 Issue 跟踪问题
- 开 Pull Request 合并改动
- 做 Code Review
- 看历史提交

### 3. 展示项目

一个项目的说明、版本、讨论、文档，通常都围绕 GitHub 仓库展开。

### 4. 接入自动化

比如：

- 自动测试
- 自动发布
- 自动检查格式

这些能力很多都能围绕 GitHub 做。

## GitHub 里最重要的几个概念

### Repository

仓库，简称 `repo`。

一个项目通常对应一个仓库。

### Commit

提交。你可以把它理解成“这一次改动的存档点”。

### Branch

分支。你可以在不影响主线的情况下单独开发。

### Pull Request

简称 `PR`。

把“某个分支的改动”申请合并到另一个分支时，就会开一个 PR。

### Issue

用来记录：

- Bug
- 待办
- 讨论项
- 需求

### Fork

把别人的公开仓库复制到你自己的账号下，方便你研究或继续开发。

## 一个最小工作流

这是新手最常见、最实用的一条线：

1. 在 GitHub 创建仓库
2. 在本地 `git clone` 下来
3. 改文件
4. `git add` + `git commit`
5. `git push`
6. 到 GitHub 看改动
7. 如果是团队协作，就开 PR

## 公开仓库和私有仓库

### Public

公开仓库。任何人都能看。

适合：

- 开源项目
- 作品集
- 想展示给别人看的代码

### Private

私有仓库。只有你和你授权的人能看。

适合：

- 商业项目
- 内部工具
- 不想公开的实验项目

## HTTPS 和 SSH 是什么关系

这两个词会在 GitHub 使用里反复出现。

它们不是 GitHub 的功能，而是你连接 GitHub 仓库时的两种认证方式。

### HTTPS

常见 URL 长这样：

```bash
https://github.com/用户名/仓库名.git
```

适合：

- 临时机器
- 偶尔使用
- 通过 Token 认证

### SSH

常见 URL 长这样：

```bash
git@github.com:用户名/仓库名.git
```

适合：

- 自己长期使用的电脑
- 日常开发
- 更稳定的推拉代码体验

如果你是长期开发者，通常更推荐 SSH。

## 常见错误

下面这 4 条是新手最容易踩的坑，每条单独说清错在哪。

### 把 GitHub 当成 Git

GitHub 不等于 Git。没有 GitHub，你照样可以在本地用 Git 管理版本；GitHub 只是把仓库放到云上、并提供协作能力。把两者划等号，会让你误以为「没网就不能用版本控制」。

### 以为上传 GitHub 就等于发布上线

代码 push（推送，把本地提交同步到远端）到 GitHub，只是把代码托管上去，并不等于你的产品已经部署、用户已经能用。部署通常还需要 CI/CD 或额外的发布步骤。

### 以为 Push 就等于协作完成

push 完代码，团队协作并没有自动结束。多人协作通常还需要：开分支、提 Pull Request、做 Code Review（代码评审）、合并。push 只是把自己这边的改动送上去，不是协作的终点。

### 以为删本地文件就从 GitHub 删干净了

删掉本地文件、甚至重新 push，Git 历史里仍会保留那条提交记录，GitHub 上也能从历史里翻出来。想真正「抹掉」，需要改写历史，而且如果别人已经 fork（派生，把别人公开仓库复制到自己账号），别人的副本也删不掉。

## 初学者应该先会哪几件事

如果你刚开始学 GitHub，先掌握这 5 件事就够了：

1. 注册账号
2. 创建仓库
3. 克隆仓库
4. 提交并推送
5. 开一个 PR

这比先学一堆高级功能有用得多。

## 自测题

以下 4 题用来检验你是否真的理解了上面的概念。答案要点附在每题后面。

1. **辨析题**：朋友说「我没法用 Git，因为我的电脑连不上 GitHub。」这句话哪里错了？
   - 答案要点：Git 是本地版本控制工具，不依赖 GitHub 也能用；GitHub 只是云端托管和协作平台。连不上 GitHub 不影响本地 `commit`、`branch` 等操作。

2. **概念题**：Branch、Commit、Pull Request 三者的先后关系是怎样的？
   - 答案要点：先在新 Branch 上做若干 Commit（改动存档），改动攒够后再开 Pull Request，把该 Branch 的改动申请合并到目标分支（如 main）。

3. **场景题**：你想做一个对外展示的作品集 Skill，又想保护隐私不泄露内部实现。该选 Public 还是 Private？为什么？
   - 答案要点：分开处理。要展示的部分放 Public 仓库；涉及隐私/内部实现的放 Private 仓库，只授权协作者可见。一个项目可以拆成多个仓库。

4. **判断题**：你把一个文件从本地删了，又 `git push`，所以它从 GitHub 上彻底消失了。对吗？
   - 答案要点：不对。当前版本里没了，但 Git 历史仍保留那条提交，GitHub 上也能从历史里找到。要真正抹掉需改写历史，且已 fork 的副本不受影响。

## 一句话总结

GitHub 是把 Git 的本地版本管理，扩展成云端托管和多人协作的平台。
