# 工具、Skill、MCP、Plugin、Workflow 到底什么关系？

## 本篇目标

读完这篇，你能回答：

- 大模型、聊天助手、Agent、工具、MCP、Skill、Plugin、Workflow 分别是什么；
- 它们各自在「同一件事」里负责哪一段；
- 为什么「给 AI 加能力」这件事，会被拆成这么多名词。

很多新手第一次接触这套体系时，会被这几个词搞得晕头转向：有人说「写个 Skill」，有人说「接个 MCP」，有人说「装个 Plugin」，还有人说「配个 Workflow」。它们听起来都在「给 AI 加能力」，但又好像不是一回事。

这篇的目的，就是把它们摆到同一张桌上，看清楚谁是谁、谁干什么。

## 前置知识

读这篇前，建议先看：

- [什么是 Skill？](./01-什么是-Skill.md)：先建立「Skill 是给 AI 装的 App」这个类比。

如果你已经能大致说出「Skill 是 AI 的能力扩展」，那这篇就可以开始。

## 核心概念：先分清楚「层」

最关键的思路是：**这些名词不在同一层**。

把它们按「离用户远近」和「职责」分成 6 层，立刻就清楚了：

| 层 | 名词 | 一句话定位 | 生活类比 |
|----|------|------------|----------|
| 大脑层 | 大模型（LLM） | 只会「想」和「说」的脑子 | 一个聪明但没有手脚的人 |
| 入口层 | 聊天助手 | 你和大脑对话的窗口 | 柜台 / 前台 |
| 行动层 | Agent | 会自己决策、自己动手的脑子 | 这个聪明人学会了打电话、查资料 |
| 能力层 | 工具 / Skill | 具体能做的一件事 / 一组事 | 一项技能 / 一个工具箱 |
| 协议层 | MCP | 让工具能被统一插拔的标准 | 万能插座 / USB |
| 编排层 | Workflow / Plugin | 把多步串起来 / 宿主程序的扩展模块 | 流水线 / 给软件装的扩展包 |

下面一层一层讲。

### 1. 大模型（LLM）：大脑

大模型本身只是一颗「会算语言」的大脑。给它一句话，它能接着往下写。但它天生没有手：不能联网、不能读你电脑里的文件、不能发消息。

> 大模型 = 想和说的能力，仅此而已。

### 2. 聊天助手（chat assistant）：入口

你平时打字对话的那个界面，就是聊天助手。它的工作是：把你输入的话，喂给大模型，再把大模型的回答显示给你。

它本身不「变聪明」，它只是个「窗口」。你换一个更强的模型，窗口还是那个窗口，但回答质量会变。

### 3. Agent：会动手的脑子

Agent 是「大模型 + 自主决策 + 能调用工具」。

关键区别在「自主」：你给它一个目标，它会自己决定先做什么、再做什么，必要时自己去调工具。普通聊天是「你问一句它答一句」；Agent 是「你说目标，它自己拆步骤干完」。

### 4. 工具（tool）：一个具体的动作

工具是能被调用的、最小的「动手单元」。它有明确的输入和输出：

- 输入：城市名
- 动作：查天气
- 输出：天气文字

工具本身不会思考，它只负责「被叫到时执行，并返回结果」。大模型负责决定「什么时候该叫这个工具」。

### 5. Skill：一整套打包好的能力

如果工具是「一把螺丝刀」，那 Skill 就是「一个装着说明书、螺丝刀、备用螺丝、操作手册的**工具箱**」。

Skill 把三样东西打包进一个文件夹：

- **知识**：怎么做这件事（写在 SKILL.md 里）；
- **步骤 / 脚本**：具体怎么动手（scripts/）；
- **参考资料和模板**：辅助材料（references/、assets/）。

而且 Skill 是「按需加载」的：平时不占大脑的注意力，只有用到时才被读进来。这是它和「一次性塞一大段提示词」最大的区别。

> 想深入了解 Skill 内部结构，看 [一个 Skill 是怎样工作的](./06-一个-Skill-是怎样工作的.md)。

### 6. MCP：让工具能「即插即用」的标准

MCP（Model Context Protocol，模型上下文协议）解决的是另一个问题：**工具太多、接法各不相同**。

以前每接一个工具，都得专门写一套对接代码。MCP 的作用是定一个「插座标准」：只要工具按这个标准做成「插头」，任何支持 MCP 的 AI 都能直接用，不用每次重新接线。

- 工具 = 一项具体能力；
- MCP = 让能力能被统一发现和插拔的「协议 / 插座」。

可以把 MCP 理解成 USB：你不需要为每个外设单独焊电路，插上就能用。

### 7. Plugin：宿主程序的扩展模块

Plugin（插件）是个更「生态向」的词。它指的是：**给一个宿主程序装的功能扩展包**。

比如浏览器插件扩展浏览器，编辑器插件扩展编辑器。在 AI 体系里，「Plugin」常常是「把能力打包、安装、分发给某个宿主」的那一层说法。它和 Skill 在很多场景下指的其实是同一类东西，只是侧重点不同：

- Skill 更强调「**这份能力本身**」（知识 + 步骤 + 脚本）；
- Plugin 更强调「**怎么把它装进某个软件并分发**」。

> 举个具体对照：同一份「代码审查」能力，在 Claude Code 里以 Skill 形式按需加载，在某个 IDE 的插件市场里以 Plugin 形式安装——东西可以是同一个，叫法随它挂在哪个宿主、怎么分发而定。
>
> 在这个仓库里，我们统一用「Skill」来描述能力本身，因为它更贴切「按需加载的能力包」这层意思。

### 8. Workflow：把多步串起来

Workflow（工作流）是「**编排**」：把多个步骤、多个工具，按顺序和条件串成一条流程。

一个工具只会干一件事；一个 Skill 负责一类事；而 Workflow 负责「先做 A，看结果，再决定做 B 还是 C」这种跨多个能力的串联。

### 几个关键关系，一口气记住

- 大模型 vs Agent：会不会「自主动手」。
- 工具 vs Skill：一把刀 vs 一整个工具箱。
- Skill vs Plugin：能力本身 vs 怎么装进软件分发。
- MCP：让工具能即插即用的「标准」（它和上面三条不一样，不是两个东西的对比，而是单独一类角色）。
- Workflow：把多步串成流程的「编排」（同样单独一类）。

## 动手步骤：同一个需求，各层谁干什么

光讲概念容易晕。我们拿一个真实需求，把每一层的「职责」摊开。

### 需求一：「帮我查下周苏州的天气，整理成一段话，再存到我的待办里」

| 层 | 这一层负责什么 | 在本需求里具体做 |
|----|----------------|------------------|
| 大模型 | 想、说、组织语言 | 把天气数据整理成一段通顺的话 |
| 聊天助手 | 接收你的话、显示结果 | 收到「查天气并存待办」这句话 |
| Agent | 拆步骤、自己决定先后 | 自己决定：先查天气 → 再整理 → 再存待办 |
| 工具 | 单个动作 | 「查天气」是一个工具，「存待办」是另一个工具 |
| Skill | 打包好的能力 | 一个「天气简报」Skill，含查询步骤和输出格式 |
| MCP | 让工具即插即用 | 天气工具按 MCP 标准做，Agent 能直接调用 |
| Workflow | 串联多步 | 查天气 → 整理 → 存待办 这条流水线 |
| Plugin | 打包安装分发 | 把这套能力装进你的 AI 客户端 |

注意：**它们不是互相替代，而是各管一段**。大模型管「聪明」，Agent 管「自己干」，工具管「具体动作」，Skill 管「打包能力」，MCP 管「即插即用」，Workflow 管「串流程」。

### 需求二：「审查我这段代码，找出问题，然后帮我提交一个 PR」

| 层 | 职责 | 具体做 |
|----|------|--------|
| 大模型 | 读懂代码、推理问题 | 分析这段代码哪里可能出错 |
| Agent | 自主拆任务 | 先审查 → 列问题 → 改代码 → 提交 |
| 工具 | 单个动作 | 读文件、运行测试、创建提交、开 PR，各是一个工具 |
| Skill | 打包能力 | 一个「代码审查」Skill，含审查清单和提交规范 |
| Workflow | 串联 | 审查 → 修改 → 测试 → 提交 这条线 |

从这两个例子你能看出一个规律：**需求越复杂、越要跨多个能力，就越需要 Agent + Workflow 来串联；越是「某个领域的固定套路」，越适合沉淀成一个 Skill。**

## 常见错误

### 把 Skill 和工具混为一谈

工具是「一个动作」，Skill 是「一整套打包好的能力（知识 + 步骤 + 脚本）」。一把螺丝刀 ≠ 一个工具箱。

### 以为「装了 MCP 就有了能力」

MCP 只是「插座标准」，它本身不提供能力。能力来自按 MCP 标准做出来的工具。插座不会自己发电。

### 以为大模型自己就能联网、读文件

不能。大模型天生只有「想和说」。联网、读文件、发消息，全靠工具 / Agent / Skill 这些「手脚」。把大模型当成无所不能，是新手最容易踩的坑。

### 把 Plugin 和 Skill 当成完全不同的东西

很多时候它们指的是同一类东西，只是「Plugin」偏「安装分发」，「Skill」偏「能力本身」。在本仓库统一用 Skill。

### 什么都想做成 Workflow

简单的一两步，直接用工具或 Skill 就够了。只有「多步骤、有条件分支、跨多个能力」时，才值得上 Workflow。别为了用而用。
