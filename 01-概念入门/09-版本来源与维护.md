# 版本来源与维护

## 本篇目标

读完这篇，你能：

- 分清一个 Skill 的来源类型（原创、上游同步、第三方收录），并说出每种该用什么方式维护；
- 说清楚上游、fork、同步这三件事是什么关系，本仓库怎么同步；

## 核心概念：先搞清「它从哪来」，才知道「该怎么养」

维护一个 Skill，第一件事不是写代码，而是搞清楚**它的内容从哪来**。来源不同，维护方式天差地别。本仓库用 [`docs/SOURCE-INDEX.md`](../docs/SOURCE-INDEX.md) 这张表记录 `skills/` 下每个 Skill 的来源——它是仓库级的「来源事实层」，所有具体版本号、上游地址、同步状态都以它为准。

来源一共分三种：

| 来源类型 | 是什么 | 本仓库的例子 | 怎么维护 |
|----------|--------|-------------|----------|
| 原创 | 本仓库自己写的 | `skill-template` | 自由修改，无人可同步 |
| 上游同步 | 从某个上游仓库定期拉更新 | `git-batch-commit`、`skill-manager` | 跟着上游更新走，按规则同步 |
| 第三方收录 | 收录官方或第三方，按需本地化 | `find-skills`、`skill-creator` | 上游有重要更新时人工对比再合并 |

三种来源，对应三种维护姿态。下面把每种的几个关键词讲清。

### 上游、fork、同步：三个词的关系

- **上游（upstream）**：你同步内容的那个原始仓库。它是「正版」，你是「跟着拉的副本」。
- **fork**：把别人的公开仓库复制一份到自己账号下（见 [什么是 GitHub？](./03-什么是-GitHub.md)）。fork 之后你就有了一份属于自己的副本，可以改。
- **同步（sync）**：定期把上游的更新拉到本地，让自己的副本别落后太多。

本仓库的做法（见 [AGENTS.md](../AGENTS.md) 的「上游同步文件」一节）：把上游 `legal-skills` 配成一个**只读的 remote（远程仓库引用，只拉不推）**，需要同步时拉它的更新，但绝不把自己的改动推回去。同步前先比对差异、自动备份到 `.starter-backups/`（这个目录被 `.gitignore` 排除，不进版本库），确认无冲突再覆盖。注意：自动备份是仓库里 `/sync-upstream` 命令封装好的；如果你直接用下面这条裸 git 命令同步，它**不会**自动备份，覆盖前要自己先 `cp` 一份留底。

同步命令长这样（以同步两个 legal-skills 来源的 Skill 为例，完整流程见 [AGENTS.md](../AGENTS.md) 和 `/sync-upstream` 命令）：

```bash
# 1. 先拉取上游最新
git fetch legal-skills main

# 2. 同步前对比差异（空输出 = 已是最新）
git diff legal-skills/main -- skills/<skill-名>

# 3. 确认无冲突，把上游内容覆盖到本地
git checkout legal-skills/main -- skills/git-batch-commit skills/skill-manager
```

### 语义化版本：三段号各代表什么

Skill 的版本通常写成 `1.4.1` 这种三段号，规则叫**语义化版本（Semantic Versioning，常缩写 SemVer）**。三段从左到右：

| 段 | 名字 | 什么时候加 | 含义 |
|----|------|-----------|------|
| 第一段 | MAJOR（主版本） | 做了不兼容的改动 | 老用法可能失效，升级要小心 |
| 第二段 | MINOR（次版本） | 加了向后兼容的新功能 | 老用法不受影响，有新东西 |
| 第三段 | PATCH（修订号） | 做了向后兼容的修复 | 只是修 bug，最安全 |

看到版本号从 `1.4.1` 升到 `1.5.0`，你就知道：加了新功能，但老用法还能用；如果升到 `2.0.0`，就要警惕老用法可能不兼容了。

本仓库 [AGENTS.md](../AGENTS.md) 还定了一条：**即使还没正式发布，CHANGELOG（变更日志，记录对外可见变更的文件）也要按 `0.x.0` 这种版本持续迭代**。比如 `0.15.0`、`0.16.0`，记录每次可见变更，别等「正式发布」才开始记。

### 变更记录和弃用

- **变更记录**：每次有用户可见的改动，就在 CHANGELOG 里记一条，带上版本号。它是给别人（和给未来的你）看的「这版改了啥」。
- **弃用（deprecate）**：一个 Skill 不再维护，不能直接删掉走人。正确做法分三步：在 `SKILL.md` 和 CHANGELOG 里**标记弃用**、**给出替代方案**（用哪个 Skill 顶上）、**留一段迁移期**（让别人有时间换），过了迁移期再考虑移除。

## 实例分析：一张表回答所有维护问题

打开 [`docs/SOURCE-INDEX.md`](../docs/SOURCE-INDEX.md)，每个 Skill 的来源、上游地址、同步到的 commit SHA（每次提交的唯一哈希标识）、许可证、本地补丁、最近核对日期，都在一张表里。下面用两个真实例子说明「来源类型决定维护方式」。

**例 1 · 上游同步型：`git-batch-commit`。** 它的来源是 `cat-xierluo/legal-skills`，许可证 MIT，本仓库已把 legal-skills 配成只读 remote。维护方式很清晰：**定期 `git fetch` 看上游有没有更新，有就按上面的同步命令拉过来**。关键纪律是「只拉不推」——你可以在本地做小修补，但不要推回上游。同步时如果上游有你想要的更新，**覆盖前先把本地修补另存一份**（`git checkout upstream -- <路径>` 是覆盖式，会吞掉本地改动）；如果本地修补还没合并进上游、又不想丢，就以本地为准、暂不同步这一版。

**例 2 · 第三方收录型：`find-skills`。** 它收录自 `vercel-labs/skills`，但本仓库**没有**把它配成可自动同步的 remote，许可证也还**待确认**（上游仓库根目前没有显式 LICENSE）。维护方式就不一样了：**上游有重要更新时，要人工 clone 上游、对比差异、确认许可证状态后，再决定要不要合并**——不能像 `git-batch-commit` 那样一条命令同步。许可证一天没确认，就一天不能把它打包进自己仓库对外分发（详见 [什么是许可证？](./02-什么是-许可证.md)）。相比之下，同样是第三方收录的 `skill-creator` 许可证已确认为 Apache-2.0，可以更放心地用——但合并更新时仍要人工对比。

两个例子一对比，规律就出来了：**上游同步型可以半自动化地跟，第三方收录型必须人工把关，原创型只对自己负责**。判断用哪种方式，先看 [`docs/SOURCE-INDEX.md`](../docs/SOURCE-INDEX.md) 里它的「来源类型」那一列。

## 常见错误

### 分不清来源，对原创 Skill 也等「上游更新」

把原创的 `skill-template` 当成「等别人更新」的 Skill，结果一直没动。正确做法：先查 SOURCE-INDEX 的来源类型，原创的就自己改，没有上游可等。

### 同步时把本地改动推回上游

把同步型 remote 当成双向的，把自己的改动 push 回 `legal-skills`。正确做法：上游同步 remote 只读，只拉不推。本地改动留在自己仓库。

### 不看版本号段位就升级

看到新版本就升，结果从 `1.x` 升到 `2.x`（MAJOR 变了），老用法失效，全线报错。正确做法：先看版本号哪一段变了，MAJOR 变动要特别小心兼容性。

### CHANGELOG 等到「正式发布」才写

觉得「还没发布，不用记变更」，结果几个月后忘了自己改过什么。正确做法：每次有可见变更就记一条，按 `0.x.0` 持续迭代（见 [AGENTS.md](../AGENTS.md) 的 CHANGELOG 约定）。

### 不维护了直接删

一个 Skill 不再用了，直接删掉目录。别人还引用着，突然就 404。正确做法：标记弃用、给替代方案、留迁移期，再考虑移除。
