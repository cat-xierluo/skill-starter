# 复用、改造，还是从零新建？

## 本篇目标

读完这篇，你能：

- 拿到一个需求时，说出该走「直接复用 / 定向改造 / 从零新建」哪一条；
- 用四个因素——匹配度、维护成本、安全风险、许可证——逐项给出判断；
- 照着一张决策流程图，把一个模糊需求落到一个明确结局；
- 分清三种结局各自的典型正例，以及最容易踩的反例。

## 前置知识

- [什么是 Skill？](./01-什么是-Skill.md)：知道 Skill 是给 AI 装的「App」。
- [什么是许可证？](./02-什么是-许可证.md)：决策四因素里有一项就是许可证，先有概念。
- [一个 Skill 是怎样工作的？](./06-一个-Skill-是怎样工作的.md)：知道 Skill 由 `SKILL.md`、`scripts/`、`references/`、`assets/` 组成，其中 `scripts/` 是会被真正执行的代码——这一点直接关系到「安全风险」这一项。

## 核心概念：先定结局，再判因素

很多人拿到需求，第一反应是「我该怎么写」。但本仓库 [AGENTS.md](../AGENTS.md) 定的默认顺序是反过来的：**先判断这个需求属于哪一类，再决定复用、改造还是新建**。

一共有三种结局：

| 结局 | 一句话 | 什么时候选 |
|------|--------|-----------|
| 直接复用 | 拿现成的用，一个字不改 | 有现成 Skill，且四个因素都过关 |
| 定向改造 | 在现成 Skill 上改一部分 | 有现成 Skill，但局部不匹配 |
| 从零新建 | 基于 `skill-template` 自己搭 | 没有现成的，或改造比新建还累 |

光知道结局不够，关键是怎么判。判的依据是四个因素：

| 因素 | 在问什么 | 具体看什么 |
|------|----------|-----------|
| 匹配度 | 现成 Skill 能干这个活吗 | 功能范围、输入输出格式、适用平台 |
| 维护成本 | 改它、养它要花多少力气 | 改动量、依赖复杂度、上游是否还在更新 |
| 安全风险 | 用它会带来多大隐患 | `scripts/` 干了什么、会不会联网、碰不碰凭据 |
| 许可证 | 我有没有权这么用 | 能否商用 / 再分发、是否要求衍生版同协议 |

四个因素不是平均的，有明确优先级：**匹配度决定走哪条路，安全风险和许可证决定能不能用，维护成本决定该改还是该新建**。

## 实例分析：一张决策流程图

下面这张文字版流程图把四个因素串起来。从「我有一个需求」开始，顺着箭头走到唯一一个结局。为了具体，我们用这个贯穿场景：**你想给团队做一个待办管理能力**（核心就是 `todo.py` 那套：`add` 加一条、`list` 列出来、`done` 标记完成）。

```text
我有一个需求（团队待办管理）
   │
   ▼
【匹配度·第一步】先搜：有没有现成 Skill？
   用 find-skills / Skills CLI / GitHub 搜一圈
   │
   ├─ 没有现成的 ───────────────────────▶ 从零新建
   │
   └─ 有现成的 ──▶【匹配度·第二步】它能干这个活吗？
                      │
                      ├─ 功能基本对得上 ──▶【安全·许可证】能合法、安全地用吗？
                      │                       │
                      │                       ├─ 都过关 ──▶ 直接复用
                      │                       │
                      │                       └─ 有隐患 ──▶ 定向改造（去掉/替换风险部分）
                      │
                      └─ 只对上一部分 ──▶【维护成本】改它的量，比新建少吗？
                                            │
                                            ├─ 少 ──▶ 定向改造
                                            │
                                            └─ 不少 ──▶ 从零新建
```

四个因素在流程图里各出现一次：匹配度（第一、二步）、安全风险、许可证、维护成本。任一分支的终点，都落在三种结局之一。

### 三个正例：每种结局各走一遍

**正例 1 · 直接复用。** 你搜到一个现成的待办 Skill，能 `add/list/done`、存 `todos.json`、无外部依赖。来源是可信组织、最近三个月还在更新、`SKILL.md` 里写明 `license: MIT`。四个因素全过关——**结论：项目级试用直接用，不写一行代码**。具体怎么审这个 Skill，看 [第三方 Skill 安全审查](../04-创建Skill/05-第三方-Skill-安全审查.md)。

**正例 2 · 定向改造。** 现成的待办 Skill 啥都好，唯一不对的是它把待办存进本地 `todos.json`，而你要存进团队的飞书表格。整个 Skill 只有「存储」这一个环节要换，其余照用——**结论：fork（把仓库复制一份到自己账号下）一份，只改存储那一步**。改之前先确认上游许可证允许派生改造（见 [什么是许可证？](./02-什么是-许可证.md) 的「派生版本」一节）。

**正例 3 · 从零新建。** 你要的不是普通待办，而是「待办 + 按截止时间自动排期 + 和公司内部工单系统联动」。搜遍生态没有接近的，就算硬改一个待办 Skill，也要动掉八成以上的代码——**结论：基于 [`skills/skill-template`](../04-创建Skill/03-基于模板创建.md) 从零搭一个**。

### 两个反例：最容易踩的决策错误

**反例 1 · 没搜就新建。**「这个我两小时就能写出来。」结果写到一半发现生态里早有一个 MIT 许可、star 很高的现成 Skill。违反 [AGENTS.md](../AGENTS.md) 的「先搜索，后创造」。先花十分钟搜，是这条决策链的第一步，跳过它后面全是白费。

**反例 2 · 匹配度只有两成却硬改造。** 看到一个 Skill「沾点边」，就一头扎进去改。改到第三天发现改掉的代码比保留的还多，引入的 bug 也比新写的还多。这就是流程图里【维护成本】那个判断点存在的意义：**改的量不比新建少，就该果断走从零新建**，别被已经投入的时间拖住（沉没成本不该影响这个判断）。

## 常见错误

### 跳过搜索直接动手

把「先搜索后创造」当成口号。正确做法：每次有需求，先 `npx skills find <关键词>` 或用项目内置 `find-skills` 搜一圈，确认没有现成的，再谈新建。搜索方法见 [02 搜索现成方案](../04-创建Skill/02-搜索现成方案.md)。

### 把「能跑」当成「匹配」

现成 Skill 能跑，但输入输出格式、适用平台和你都对不上，硬塞进流程。正确做法：匹配度看功能范围、输入输出、平台三项，任何一项差太远，就走定向改造或新建。

### 低估维护成本

只算「改起来快」，不算「以后上游一更新，我这套改法要不要重做」。正确做法：改造前问一句——上游还活着吗？我的改动和上游冲突时怎么办？冲突太频繁，不如新建。

### 只看功能，不看安全

现成 Skill 功能完美，但 `scripts/` 里藏着读 `~/.ssh`、联网外传的代码，直接全局装。正确做法：装之前按 [第三方 Skill 安全审查](../04-创建Skill/05-第三方-Skill-安全审查.md) 过一遍脚本、网络、凭据。安全是四个因素里能造成实际损失的那一个。

### 许可证不清就再分发

自己试用和打包给别人用是两回事。未确认许可证的 Skill，可以自己试，但别收进自己仓库对外分发。正确做法：分发前先确认上游许可证，迁移类 Skill 保持上游许可证不变（见 [AGENTS.md](../AGENTS.md) 的「许可证管理规范」）。

## 自测题 / 验收

1. 三种结局分别是什么？各举一个「该选它」的场景。
2. 决策依据的四个因素是哪四个？哪一个决定走哪条路，哪一个决定改还是新建？
3. 拿你自己最近的一个需求，照着流程图走一遍：先搜 → 判匹配度 → 判安全与许可证 → 判维护成本，说出落在哪个结局。
4. 一个现成 Skill 功能只匹配 20%，但你已经改了两天。按流程图，现在该怎么办？为什么「沉没成本」不该影响这个判断？

第 3 题能用自己的需求走通，说明这张决策图你已经能用。

## 下一篇

这篇讲的是「该复用、改造还是新建」的判断。一旦你选中了某个现成 Skill 要用，下一个绕不开的问题是：**它凭什么能在我电脑上跑命令、读文件、联网？我该信它到什么程度？** 这就是 [权限与信任边界](./08-权限与信任边界.md) 要讲的。

---

**一句话理解**：遇到需求先搜，用匹配度、安全风险、许可证、维护成本这四个因素逐项判断，落到「直接复用、定向改造、从零新建」三个结局之一——能复用就不改造，能改造就不新建，但安全或许可证不过关的，宁可不用。
