# 05 第三方 Skill 安全审查

在 [02 搜索现成方案](./02-搜索现成方案.md) 里我们说「动手前先搜一圈」。找到现成 Skill 之后，还有一步常被跳过：**安装之前，先把它当陌生人审一遍**。这篇就讲这一步。

> 仓库里第三方 Skill 的来源事实（上游 URL、许可证、最近核对日期）以 [`docs/SOURCE-INDEX.md`](../docs/SOURCE-INDEX.md) 为准，本文引用的事实都来自该索引。

## 本篇目标

读完这篇，你应该能：

- 说清「为什么不能直接 `-g -y` 全局静默安装第三方 Skill」；
- 按一份清单审查任意第三方 Skill：来源、源码、脚本、自动执行点、网络调用、凭据访问、许可证、更新活跃度；
- 区分「项目级试用」和「全局安装」，并解释为什么默认推荐前者；

命令以 macOS / Linux 为主，Windows 思路一致、命令名可能不同（见 [开发环境与依赖入门](../02-工具指南/08-开发环境与依赖入门.md)）。版本与平台信息最近核对：2026-07。

## 核心概念：为什么第三方 Skill 需要审查

**Skill 不是一段文字，是一份执行授权。** `scripts/` 是会被真正执行的代码，能读文件、跑命令、联网——**安装一个 Skill，约等于授权它的作者在你的电脑上做事**。授权有多大，取决于你把它装在哪、给了什么权限。

`-g -y` 把这份授权拉到最大：

```bash
npx skills add <owner/repo>@<skill> -g -y
```

`-g`（global，全局 / 用户级）装一次你**所有项目**都能用，影响范围最大；`-y`（yes，跳过确认）把安装中所有「要不要继续 / 覆盖」的提问**全部自动回答是**。两者叠加 = 「我信任这个陌生人，请静默、全局地装好，中途别问我」。它被投毒或安装脚本顺手改了你的配置，你毫无察觉。`-g -y` 不一定有害——你充分信任的官方 Skill 用它也合理；问题在于**不该对没审过的第三方 Skill 默认用它**。

读后面要反复出现的三个词：**凭据（credentials）**指能换权限的东西（API Token、密码、SSH 私钥、`.env` 里的密钥），被读到并外传 = 交出钥匙；**项目级 vs 全局**——项目级只对当前目录生效，全局（`-g`）对你所有项目生效，审查阶段默认用项目级把爆炸半径限制在一个目录；**钩子（hooks）**是一种「在你每次工具调用前后自动执行命令」的机制（通常写在 `settings.json` 里），如果某 Skill 的安装脚本偷偷加了钩子，它就能在你**不知情**时、每次你用工具时自动跑命令——这是最隐蔽也最该警惕的执行点。

> 审查第三方 Skill，本质是先回答：**我愿意让这个作者，在我的电脑上拥有多大的执行权？** 答案越小越好，所以默认装到项目里、限定目录、想好怎么撤。

## 动手步骤：审查一个第三方 Skill 的 7 步清单

下面 7 步可以直接照着做，每一步都是**真有动作**的。

**第 1 步：看来源与清单。** 打开仓库页面看三件事：作者是谁（官方组织如 `anthropics`、`vercel-labs` 通常比无名账号可信）、多少人用且最近是否更新（stars、最近 commit、issue 有没有回复）、出现在哪些清单里（只在陌生 gist，还是被官方文档或可信索引收录）。仓库内每个 Skill 的来源事实见 [`docs/SOURCE-INDEX.md`](../docs/SOURCE-INDEX.md)。

**第 2 步：读完整源码，不只看 README。** README 是广告，`SKILL.md` 和 `scripts/` 才是合同。读 `SKILL.md` 正文（不只看 frontmatter 的 description），看它指示 AI 去做什么、会不会让你跑命令；逐个打开 `scripts/` 下的脚本；**重点看 `install.sh` / `update.sh` 等安装脚本**——它决定「装这个 Skill 时到底对我的系统动了什么手脚」。

**第 3 步：找三类高危点。** 读源码时盯住三类最容易出事的地方（正好三类）：

| 类别 | 在代码里长什么样 | 为什么危险 |
|------|------------------|------------|
| 网络调用 | `curl` / `wget` / `requests.post` / `fetch` / `npx skills add` | 可能外传数据，或拉回恶意内容 |
| 凭据 / 文件访问 | 读 `~/.ssh`、`.env`、`~/.aws`、token 文件、整个家目录 | 泄露密钥 = 交出钥匙 |
| 自动执行 | 改 `settings.json` 加 hook、开机自启、`PreToolUse` 钩子 | 在你不知情时静默跑命令 |

看到这三类就停下来问：「这一步有必要吗？它访问的东西，和这个 Skill 声称要干的活，对得上吗？」

**第 4 步：查许可证。** 「公开」不等于「你能随便用」。按 [什么是许可证？](../01-概念入门/02-什么是-许可证.md)：看仓库根有没有 `LICENSE` / `LICENSE.txt`、看 frontmatter 有没有 `license` 字段；**两个都没有 = 未声明**，按规则**不应默认视为允许复用或再分发**。许可证不明的 Skill 可以自己试用，但别打包进自己的仓库再分发（方案见 [`docs/LICENSE-PLAN.md`](../docs/LICENSE-PLAN.md)）。

**第 5 步：评估更新活跃度。** 半年没动、issue 堆成山的 Skill，即使现在安全也是定时炸弹。看最近 commit 时间（3 个月内为佳）、有没有未处理的安全 issue、作者还在不在维护。不活跃 = 出问题没人修。

**第 6 步：默认项目级试用。** 审查通过 ≠ 立刻全局装。先**项目级试用**：把它放到某一个具体项目的 skills 目录里（或用不带 `-g` 的方式装），作用范围只限这一个目录。万一行为异常，污染的只是这一个项目，删掉目录就干净了。

**第 7 步：想好退出方案。** 装之前先想好「怎么撤」，记下三样：**装在哪**（放进哪个目录、改了哪个配置）、**怎么卸**（有没有 `uninstall`，没有的话删目录够不够、要不要手动清 `settings.json` 里的钩子）、**怎么验证干净**（卸完跑一下 `bash scripts/check.sh` 确认无残留）。没有退出方案 = 装得上、卸不净。

## 实例分析：审查仓库里的两个真实 Skill

拿本仓库**真实收录**的两个第三方 Skill 走一遍清单。事实记录在 [`docs/SOURCE-INDEX.md`](../docs/SOURCE-INDEX.md)，路径是 `skills/find-skills/SKILL.md` 和 `skills/skill-creator/SKILL.md`。

### 样本一：`find-skills`（纯说明型 Skill）

来自 `vercel-labs/skills`（`npx skills` CLI 与 skills.sh 背后的生态），帮你发现和安装其它 Skill。按清单走：

- **来源 / 活跃度**：vercel-labs 维护的活跃生态，可信度较高。
- **源码**：整个 Skill**只有一个 `SKILL.md`**，无 `scripts/`、无 `assets/`、无安装脚本，审查很快。
- **高危点**：它指示运行 `npx skills find / add / check / update`，都联网（npm + skills.sh），属正常但要意识到「用它就会联网」；凭据 / 文件、自动执行均无。
- **许可证**：这里有**真问题**——`docs/SOURCE-INDEX.md` 记录上游仓库根**没有显式 LICENSE**，GitHub API 返回 `license=null`，社区已开 [issue #946](https://github.com/vercel-labs/skills/issues/946) 索要，状态**「待确认」**。按第 4 步，未确认就**不应再分发**，自己试用可以。

还藏着一个与本篇直接相关的点：`find-skills/SKILL.md` 在「Step 4」里直接示范 `npx skills add ... -g -y`——就是核心概念里那个「全局 + 跳过确认」的高风险组合。这是反面教材：**来源可信的 Skill，也可能在文档里示范不安全的安装方式**，不能因作者可信就放过正文每一条命令。

**结论**：可以用，但 (1) 不照搬 `-g -y`，改项目级试用；(2) 许可证待确认，先用着、别再分发。

### 样本二：`skill-creator`（带脚本的 Skill）

来自 `anthropics/skills`（Anthropic 官方的 meta-skill，用于创建和迭代 Skill）。

- **来源 / 活跃度**：Anthropic 官方维护，可信度高。
- **源码**：结构复杂——`SKILL.md` + `scripts/`（多个 Python 脚本）+ `assets/` + `references/` + `agents/` + `LICENSE.txt`，**审查面更大**，必须逐个看 `scripts/`。
- **高危点**：脚本会用 `python -m scripts.run_loop` 调 `claude -p`（拉起一个 Claude 子进程）、`webbrowser.open()` 起本地服务、spawn 子代理；会读写 workspace 目录、读 `evals/evals.json`、调 `claude` CLI（会带着你的会话上下文）。属「能跑代码、能动文件」的 Skill，权限明显高于纯说明型。未见改 `settings.json` 加 hook。
- **许可证**：目录有 `LICENSE.txt`，是 **Apache-2.0**。注意：frontmatter **没写** `license` 字段，以目录 `LICENSE.txt` 为准；Apache-2.0 带专利条款和 **NOTICE 文件义务**，再分发必须保留 `LICENSE.txt` 和（若有）`NOTICE`，不能用别的许可证覆盖（见 [`docs/LICENSE-PLAN.md`](../docs/LICENSE-PLAN.md)）。

**结论**：来源可信、许可证明确，可以放心用。但因为带脚本、执行面大，第一次用前**先读懂 `scripts/` 再跑**，别直接全局静默安装。

两个样本一对比就能看出：**审查的工作量随「脚本面」变大**——纯说明型 Skill（`find-skills`）只需读一个 `SKILL.md`、重点盯许可证；带脚本的 Skill（`skill-creator`）还得逐个读懂 `scripts/` 的子进程与文件操作，并留意 Apache-2.0 的分发义务。

## 常见错误

1. **直接照搬 `-g -y`**：看到 README 这么写就照敲，等于把全局静默授权交给陌生人。先项目级试用。
2. **只看 README，不读 `SKILL.md` 正文和 `scripts/`**：合同在源码里，README 不会告诉你脚本藏了什么。
3. **漏掉钩子（hooks）**：忘了检查安装脚本有没有偷偷改 `settings.json` 加自动执行的钩子——最隐蔽的执行点。
4. **把「上游公开」当成「许可证允许」**：公开仓库也可能没 LICENSE（`find-skills` 上游就是）。未声明 ≠ 可复用。
5. **全局装完不留卸载方案**：装得上、卸不净。装之前先记下「装在哪、怎么卸、怎么验证干净」。
6. **许可证待确认就当 MIT 用、打包再分发**：自己试用和再分发是两回事，未确认前别纳入「可自由分发」。

## 自测题 / 验收

1. 用自己的话说：为什么 `-g -y` 比项目级安装风险更高？（讲清「全局」和「跳过确认」分别授权了什么。）
2. 审查清单至少背出 5 步，并说出每步「具体要做什么动作」。
3. 打开 `skills/find-skills/SKILL.md`，找出那条与本篇建议冲突的安装命令。（提示：在 Step 4 Offer to Install。）
4. `skill-creator` 是 Apache-2.0。要把它收进自己仓库再分发，必须保留什么？为什么不能用别的许可证覆盖？
5. 给出一个「项目级试用 + 退出方案」的完整步骤：装在哪、怎么试、出问题怎么撤、怎么验证干净。

第 3、5 题能动手做出来，说明这份清单你已经能用了。
