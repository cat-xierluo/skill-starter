# 调试与发布

上一篇 [03 基于模板创建](./03-基于模板创建.md) 帮你搭起 Skill 骨架，[07 带脚本 Skill](./07-带脚本-Skill.md) 又让骨架「会做」了一件事。但搭起来、能跑通一条命令，都不等于别人能用——本地能跑，换台机器可能路径崩；你测过触发，别人可能根本触发不了；你改完代码，没有版本号就没人知道是不是新版。这篇讲清楚 Skill 从「我这里能跑」走到「别人能稳定用」的最后一公里：本地怎么验证触发、跨平台怎么不踩坑、出错怎么诊断、版本怎么管理、怎么打 tag 和写安装说明。贯穿示例继续用 07 篇造的那个 `todo` Skill（`SKILL.md` + `scripts/todo.py`）。

## 本篇目标

读完这篇，你能：

- 在本地验证一个 Skill 是否被正确发现、被正确触发，并定位「触发不了」的原因；
- 处理 Skill 的跨平台差异（`python3` vs `python`、Bash 在 Windows 上需 Git Bash、虚拟环境激活命令不同）；
- 按一张「调试问题表」快速排查触发不了、权限错误、超时、路径错误四类常见故障；
- 给 Skill 做版本管理：用语义化版本号、写 `CHANGELOG.md`、打 git tag；
- 写出可被别人照着执行的安装说明（GitHub Release + Skills CLI）。

命令以 macOS / Linux 为主，Windows 差异处逐一标注（[终端入门](../02-工具指南/06-终端与命令行入门.md) 讲过退出码基础，[Git 入门](../02-工具指南/01-Git-入门.md) 讲过版本控制基础，这里直接用）。

## 核心概念：调试与发布是两个阶段，门禁不同

调试和发布不是同一件事，把它们混在一起最容易「本地跑通就以为能发布」。下面一张表先划清两个阶段的边界：

| 阶段 | 回答的问题 | 门禁 | 失败后果 |
|------|------------|------|----------|
| 调试（本地） | 「在我这台机器上，它真的按预期工作吗？」 | 本地门禁：脚本能跑、退出码诚实、能被 AI 触发 | 你自己用着就出错 |
| 发布（对外） | 「换一台机器、换一个用户，它还能用吗？」 | 真实可用门禁：跨平台、依赖可装、版本可追溯、安装说明可照抄 | 别人装上就崩，再也没人用 |

这两个门禁的要求是叠加的：发布门禁包含调试门禁的全部要求，再加上「换环境也要稳」。所以本篇动手步骤的顺序就是先过本地门禁（第 1-3 步：发现、跨平台、诊断），再过发布门禁（第 4-5 步：版本、tag 与安装说明）。

这里要先把几个反复出现的术语讲清（不依赖你点链接就能懂）：

- **frontmatter**：`SKILL.md` 开头被 `---` 包起来的那段元信息，关键字段是 `name`（目录名要和它一致）和 `description`（决定 AI 什么时候触发它）。调试「触发不了」八成先查这里。
- **语义化版本（Semantic Versioning）**：版本号写成 `主版本.次版本.修订号`（如 `0.1.0`、`1.2.3`）。`0.x.0` 表示还没到 1.0 的早期阶段，破坏性改动可以随便加；到了 `1.x.x` 就要更克制。本仓库自己的 `CHANGELOG.md` 从 `0.1.0` 起一直按这个规则迭代，是「版本管理」的活教材。
- **tag**（标签）：Git 里给某个 commit 打的命名书签，常用版本号命名（如 `v0.1.0`）。它就是「这一刻发布的就是这个版本」的锚点。
- **release**（发布）：在 tag 之上挂一份给用户看的说明（通常在 GitHub 的 Releases 页面），附上下载方式。tag 是技术锚点，release 是面向用户的发布物。
- **回滚**（rollback）：发布后发现新版本有问题，退回上一个能用的版本。tag 让回滚变得可行——只要旧 tag 还在，就能回到那个状态。完整回滚实操（引入回归 → 用 tag 回滚）见 [10 从复制到发布-逐步实验](./10-从复制到发布-逐步实验.md)。

> 一句话定位：调试解决「能不能用」，发布解决「别人能不能稳定用」。前者看你自己，后者看换台机器。

## 动手步骤：从本地能跑到别人能用

下面 5 步把 07 篇的 `todo` Skill 从「本地跑通」推到「打 tag 发布、写安装说明」。每步都是真有动作的。

### 第 1 步：本地发现与触发验证

Skill 写好后第一件事该做什么？先别急着测功能——先测「它有没有被发现、被触发」。AI 使用 Skill 的链路是「发现 → 触发 → 加载 → 执行 → 输出」，前两段坏了，后面再正确也没用。在仓库里，Skill 通过 `.claude/skills/` 这个软链接被 Agent 发现（README 的「多 Agent 共享」一节讲过：`.codex`、`.openclaw`、`.workbuddy` 都软链到 `.claude/skills`，单一来源、不双写）。先确认 `todo` 在发现路径上：

```bash
ls -la .claude/skills/todo/SKILL.md       # 应能看到文件
ls -la .openclaw/skills/todo/SKILL.md     # 软链应当指向同一个文件
```

接着验证触发——核心看 `SKILL.md` 的 frontmatter。把 `todo` 的 `description` 念成两种问法，看它该不该触发：

```text
正向触发（该触发）：
  「帮我加个待办：读完概念入门」
  「我有什么待办」
负向触发（不该触发，详见 description 里写的「不要用于」）：
  「在日历上加个提醒」   ← 涉及到期提醒，不该触发
  「团队看板怎么用」     ← 涉及多人协作，不该触发
```

如果正向问法没触发，先回到 `description` 检查三件事：(1) 是否写清「应在……时使用」；(2) 是否列出负向触发（「不要用于：……」）；(3) 是否覆盖用户的多种问法（「记一下」「加个待办」「我有什么待办」）。`description` 写得太泛或太具体都会让 AI 判断失误——这是「触发不了」最常见的原因（详见下方调试问题表）。

> 跨平台提示：触发验证不需要敲命令，是在 AI 会话里用自然语言试。但「Skill 是否被发现」依赖目录结构和软链，Windows 上软链行为和 macOS / Linux 不同，建议在 Git Bash 或 WSL 里核对路径。

### 第 2 步：依赖与跨平台处理

本地能触发后，要保证换台机器也能跑。`todo.py` 只用 Python 标准库（`json`、`sys`、`pathlib`），**没有外部依赖**——这是最省心的情形。但 Skill 一旦 `import` 了第三方库，跨平台就成了发布前必须处理的事。

先说命令本身的跨平台差异，这是 Windows 用户最先撞的坑：

| 平台 | 跑 Python 脚本 | 创建虚拟环境 | 激活虚拟环境 |
|------|----------------|--------------|--------------|
| macOS / Linux | `python3 scripts/todo.py ...` | `python3 -m venv .venv` | `source .venv/bin/activate` |
| Windows（PowerShell） | `python scripts/todo.py ...` | `python -m venv .venv` | `.\.venv\Scripts\Activate.ps1` |
| Windows（Git Bash） | `python scripts/todo.py ...` | `python -m venv .venv` | `source .venv/Scripts/activate` |

三条注意：(1) `SKILL.md` 正文里统一写 `python3`，Windows 用户自行替换成 `python`（macOS 和大多数 Linux 自带 `python3`，Windows 装完 Python 后通常只有 `python`）。(2) PowerShell 激活可能撞上 ExecutionPolicy 报错，解法见 [开发环境与依赖入门](../02-工具指南/08-开发环境与依赖入门.md)。(3) 你的脚本如果用了 Bash（`.sh`），Windows 用户必须在 Git Bash 里跑，原生 cmd / PowerShell 跑不了——这一点要在 `SKILL.md` 里写明。

依赖声明按 07 篇的规矩：外部依赖一律写进 `assets/requirements.txt`（带版本号，如 `requests==2.32.3`，版本按你实际用的写），并在 `SKILL.md` 写清「先建虚拟环境、再 `pip install -r assets/requirements.txt`」。不声明依赖 = 换台机器就 `ModuleNotFoundError`，这是发布门禁最容易漏的一条。

### 第 3 步：用调试问题表诊断四类故障

触发和跨平台都过了，仍会有运行时故障。下面这张表保留自原文，是本篇最有价值的骨架——四类最常见问题、可能原因、解决方向，照着对就行：

| 问题 | 可能原因 | 解决 |
|------|----------|------|
| 触发不了 | `description` 写得太泛或太模糊 | 检查 SKILL.md frontmatter 的 `description`，补正向触发、负向触发和多种问法（见第 1 步） |
| 权限错误 | 缺少授权（OAuth / API Token / 文件读写权限） | 走环境变量重新授权；脚本要写文件时确认目标目录可写（见 [09 环境变量与密钥安全](../02-工具指南/09-环境变量与密钥安全.md)） |
| 超时 | 任务太重，单次执行超过工具的超时阈值 | 拆解任务，或在脚本里加 `timeout` 限制单步耗时 |
| 路径错误 | 用了相对路径或硬编码绝对路径 | 用 `__file__` / `Path(__file__).parent` 基于脚本自身位置定位，别写死 `/Users/your-name/...` |

带脚本型还有一类只在调试时才暴露的问题：**脚本失败却返回退出码 0**。Agent 靠退出码判断成败（0 = 成功，非 0 = 失败），失败却返回 0 会骗 Agent 拿着错误结果往下走。验证方法（退出码 macOS/Linux 用 `echo $?`，Windows PowerShell 用 `$LASTEXITCODE`）：

```bash
python3 scripts/todo.py done 99   # 故意失败：应退出码非 0、stderr 报「找不到 id」
echo $?                           # 应打印非 0（如 1）
```

如果它打印了 0，说明契约没守住——回 07 篇的「常见错误」对照修。

### 第 4 步：版本管理与 CHANGELOG

本地门禁全过后，进入发布门禁。第一步是给 Skill 一个可追溯的版本号。本仓库的做法是直接抄过来用：即使 Skill 还没正式对外发布，也按 `0.x.0`（如 `0.1.0`、`0.2.0`）持续记录，而不是只挂一个「Unreleased」。本仓库根 `CHANGELOG.md` 从 `0.1.0` 一路记到 `0.22.0`，就是这个约定的活教材。

给 `todo` Skill 写第一份 `CHANGELOG.md`，照 Keep a Changelog 的段落结构（`Added` / `Changed` / `Fixed` / `Removed`）：

```markdown
# Changelog

本文件记录 todo Skill 对外可见的变更。

## 0.1.0 - 2026-07-28

### Added

- 首个可用版本：`add` / `list` / `done` 三命令，数据存 `todos.json`。
- 输入输出契约：成功走 stdout（JSON），错误走 stderr，退出码 0/1/2。
- `.env.example` 与 `assets/todos.example.json` 模板。
```

版本号怎么涨，按语义化版本的约定（前三条最常用）：

| 改动类型 | 例子 | 版本号变化 |
|----------|------|------------|
| 破坏性改动（契约变了、不向后兼容） | `done` 命令改名为 `complete` | 次版本号 +1（`0.1.0` → `0.2.0`，`0.x` 阶段主版本固定 0） |
| 新增功能（向后兼容） | 加一个 `clear` 命令 | 次版本号 +1 |
| 仅修 bug（向后兼容） | 修 `done 99` 误返回 0 的问题 | 修订号 +1（`0.1.0` → `0.1.1`） |

这里有个本仓库特有的强化点：**`TASKS.md` 和 `DECISIONS.md` 要和 `CHANGELOG.md` 同步更新**。`CHANGELOG.md` 记「对外可见的变更」，`TASKS.md` 记「当前待办和完成状态」，`DECISIONS.md` 记「为什么这么决定」。三者是本仓库协作文档体系的一组约定（见根 `AGENTS.md`）。发布前对照检查：这一版做完的任务在 `TASKS.md` 里是否标完成？关键决策是否记进 `DECISIONS.md`？`CHANGELOG.md` 是否反映了这些改动？三个文件对不上，发布就少了追溯线索。

### 第 5 步：打 tag、写安装说明

版本号定好、CHANGELOG 写好，就把这个版本「钉死」——打 git tag，再写一份别人能照抄的安装说明。

先打 tag（前提是代码已 commit；commit 规范见 [提交到 GitHub 与 Commit 规范](../02-工具指南/04-提交到-GitHub-与-Commit-规范.md)）：

```bash
git tag -a v0.1.0 -m "todo Skill 0.1.0：首个可用版本"
git push origin v0.1.0
```

`-a` 打带说明的标签（annotated tag，会记下打 tag 的人、时间、说明，比轻量标签信息全）；`-m` 后面是这条 tag 的说明。tag 推上去后，在 GitHub 的 Releases 页面基于这个 tag 发一个 release，把 `CHANGELOG.md` 里 `0.1.0` 那段贴进 release notes——这就是面向用户的发布物（GitHub 入门见 [GitHub 入门](../02-工具指南/02-GitHub-入门.md)）。

接着在 `SKILL.md` 或 `README.md` 里写清安装方式。本仓库 README 背书的主推渠道有两条：

**方式一：Skills CLI 安装**（主推）。Skills CLI（`npx skills`，来自 vercel-labs/skills 生态）是本仓库默认的 Skill 发现与安装工具：

```bash
npx skills add <owner>/<repo>@todo
```

`<owner>/<repo>` 换成你的 GitHub 仓库地址，`@todo` 是 Skill 在仓库里的目录名。这条命令用户照抄即可，不需要手动 clone。

**方式二：GitHub Release + 手动安装**。直接分享仓库地址，用户 clone 或下载 release 后把 Skill 目录放进自己的 `.claude/skills/`：

```bash
git clone https://github.com/<owner>/<repo>.git
cp -r <repo>/skills/todo ~/.claude/skills/todo
```

**关于 OpenClaw 与 ClawHub**：OpenClaw 是真实存在的平台，如果你的 Skill 面向 OpenClaw 用户，可在其平台按文档导入（仓库 URL 或 Skill 目录）。原文提到的「ClawHub 一键安装」目前**仅出现在上游 `legal-skills` 的 `git-batch-commit` 参考文档里**（见 `skills/git-batch-commit/references/clawhub-sync-check.md`），**本仓库 README 未背书**，是否作为推荐渠道**待核对**——在它被正式收录前，不要写成「推荐」，写成「若你的环境装了 `clawhub-sync` 才会触发」更稳妥。

发布前过一遍这张清单（保留自原文，是发布门禁的最终检查）：

- [ ] `SKILL.md` 描述清晰（`description` 覆盖正向 / 负向触发、多种问法）
- [ ] 脚本能跑通（退出码诚实、stdout / stderr 分开、无硬编码路径）
- [ ] 跨平台已处理（`python3` vs `python`、Bash 需 Git Bash、依赖已声明）
- [ ] 敏感信息放 `.env`，模板放 `.env.example`，真值被 `.gitignore` 忽略
- [ ] `CHANGELOG.md`、`ROADMAP.md`、`TASKS.md`、`DECISIONS.md` 已同步
- [ ] 已打 tag 并推送，GitHub Release 已发布，安装说明可照抄

### 推荐仓库结构（发布前对照）

发布前最终目录长这样（保留自原文，是发布门禁的物料清单）：

```text
todo/
├── SKILL.md
├── CHANGELOG.md
├── ROADMAP.md
├── TASKS.md
├── DECISIONS.md
├── .env.example
├── LICENSE.txt          # 需自行新增（模板不预选许可证，见 03 篇）
├── assets/
│   ├── requirements.txt        # 有外部依赖时才需要
│   ├── config.yaml.example
│   └── todos.example.json
├── references/
└── scripts/
    └── todo.py
```

每个位置职责一句话：`SKILL.md` 是说明书和触发条件；`scripts/` 是干活的代码；`assets/` 放配置模板、依赖清单、示例数据；`references/` 放给 AI 按需读的详细资料；`.env.example` 放环境变量模板（真值 `.env` 不进仓库）；`CHANGELOG` / `ROADMAP` / `TASKS` / `DECISIONS` 四件套是协作文档，对外可见的变更走 CHANGELOG。运行时生成的数据（如 `todos.json`）由脚本现写，不进仓库（记得加进 `.gitignore`）。

## 常见错误

### 触发不了却去查脚本

Skill 没被触发，第一反应是去翻 `scripts/`——但触发阶段根本没走到执行。正确顺序：先查 frontmatter 的 `description`（是否覆盖正向 / 负向触发和多种问法），再查 Skill 是否在发现路径（`.claude/skills/` 软链是否指向它），最后才轮到脚本。

### 本地能跑就直接发布

「我这台机器能跑」只过了本地门禁，没过发布门禁。换台机器：`python3` 可能要写成 `python`、依赖没装、硬编码路径崩、Windows 跑不了 Bash。正确做法：发布前过一遍第 2 步的跨平台表和发布检查清单。

### 脚本失败却返回退出码 0

Agent 只看退出码是否为 0。失败返回 0，Agent 就当成功、拿着错误结果往下走。正确做法：所有错误路径返回非 0，原因走 stderr。`done 99` 那条验证就是专门防它的。

### 改了代码但不升版本号、不写 CHANGELOG

用户装的是 `v0.1.0`，你偷偷改了代码又推上去，tag 还指着旧 commit——用户永远拿不到你的修复，出了问题也没法对照版本。正确做法：任何对外可见的改动都升版本号（按第 4 步的表）、写进 `CHANGELOG.md`、打新 tag。

### TASKS / DECISIONS 和 CHANGELOG 对不上

`CHANGELOG.md` 写了「修复 done 99 误返回 0」，但 `TASKS.md` 里这条任务还没标完成、`DECISIONS.md` 里也没记「为什么把退出码从 0 改成 1」。三个文件对不上，追溯就断了。正确做法：发布前对照检查，三者反映同一组事实。

### 把 ClawHub 当默认推荐渠道写进文档

ClawHub 目前只在上游 `legal-skills` 的参考文档里出现，本仓库 README 未背书。把它写成「推荐」会让用户照抄后失败。正确做法：主推 Skills CLI（`npx skills`）和 GitHub Release；ClawHub 标「待核对」或「仅当环境装了 `clawhub-sync` 才触发」。

## 自测题 / 验收

1. 本地验证 Skill 被发现，你要检查哪两件事？（提示：发现路径和 frontmatter。）如果正向问法没触发，先查 `description` 的哪三点？
2. 给 `todo.py` 加一个 `import requests`，发布前必须同步做哪两件事？Windows 用户激活虚拟环境可能撞上什么问题？
3. 跑 `python3 scripts/todo.py done 99`，它应该返回什么退出码？如果返回 0，说明什么问题？这条验证防的是哪类常见错误？
4. 你修了 `done` 命令的一个 bug（向后兼容）。版本号该怎么涨？要在哪几个文件里留记录（至少说出三个）？为什么要打 tag？
5. 本仓库 README 背书的发布主推渠道是哪两条？ClawHub 为什么不能写成「推荐」？

第 5 题能说清「主推渠道」和「ClawHub 待核对」的区别，说明你已经在按「真实可用」而非「本地能跑」的标准做发布了。
