# 搜索现成方案

上一篇 [01 需求分析](./01-需求分析.md) 帮你想清楚**要什么**。这篇讲想清楚之后、动手之前的关键一步：**先搜一圈，别重复造轮子**。你大概率不是第一个想解决这类问题的人——动手前花十分钟搜索，可能省下后面十个小时的编码和排错。

但搜索只是起点。本仓库 [README](../README.md) 的默认使用路径说得很明白：先搜现成方案，搜到了优先直接用或定向改造，**只有找不到合适方案时，再进入创建流程**。这篇就把这条路径的前半段——「搜、筛、评、试、决」——讲透。

## 本篇目标

读完这篇，你能：

- 按「find-skills / Skills CLI → GitHub → 互联网」的顺序做一轮完整搜索；
- 用项目内置的 `find-skills` 或 Skills CLI（即 `npx skills` 命令行工具）三种方式之一搜出候选 Skill；
- 用一张五维度评估表给候选 Skill 打分，判断「相关性、活跃度、质量、依赖、许可证」谁过关、谁不行；
- 区分「项目级试用」和「全局安装」，并解释为什么默认推荐前者（安全口径承接 [05 第三方 Skill 安全审查](./05-第三方-Skill-安全审查.md)）；
- 在「直接复用 / 定向改造 / 从零新建」三条出路里，挑出当下最划算的一条。

命令以 macOS / Linux 为主；本篇的命令都很短，Windows 读者在 Git Bash 里照抄即可，PowerShell 注意引号差异。版本与平台信息最近核对：2026-07。

## 前置知识

- [01 需求分析](./01-需求分析.md)：你已经把需求拆成「目标 / 触发场景 / 输入 / 输出 / 边界」——搜索时拿这个去比对候选 Skill 的描述。
- [什么是 Skill？](../01-概念入门/01-什么是-Skill.md)：知道 Skill 是给 AI 装的「App」，是一个文件夹（`SKILL.md` + 可选 `scripts/`、`references/`、`assets/`）。
- [什么是许可证？](../01-概念入门/02-什么是-许可证.md)：评估表里有一项就是许可证，「公开可见」和「允许复用」是两回事。
- 命令行基础：会敲 `npx`、`cd`、`cp` 即可，无需预先掌握，照抄示例即可。

## 核心概念：先搜后造，找到不等于能用

### 为什么要先搜索

四个理由，按重要性排：

1. **大概率已经有人解决过**。todo、commit 规范、PR 模板、文档生成这类常见需求，生态里早有现成 Skill，没必要从零写。
2. **搜索过程会逼你想清楚需求**。为了在搜索框里敲对关键词，你会被迫把「我要做的到底是哪一类事」说精确——这一步本身就是在做需求分析。
3. **省下的是自己的时间**。即便现成方案只能用一半，你也省掉了搭脚手架、定结构、写测试的体力活。
4. **有时候会发现更优雅的思路**。看别人怎么拆同一个问题，常常比闷头写更能打开视野。

### 搜索顺序（按这个走）

记住一条主线，从近到远：

| 顺序 | 渠道 | 找什么 | 为什么这个顺序 |
|------|------|--------|----------------|
| 1 | **find-skills / Skills CLI**（首选） | 已收录的 Skill 生态 | 最近、最可信、和你的工作流天然对接 |
| 2 | **GitHub** | 关键词 + 平台限定搜代码与仓库 | 生态收录之外的开放方案 |
| 3 | **互联网**（搜索引擎） | 通用问题、API 用法、概念理解 | 兜底，但通常搜不到「Skill」这种打包形态 |

为什么是这个顺序？越靠前，匹配到「能直接装的 Skill」的概率越高；越靠后，搜到的越是「思路 / 代码片段」，需要你自己二次打包成 Skill。所以从前往后找，前面没有再退一步。

### find-skills 的三种用法

`find-skills` 是本仓库**项目内置**的纯说明型 Skill（源文件在 `skills/find-skills/`），作用就是帮你发现和安装其它 Skill。它本身来自第三方生态 [vercel-labs/skills](https://github.com/vercel-labs/skills)（即 Skills CLI / skills.sh 背后的项目），本仓库已收录内置。用起来有三种入口：

**方式一：直接用项目内置的 find-skills。** 如果你正在这个 starter 仓库里用 Claude Code（或 OpenClaw、Codex 等同样通过符号链接共享的 Agent），项目已经把根目录 `skills/` 暴露给了 `.claude/skills`：

```text
.claude/skills -> ../skills
.claude/skills/find-skills/
```

也就是说，仓库本身就带了一个开箱即用的搜索引导 Skill——你只要对 Agent 说「帮我找个做 X 的 Skill」，它就会触发 `find-skills` 并跑搜索流程。实际维护的源文件是 `skills/find-skills/SKILL.md`，`.claude/skills/find-skills/` 只是通过符号链接暴露出来的项目级入口，**不复制、不双写**。

**方式二：直接用 Skills CLI 搜索。** Skills CLI 是 `npx skills` 这条命令行工具的正式名字，是 skills 生态的「包管理器」，相当于 Skill 界的 npm。直接敲：

```bash
npx skills find <关键词>
```

它会把匹配到的 Skill 列成清单，告诉你每个 Skill 的来源仓库和安装命令。也可以去浏览器浏览：<https://skills.sh/>。

**方式三：先安装独立的 find-skills。** 如果你的工作流不在这个仓库里、又想长期用 find-skills 引导搜索，可以把它独立装到自己项目里（安装命令与风险见下面「动手步骤」第 1 步的安全提醒，**不要直接照抄 `-g -y`**）。

### 五维度评估表（最有用的骨架）

搜到一堆候选之后，别急着装。先按这张表给每个候选打分——这是本篇最值得背下来的东西：

| 维度 | 看什么 | 差 | 好 |
|------|--------|-----|-----|
| 相关性 | 描述和你的需求是否匹配 | 勉强相关，得大改 | 精准命中，开箱即用 |
| 活跃度 | 最近更新时间、issue 回复 | 一年前没动过 | 3 个月内还在更新 |
| 质量 | README 是否清晰、代码是否规范 | 文档混乱、结构散乱 | 结构清晰、有测试 |
| 依赖 | 需要什么外部依赖 | 重依赖、要装一堆 | 零依赖或轻量 |
| 许可证 | 能否商用 / 再分发 | 不明确或未声明 | MIT / Apache-2.0 |

五条全过的，直接用；三到四条过的，考虑定向改造（见 [07 复用改造还是新建](../01-概念入门/07-复用改造还是新建.md)）；不到三条的，多半不值得花时间，不如新建。

许可证这一条单独提醒：**目标仓库许可证不明确时，不要直接复制实现**。先看 [什么是许可证？](../01-概念入门/02-什么是-许可证.md) 搞清「试用」和「再分发」的差别——本仓库收录的 `find-skills` 上游就未提供 LICENSE（状态「待确认」，见 [`docs/SOURCE-INDEX.md`](../docs/SOURCE-INDEX.md)），可以自己试用，但不能打包进自己的仓库再分发。

## 动手步骤：用 todo 场景走一遍搜索

下面用一个贯穿全系列的例子把搜索流程完整走一遍。需求：你想做一个本地待办 Skill（基于 `todo.py`，存 `todos.json`，`add/list/done` 三命令），让 Agent 帮你管待办。先别急着写，先搜。

### 第 1 步：用 find-skills / Skills CLI 搜第一轮

最省事的方式：直接对 Agent 说「帮我找一个管理 todo / 待办列表的 Skill」，触发项目内置的 `find-skills`。或者自己敲 Skills CLI：

```bash
npx skills find todo
npx skills find "task management"
```

看返回的清单，记下候选的名字、来源仓库（形如 `owner/repo@skill`）和 skills.sh 链接。

**关于 `-g -y` 的安全提醒**（重要）：`find-skills/SKILL.md` 在示范安装时会写 `npx skills add <owner/repo@skill> -g -y`。这里 `-g`（global，全局 / 用户级）装一次你所有项目都能用，`-y`（yes，跳过确认）把安装中所有提问自动回答是。两者叠加 = 「全局、静默、别问我」。对**没审过的第三方 Skill**，这是高风险组合——一旦它投毒或安装脚本顺手改了你的配置，你毫无察觉。所以**默认推荐项目级试用**（不带 `-g`，只装到当前目录），全局 `-g -y` 留给你充分信任的官方 Skill，且要先看源码。完整审查清单见 [05 第三方 Skill 安全审查](./05-第三方-Skill-安全审查.md)。

### 第 2 步：去 GitHub 搜第二轮

第一轮没命中精准的，退一步去 GitHub。用关键词加平台限定搜，扩大命中面——常见平台关键词都试一遍（本仓库面向 OpenClaw、Claude Code、Skills CLI 生态，所以这几个词都可以加，但不要把任何一个当成唯一平台）：

```text
todo "claude skill"
todo "agent skill"
todo "openclaw skill"
```

重点看三件事：**stars**（多少人用，反映可信度）、**最近更新时间**（活跃度）、**README 是否清晰**（质量）。把看起来靠谱的两三个候选记下来。

### 第 3 步：用评估表逐个打分

把第 1、2 步筛出来的候选，挨个套进五维度评估表。比如候选 A 是一个活跃维护、MIT 许可、但只支持 `add/list` 没有 `done` 的 todo Skill：

| 维度 | 候选 A | 判断 |
|------|--------|------|
| 相关性 | 缺 `done` 命令，得加 | 中（4/5） |
| 活跃度 | 上周还在更新 | 过 |
| 质量 | README 清晰、有测试 | 过 |
| 依赖 | 只用 Python 标准库 | 过 |
| 许可证 | MIT | 过 |

四条过、一条局部不匹配——这种候选最适合「定向改造」（在它的基础上补一个 `done` 命令），比从零新建划算得多。

### 第 4 步：项目级试跑

打分过关的，先**项目级试用**（不是全局装）。把它放到某个测试项目的 skills 目录里（或用不带 `-g` 的方式装），作用范围只限这一个目录：

```bash
# 在一个测试项目里，装到项目级（不带 -g）
npx skills add <owner/repo@skill>
```

然后跑一遍核心场景，看它真的能干活、没有奇怪行为。万一行为异常，污染的只是这一个项目，删掉目录就干净了。试用阶段盯住：它有没有联网、有没有读你的密钥、有没有改 `settings.json` 加钩子（hooks，一种在你每次工具调用前后自动执行命令的机制）——这三类高危点的完整清单见 [05 第三方 Skill 安全审查](./05-第三方-Skill-安全审查.md)。

### 第 5 步：决定复用、改造还是新建

试跑完，在三条出路里挑一条（决策细节见 [07 复用改造还是新建](../01-概念入门/07-复用改造还是新建.md)）：

| 出路 | 什么时候选 | 下一步去哪 |
|------|-----------|-----------|
| **直接复用** | 五维度全过、试跑正常 | 收工，把它纳入项目 |
| **定向改造** | 大体匹配、只差局部 | 基于 Fork 改，见 07 复用改造 |
| **从零新建** | 搜了一圈没合适的 | [03 基于模板创建](./03-基于模板创建.md) |

> 恭喜走到「从零新建」的人：你是这个细分场景里第一个动手的。带着你前面搜索时积累的关键词、别人方案的优缺点，去 [03 基于模板创建](./03-基于模板创建.md) 开始搭建——你比没搜过的人起点高得多。

## 常见错误

### 只搜一个渠道就放弃

只在 Skills CLI 搜了一下没结果，就断定「没有现成方案，我自己写」。实际上 GitHub 和互联网里可能还有大量生态未收录的方案。按「find-skills / Skills CLI → GitHub → 互联网」三步都走完，再下结论。

### 看到第一条结果就装

搜出来第一个 todo Skill 就 `npx skills add`，没比较、没打分。结果装下来发现许可证不明、依赖一堆、上周就停更了。正确做法：至少筛两三个候选，套评估表逐项打分再决定。

### 把「公开」当成「许可证允许」

仓库公开可见，不代表你可以复制它的实现再分发。本仓库收录的 `find-skills` 上游就没有 LICENSE（状态「待确认」）。未声明 ≠ 可复用。先看 [什么是许可证？](../01-概念入门/02-什么是-许可证.md)，区分「自己试用」和「再分发」。

### 直接照搬 `-g -y` 全局静默安装

README 里写了 `-g -y` 就照敲，等于把全局静默授权交给陌生人。正确做法：对没审过的第三方 Skill 默认项目级试用（不带 `-g`），全局安装留给充分信任的官方 Skill，且先看源码。详见 [05 第三方 Skill 安全审查](./05-第三方-Skill-安全审查.md)。

### 只看 README 不看源码

README 是广告，`SKILL.md` 和 `scripts/` 才是合同。README 不会告诉你脚本里藏了什么网络调用、读了哪些文件。评估时至少打开 `SKILL.md` 正文和 `scripts/` 扫一遍。

### 找到现成方案就跳过需求分析

看到有现成 todo Skill，就把自己在 01 里写的需求文档扔了。结果装下来发现它支持的命令、存的格式、触发的场景和你真正要的对不上。正确做法：拿着 01 的需求文档去比对每个候选的描述，匹配度才是评估表第一行「相关性」的判据。

## 自测题 / 验收

1. 默写出搜索顺序的三步，并解释「为什么是这个顺序」。
2. `find-skills` 的三种用法分别是什么？哪种是这个 starter 仓库里开箱即用的？
3. 用五维度评估表给你最近找到的一个候选 Skill 打分，并说出它走「复用 / 改造 / 新建」哪条出路。
4. `npx skills add <pkg> -g -y` 里的 `-g` 和 `-y` 分别授权了什么？为什么对没审过的第三方 Skill 不该用它？
5. 你在 GitHub 搜 `todo "agent skill"` 找到一个仓库，它没有 LICENSE 文件。你能把它复制进自己仓库再分发吗？为什么？

第 3、5 题能答上来，说明你已经能把搜索结果转化成一个明确决策——这篇的目标就达到了。
