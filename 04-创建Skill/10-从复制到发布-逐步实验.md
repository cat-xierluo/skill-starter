# 从复制到发布：逐步实验

前面几篇把 Skill 的每个环节都讲过了——[03 基于模板创建](./03-基于模板创建.md) 讲怎么搭骨架，[07 带脚本 Skill](./07-带脚本-Skill.md) 讲脚本契约，[04 调试与发布](./04-调试与发布.md) 讲版本和发布。但"听过一遍"和"自己走通一遍"差得很远。这篇是一次端到端走查：在一个干净目录里，从复制模板开始，一路走到运行、测试、打版本、发布，最后演示一次真实的回滚。

## 本篇目标

跟着做完这次实验，你能：

- 在干净目录里从模板复制出一个完整的 `todo` Skill，并改写成可运行的样子；
- 跑通 `add` / `list` / `done` 三命令，亲眼确认退出码诚实（失败真的返回非 0）；
- 用测试守住脚本契约，并看懂测试红灯在告诉你什么；
- 给这个 Skill 写版本号、打 git tag，完成一次本地"发布"；
- 演示一次真实的回滚：故意引入一个回归，再用 tag 退回能用版本。

## 前置知识

- [07 带脚本 Skill](./07-带脚本-Skill.md)：`todo.py` 的契约（成功走 stdout、错误走 stderr、退出码 0/1/2）。本篇直接照搬那套契约，不重述。
- [04 调试与发布](./04-调试与发布.md)：语义化版本、tag、release 的概念。本篇只敲命令，概念一律回到这里查。
- [Git 入门](../02-工具指南/01-Git-入门.md)：尤其「撤销操作：restore / revert / reset 怎么选」一节——回滚实验会用到。
- 命令行基础：`mktemp`、`cp`、`cd`、`python3`。macOS 和大多数 Linux 自带；Windows 用 Git Bash（`mktemp` 在 Git Bash 里可用，原生 PowerShell 没有）。

本仓库已经有一个完整可运行的标准示例 [`skills/todo`](../skills/todo/)——它就是你这次实验要复制出来的东西的「标准答案」。做的时候随时可以打开它对照。

## 核心概念：本篇是走查，不是讲概念

本篇不重复 04/07 的概念说明。它的定位是**把概念串成一条能照着敲的命令链**：每一步都告诉你敲什么、该看到什么、错了怎么办。只有一个概念是 04 没讲透的——**回滚实操**（04 只给了一句话定义），本篇第 7 步会把它补全。

实验全程在一个**临时目录**里做，不碰你的仓库工作树。这是故意设计的：T-007 的 `skills/todo` 已经在仓库里，你要是在仓库内再 `cp` 一份会撞名；更重要的是，干净目录能逼你把"从零开始"的每个动作都走一遍。

## 动手步骤：7 步从复制到回滚

下面 7 步把一个 `todo` Skill 从模板推到"能打 tag 发布、能回滚"。每步都有输入（敲什么）、预期结果（看到什么）、失败恢复（错了怎么办）。

### 第 1 步：在干净目录复制模板

先建一个一次性临时目录，在里面初始化一个独立的 git 仓库，再从模板复制出 `todo`：

```bash
LAB=$(mktemp -d)                 # 建临时目录，路径存进 LAB
cd "$LAB"
git init                          # 初始化一个独立仓库（后面打 tag、回滚都用它）
cp -r /path/to/skill-starter/skills/skill-template todo
cd todo
ls                                # 应看到 SKILL.md、scripts/、assets/、LICENSE.txt 等
```

> 上面的 `/path/to/skill-starter/` 换成你本地的仓库实际路径。复制命令的原理见 [03 基于模板创建](./03-基于模板创建.md)。

**预期结果**：`todo/` 目录里有一整套骨架文件（`SKILL.md`、`scripts/main.py`、`assets/config.yaml.example`、`LICENSE.txt`、`CHANGELOG.md` 等）。

**失败恢复**：`ls` 看不到文件 → 检查 `cp` 的源路径写对没有；`git init` 报错 → 确认你在临时目录里（`pwd` 看一下）。

### 第 2 步：改写成 todo Skill

模板是通用的，要把它改成 `todo`。对着标准答案 [`skills/todo`](../skills/todo/) 改：

1. **改 `SKILL.md`**：`name: skill-template` 改成 `name: todo`；`description` 换成 todo 的正向/负向触发；正文换成 todo 的契约（照 [`skills/todo/SKILL.md`](../skills/todo/SKILL.md) 抄）。
2. **换脚本**：删掉 `scripts/main.py`，新建 `scripts/todo.py`，内容照 [`skills/todo/scripts/todo.py`](../skills/todo/scripts/todo.py)（add/list/done 三命令）。
3. **删掉 todo 用不到的配置**：`todo.py` 只用标准库、不读配置，所以删掉 `.env.example`、`assets/config.yaml.example`、`assets/requirements.txt`（模板验收清单要求"配置字段必须被实际读取"，留空壳反而违规）。保留 `assets/todos.example.json`（放 `[]`）。
4. **加 `.gitignore`**：写上 `todos.json`（运行时数据）和 `__pycache__/`（Python 运行时缓存）。这两样都会在你跑脚本后生成，不忽略的话 `git add .` 会把它们提交进仓库。
5. **清空协作文档占位**：`CHANGELOG.md` / `ROADMAP.md` / `TASKS.md` / `DECISIONS.md` 里的模板占位文字换成 todo 自己的内容。

**预期结果**：`todo/` 的目录结构和 `skills/todo/` 一致——同样的文件、同样该删的都删了。

**失败恢复**：`name` 和目录名不一致 → 仓库的 `check_skills.py` 会报 error（`name` 必须等于目录名）；忘删配置文件 → 对照标准答案，todo 不该有这些文件。

### 第 3 步：运行，确认退出码诚实

改完后先手动跑一遍四条命令，重点看退出码（macOS/Linux 用 `echo $?`，PowerShell 用 `$LASTEXITCODE`）：

```bash
cd "$LAB/todo"
python3 scripts/todo.py add 买牛奶          # 应输出一条 JSON，退出码 0
python3 scripts/todo.py list                # 应列出刚加的条目，退出码 0
python3 scripts/todo.py done 1              # 应输出该条 JSON，退出码 0
python3 scripts/todo.py done 99             # 故意失败：退出码非 0，stderr 报"找不到 id"
echo $?                                     # 上一条的退出码，应是 1
```

**预期结果**：前三条成功（stdout 有 JSON、退出码 0）；最后一条 `done 99` **必须退出码非 0** 并在 stderr 报错。`todos.json` 出现在当前工作目录（cwd），不是在 `todo/` 源目录里。

**失败恢复**：`done 99` 返回了 0 → 这是契约崩了（AI 会被骗成"假绿"），回去检查脚本的错误路径有没有 `return 1`；数据写到了源目录而不是 cwd → 检查 `DB = Path.cwd() / "todos.json"` 这行有没有改对（见 [07 带脚本 Skill](./07-带脚本-Skill.md) 的数据位置说明）。

### 第 4 步：用测试守住契约

手跑一遍只是验证"这一刻能跑"。要守住契约，得有测试。本仓库的 [`tests/test_skill_todo.py`](../tests/test_skill_todo.py) 就是标准答案的测试——你可以直接跑它当对照：

```bash
cd /path/to/skill-starter
python3 -m unittest tests.test_skill_todo -v
```

它覆盖了 10 个场景：正常路径（add/list/done）、4 类错误路径（done 99、空文本、无参数、未知命令）、守恒性（done 后数据真的变 true，防假绿）、干净隔离（运行不污染源目录）、必需文件齐全。

你自己在临时目录复制的版本，可以照着这个测试写一个等价的最小测试，或者直接理解它断言了什么，照着断言来核对。

**预期结果**：仓库的测试全绿（10 个 OK）。

**失败恢复**：测试红灯 → 看是哪一类：退出码不对（错误路径返回了 0）、假绿（done 没真改数据）、隔离失败（数据写到源目录）。每一类都对应一个明确的脚本 bug，对照 [07 带脚本 Skill](./07-带脚本-Skill.md) 的「常见错误」排查。

### 第 5 步：写版本号并提交

能跑、测试绿，就给它一个版本。在 `CHANGELOG.md` 写一段 `0.1.0`：

```markdown
## 0.1.0 - 2026-07-30

### Added

- add / list / done 三命令，纯标准库实现。
```

然后提交（commit 规范见 [提交到 GitHub 与 Commit 规范](../02-工具指南/04-提交到-GitHub-与-Commit-规范.md)）：

```bash
cd "$LAB/todo"
git add .
git commit -m "feat: todo Skill 0.1.0 首个可用版本"
```

**预期结果**：`CHANGELOG.md` 有 `0.1.0` 段落；commit 成功（`git log` 能看到）。

**失败恢复**：协作文档占位没清干净 → 对照标准答案改；版本号写错（比如写成 `v1`）→ 对照 [04 调试与发布](./04-调试与发布.md) 的语义化版本表（`主版本.次版本.修订号`）。

### 第 6 步：打 tag 完成本地发布

把 `0.1.0` 这个状态"钉死"——打 git tag（tag 的概念见 [04 调试与发布](./04-调试与发布.md)）：

```bash
git tag -a v0.1.0 -m "todo Skill 0.1.0：首个可用版本"
git tag                              # 应列出 v0.1.0
```

`-a` 打带说明的标签（annotated tag，会记下打 tag 的人、时间、说明）。到这一步，本地"发布"就完成了——`v0.1.0` 这个 tag 就是"这个版本发布的就是这个 commit"的锚点。

> 可选的真实发布：如果你有自己的 GitHub 远程仓库，可以 `git push origin v0.1.0` 再用 `gh release create v0.1.0` 发一个 release。命令见 [GitHub 入门](../02-工具指南/02-GitHub-入门.md)。没有远程也没关系，本地 tag 演示足以理解整套流程。

**预期结果**：`git tag` 列表里出现 `v0.1.0`。

**失败恢复**：tag 打错名（比如打成 `v0.1`）→ `git tag -d v0.1` 删掉重打；打 tag 时提示"没有提交"→ 回第 5 步先 commit。

### 第 7 步：演示一次真实的回滚

这一步是 04 篇没讲透的——**回滚实操**。先故意引入一个回归，再用 tag 退回能用版本。

**引入回归**：编辑 `scripts/todo.py`，把 `done` 命令里"找不到 id"那段改成总返回 0（制造"假绿"）：

```python
        # 故意改坏：找不到也返回 0（假绿）
        print(f"error: 找不到 id={tid}", file=sys.stderr)
        return 0    # ← 原来是 return 1
```

提交这个坏版本：

```bash
git add scripts/todo.py
git commit -m "0.2.0（故意引入回归）"
python3 scripts/todo.py done 99      # 现在退出码变成 0 了——契约崩了
echo $?                              # 0，不该是 0
```

**用 tag 回滚**。回滚有几种方式，按"改动是否已发布"选（选法的概念底座见 [Git 入门](../02-工具指南/01-Git-入门.md) 的 restore/revert/reset 对比表）：

- **只想看看旧版本长什么样**（不改当前分支）：
  ```bash
  git switch --detach v0.1.0         # 进入 detached HEAD，停在 v0.1.0
  python3 scripts/todo.py done 99    # 退出码又是 1 了，契约恢复
  git switch main                    # 看完回到 main
  ```
- **已发布、想追加一个"撤销提交"**（不改历史，安全）：
  ```bash
  git revert HEAD                    # 新增一个反向提交，抵消那个坏 commit
  ```
- **还没发布、想整体丢掉坏 commit**（本地，慎用）：
  ```bash
  git reset --hard v0.1.0            # 把分支指针挪回 v0.1.0，丢弃之后的提交
  ```

无论哪种，回滚后再跑 `done 99`，退出码应该重新变成 1——契约恢复。

**预期结果**：回滚后 `done 99` 退出码非 0，契约恢复正常。

**失败恢复**：`reset --hard` 误删了还没提交的工作 → 用 `git reflog` 找回（reflog 记录了 HEAD 的每一次移动，见 [Git 入门](../02-工具指南/01-Git-入门.md)）；revert 之后又想撤销 revert → 再 revert 一次，或本地用 reset。

## 常见错误

### 复制后忘改 `name`

模板的 `name: skill-template` 没改成 `name: todo`，结果 `check_skills.py` 报 error（`name` 必须等于目录名）。改 frontmatter 的 `name` 让它和目录名一致即可。

### 忘把运行时产物加进 `.gitignore`

跑了几次脚本后 `git status` 会多出 `todos.json`（运行时数据）和 `scripts/__pycache__/`（Python 缓存），一旦 `git add .` 就把它们提交进仓库。正确做法：在 `.gitignore` 写上 `todos.json` 和 `__pycache__/`，运行时产物永不进仓。

### 打 tag 之前没有 commit

`git tag` 指向的是当前 commit，没 commit 就打 tag 等于把"未保存的改动"当成版本锚点。正确做法：先 `git add . && git commit`，再打 tag。

### 回滚用 `reset` 误删了未推送的工作

`git reset --hard` 会丢掉目标 commit 之后的全部提交。如果其中有还没 push 的工作，就找不回来了。正确做法：已发布的改动用 `git revert`（追加反向提交，不改历史）；只有确定"本地、没 push、可以丢"时才用 reset。误删了用 `git reflog` 找回。

### 测试红了却当绿灯继续

看到测试失败就略过，继续往下做，结果后面每一步都建立在错误基础上。正确做法：测试红灯时先停下来，对照错误路径表定位是哪一类失败（退出码/假绿/隔离），修到绿灯再走。

## 自测题 / 验收

1. 为什么这次实验要在临时目录（`mktemp -d`）里做，而不是直接在仓库里复制？如果在仓库内 `cp -r skills/skill-template todo` 会撞上什么问题？
2. 你跑 `done 99`，它返回了退出码 0。这说明脚本的什么契约崩了？AI 调用它会被骗成什么？
3. 打 `git tag -a v0.1.0` 之前，必须先做哪一步？为什么 tag 不能指向"还没保存的改动"？
4. 你的坏改动**已经 push 到远程**了，现在要回滚。`reset --hard` 和 `git revert` 该选哪个？为什么？（选法见 [Git 入门](../02-工具指南/01-Git-入门.md)）
5. **产物验收清单**：对照 [`tests/test_skill_todo.py`](../tests/test_skill_todo.py) 的 `test_required_files_present`，你复制的 `todo/` 应该包含哪些文件？缺了哪个说明哪一步没做对？

> 第 5 题的答案清单是：`SKILL.md`、`LICENSE.txt`、`CHANGELOG.md`、`ROADMAP.md`、`TASKS.md`、`DECISIONS.md`、`scripts/todo.py`、`assets/todos.example.json`、`.gitignore`。能对着这份清单核对自己的产物，说明你已经能独立产出一个完整 Skill 了。
