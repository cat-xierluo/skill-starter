# 需求分析

做 Skill 最容易跳过的一步，就是动手前先把「要做成什么样」想清楚。很多人拿到一个模糊想法——「我想要个待办工具」「帮我把提交规范记下来」——就直接开始建文件夹、写 `SKILL.md`。结果写到一半发现需求变了，或者做完才发现跟另一个 Skill 撞车了。这篇讲怎么在动手前，把一个模糊想法澄清成一份可验收的 Skill 需求。

本篇聚焦「Skill 场景下的需求分析」：用户画像、触发与负向触发、输入输出契约、失败处理、依赖、安全、许可证、验收标准。通用的「从模糊想法到验收标准」方法论（目标 / 用户 / 范围 / 非目标 / 约束 / 输入输出 / 完成条件这 7 要素）在 [从需求到验收标准](../03-AI协作与上下文/05-从需求到验收标准.md)；本篇是它落地到 Skill 场景的进阶视角，在那 7 块之上补上 Skill 特有的几块。

## 本篇目标

读完这篇，你能：

- 判断一句「我想要个 XX」是模糊需求还是可验收需求，并说出它差的几块；
- 用复杂度评估表，决定一个 Skill 该直接实现、先写 `SKILL.md`、还是拆分；
- 判断这个需求该新建一个 Skill，还是合并进现有 Skill；
- 写出一份覆盖触发、输入输出、失败处理、验收的 Skill 需求文档；
- 识别 Skill 需求里容易漏的依赖、安全、许可证陷阱。

## 前置知识

- [什么是 Skill](../01-概念入门/01-什么是-Skill.md)：知道 Skill 是一个文件夹，核心是 `SKILL.md`（说明书）。本篇反复用到两个词——**触发**（AI 判断「现在该不该启用这个 Skill」）和 **frontmatter**（`SKILL.md` 开头被 `---` 包起来、给 AI 读的元信息，其中的 `description` 字段决定触发准不准）。
- [从需求到验收标准](../03-AI协作与上下文/05-从需求到验收标准.md)：通用的「7 要素」需求方法论。本篇承接它，把同样的思路收窄到 Skill 场景，并补上 Skill 特有的触发、许可证、依赖等几块。
- [复用改造还是新建](../01-概念入门/07-复用改造还是新建.md)：专门讲「该不该新建」的判断，本篇会用到其中几条结论。

不需要会写代码。文中的 `todo.py` 是全系列统一的小项目（Python 3 标准库、存 `todos.json`、`add/list/done` 三命令），这里只拿它当需求分析的靶子。

## 核心概念：做 Skill 前，先回答这几个问题

Skill 场景的需求分析，比通用需求多关心几件事——因为 Skill 不是一次性脚本，它会被反复触发、可能装到别人机器上、还可能跟别的 Skill 抢着响应。所以在通用的「目标 / 范围 / 约束 / 验收」之上，还要补这几块：

- **谁会用、什么时候触发**：Skill 的价值在于「在恰当的时候自动被启用」，所以触发条件是需求的一部分，不是留到写 `SKILL.md` 时才想的实现细节。
- **不该触发的情况**（负向触发）：不写清楚，你的 Skill 就会到处插嘴。
- **输入输出契约**：用户说什么、Skill 改了什么文件、返回什么。带脚本型 Skill 尤其要把这个钉死（见 [07 带脚本 Skill](./07-带脚本-Skill.md)）。
- **失败时怎么办**：文件不存在、参数缺、编号越界——这些都要在需求里想好，而不是等用户撞上。
- **依赖、安全、许可证**：Skill 装到别人机器上，依赖装不装得上、有没有危险操作、用什么许可证发布，都得在动手前定。

### 先评估复杂度：直接做、先写说明书、还是拆分

下面这张表是判断「这个 Skill 该怎么做」的第一道分诊。先粗估复杂度，再决定路径：

| 复杂度 | 特征 | 处理方式 |
|--------|------|----------|
| 低 | 单一动作、逻辑简单、无需外部状态 | 直接实现：写一份精简 `SKILL.md` 即可（见 [06 纯说明型 Skill](./06-纯说明型-Skill.md)） |
| 中 | 2-3 步组合、需要判断分支、可能读写文件 | 先写 `SKILL.md` 梳理流程，再补 `scripts/`（见 [07 带脚本 Skill](./07-带脚本-Skill.md)） |
| 高 | 多步骤、多状态、依赖外部服务、跨多个场景 | 拆成多个 Skill 或编排（见 [08 多 Skill 编排](./08-多Skill编排.md)） |

经验法则：**如果一个 Skill 要靠很长的说明或很多脚本才能讲清，多半是它太大**。坊间常听到的「超过 200 行代码说明太大」是个参考信号，别当成硬指标——真正该看的是「能不能用一句话说清它在什么场景做什么」。说不清，就该拆；能说清，就不必为了凑某个行数而硬拆。

### 再判断：新建一个 Skill，还是合并进现有的

不是每个需求都值得开一个新文件夹。先问下面两组问题。

倾向于**新建独立 Skill**（满足任一）：

- 它是一个能独立使用的场景，不依赖别的 Skill；
- 它需要单独的配置或状态（自己的 `assets/`、自己的数据文件）；
- 它可能被多个调用方复用（不止一个项目或人会触发它）；
- 团队里有多人需要。

倾向于**合并进现有 Skill**（满足任一）：

- 只是某个现有 Skill 的小功能扩展；
- 两个功能强绑定，拆开反而要让用户触发两次；
- 使用频率极低，单独成 Skill 不值得维护。

更细的「复用、改造、新建」判断见 [复用改造还是新建](../01-概念入门/07-复用改造还是新建.md)。

## 动手步骤：把「我想要个待办工具」澄清成 Skill 需求

下面用一个真实想法走一遍。需求是这样的——你随口一句：

> 「我想要个待办工具，能记事、能看、能标记完成。」

这是一句典型的模糊需求。下面 5 步把它澄清成一份可验收的 Skill 需求文档。你要做的，是把每一步的答案填进最后那张模板。

### 第 1 步：问清谁用、什么时候触发

先把「用户」和「触发」钉死。

- **谁用**：只有我自己，单机。这一句决定了不用考虑登录、多用户、并发。
- **正向触发**：当我说「记一下买牛奶」「帮我加个待办」「我还有什么事没做」时，这个 Skill 该被启用。
- **负向触发**：当我只是在聊天里提到「待办」这个词、或让我删文件、或让我写代码时，不要触发。

把触发写进需求，是因为 Skill 的 `description` 就是从这里来的（怎么把触发写到位，见 [06 纯说明型 Skill](./06-纯说明型-Skill.md) 的「触发怎么保证」一节）。现在想清楚，写 `SKILL.md` 时就不用再猜。

### 第 2 步：把输入输出写成契约

把「能记事、能看、能完成」翻译成具体的输入和结果。待办数据存在当前目录的 `todos.json`（和全系列统一项目 `todo.py` 一致）：

```text
说「记一下买牛奶」    →  往 todos.json 加一条，回复「已添加 #1：买牛奶」
说「我还有什么没做」  →  读 todos.json，列出未完成项（带编号）
说「第 1 条做完了」    →  把 todos.json 里第 1 条标记完成，回复「已完成 #1」
```

把输入输出写成「左输入、右结果」的对照，需求就有了形状——既知道 Skill 要做什么，也知道验收时该拿哪句话去试。

### 第 3 步：想清楚失败时怎么办

新手最容易漏的一步。列出可能失败的场景和该有的行为：

- `todos.json` 不存在 → 第一次记事时自动创建，不报错；
- 说「完成第 5 条」但只有 3 条 → 回复「没有第 5 条」，不崩溃；
- 说「记一下」但没说记什么 → 反问「要记什么？」，不要瞎建一条空待办；
- 文件没写权限 → 报错并说明原因，而不是静默失败。

这一步的价值在于：**失败处理也是需求**。等到写脚本时才发现没想，就只能临时拍脑袋，结果每种失败的行为都不一致。

### 第 4 步：盘依赖、安全、许可证

Skill 会装到（可能不止你一个人的）机器上，这三件事必须动手前定：

- **依赖**：只用 Python 3 标准库，不装第三方包（避免 `pip install` 在不同机器、不同平台装不上——macOS / Linux 上常是 `pip3`，Windows 上常是 `pip`，行为不一）。不联网。
- **安全**：只读写当前目录的 `todos.json`，不碰用户主目录、不删别的文件、不执行外部命令。这条同时是需求和安全边界（更系统的安全视角见 [05 第三方 Skill 安全审查](./05-第三方-Skill-安全审查.md)）。
- **许可证**（规定别人能怎么用、改、再分发的法律条款）：如果打算发布或分享，要定一个。选什么、怎么选见 [什么是许可证](../01-概念入门/02-什么是-许可证.md)。

这一步最容易被跳过，但它决定了 Skill 能不能在别的机器上跑起来、能不能合法分享。

### 第 5 步：写出可验收的完成条件，并落成需求文档

最后把前面四步整理成一份文档，关键是把「完成」写成可观察的条件——能用命令跑出来、能用文件内容核对，而不是「感觉挺好」。

下面这份模板融合了原文的「目标 / 触发场景 / 输入 / 输出 / 注意事项」，并补上了 Skill 特有的失败处理、约束、许可证几块。把待办 Skill 的答案填进去：

```text
# 需求：待办管理 Skill

## 目标
一句话：用户口述待办，Skill 帮他增、查、完成，数据存 todos.json。

## 用户与触发
- 用户：只有我自己，单机。
- 正向触发：说「记一下…」「我还有什么没做」「第 N 条做完了」。
- 负向触发：聊天里顺带提到「待办」、让删文件、让写代码 → 不触发。

## 输入输出契约
- 「记一下 X」     →  新增一条，回复「已添加 #N：X」
- 「我还有什么没做」→  列出未完成项
- 「第 N 条做完了」 →  标记完成，回复「已完成 #N」

## 失败处理
- 文件不存在 → 首次记事自动创建
- 编号越界   → 回复「没有第 N 条」
- 内容为空   → 反问，不建空条目

## 约束与安全
- Python 3 标准库，不联网，不装第三方包
- 只读写当前目录 todos.json

## 许可证
MIT（待定，选法见 01-概念入门/02）

## 可观察的完成条件
[ ] 说「记一下买牛奶」后，todos.json 出现 {"title":"买牛奶","done":false}
[ ] 说「我还有什么没做」后，列出至少一条带编号的未完成项
[ ] 说「第 1 条做完了」后，todos.json 第 1 条 done 变 true
[ ] todos.json 不存在时，首次记事自动创建不报错
[ ] 说「完成第 9 条」（不存在）时，回复「没有第 9 条」而非崩溃
```

每条完成条件都能核对——看 `todos.json` 内容、看回复文字。没有任何一条是「体验流畅」「代码优雅」这种没法判定的。好的需求文档，让你在写 Skill 时不需要再问任何人，验收时也不靠感觉。

## 常见错误

### 只写正向触发，不写负向触发

只写了「用户提到待办时触发」，结果你在聊天里随口说一句「我待办太多了」，Skill 就跳出来插嘴。正确做法：需求里同时写清楚「什么时候不触发」，落到 `description` 里就是负向触发。

### 把模糊形容词当需求

需求里写「要好用、要智能、要简洁」。这些没法验收，也没法实现。正确做法：每个形容词都翻译成可观察的行为——「简洁」=「`list` 输出每行一条、带编号」，「好用」=「说『记一下 X』就能加，不用背命令」。

### 需求文档里没有失败场景

只写了「正常怎么做」，没写「文件不存在 / 编号越界 / 参数缺」时怎么办。结果每种失败的行为都不一致，用户每次撞坑。正确做法：专门留一栏「失败处理」，把能想到的失败都列上（见第 3 步）。

### 没盘依赖就开工，结果 Skill 装不上

写脚本时随手 `pip install` 了个包，自己机器能跑，分享给别人装不上（不同平台、不同 Python 版本）。正确做法：第 4 步就把依赖钉死——能用标准库就用标准库；必须用第三方包，就明确写进需求和依赖清单。

### 引入了许可证不兼容的依赖

为了让 Skill 多个功能，引了一个第三方包，却没看它的许可证，结果整个 Skill 没法按你想要的许可证发布。正确做法：动手前确认要用的依赖的许可证，和你的发布许可证兼容（见 [什么是许可证](../01-概念入门/02-什么是-许可证.md)）。

### 把「超过 200 行」当硬指标而硬拆

听说「Skill 超过 200 行就太大」，于是硬把一个本该完整的功能拆成两半，用户反而要触发两次。正确做法：行数只是参考信号，真正看的是「能不能一句话说清它在什么场景做什么」。说不清才该拆，能说清就不必为了凑数字而拆。

## 自测题 / 验收

1. 拿你自己的一句模糊想法（比如「我想要个记笔记的工具」），按第 1-5 步走一遍，说出它现在差的几块是什么。
2. 一个需求是「读 3 个 CSV、算合计、导出 Excel」，按复杂度评估表，它属于低 / 中 / 高？该直接做、先写 `SKILL.md`、还是拆分？说出依据。
3. 同样一个「导出 Excel」的小功能，你的团队已经有一个「数据处理 Skill」——什么情况下该合并进去，什么情况下该新建？各举一个。
4. 给待办 Skill 的 `description` 写一段，要同时包含正向触发、负向触发、和至少两种真实问法。
5. 下面哪几条是「可观察的完成条件」，哪几条不是？为什么：「`list` 输出每行带编号」 / 「界面好看」 / 「说『记一下 X』后 todos.json 多一条」 / 「体验流畅」。

第 5 题能分清可观察与不可观察，说明验收这块你过关了。
