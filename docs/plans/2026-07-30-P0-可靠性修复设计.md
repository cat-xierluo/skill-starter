# P0 可靠性修复设计

日期：2026-07-30

## 背景与目标

2026-07-29 审查发现三类“成功假象”：`skill-manager update` 吞掉失败退出码；GitHub 子目录安装把网页 URL 当作 Git remote 保存；Skill frontmatter 在标准 YAML 解析失败后仍可能由 fallback 判为通过。本轮目标是关闭这三个 P0，同时把更新流程的同版本变化识别和失败回滚一并做到可验证。

不重写整个 skill-manager，也不修改上游同步指南。现有命令、registry 主体结构和本地符号链接安装方式保持兼容。

## 方案选择

比较过三种方案：只补条件判断的最小补丁无法解决旧 registry 和替换失败；完整重写安装/更新层会扩大 fork 面积；最终采用中等范围的可靠性改造。安装端只修正元数据语义，更新端保留两条既有路径，但重构远程候选版本的准备、比较和切换过程。

`remote_url` 固定表示可克隆仓库地址，`install_branch` 和 `remote_subpath` 分别保存分支与子目录。读取到旧 `/tree/...` 或 `/blob/...` 地址时，更新器在内存中拆分，并在成功更新 registry 时持久化为新格式。

## 更新数据流与错误处理

远程更新先在系统临时目录执行 shallow clone 或 sparse checkout，确认目标目录包含 `SKILL.md` 后复制为候选版本。更新判断同时参考远端 commit 和候选目录与现有目录的实际差异，因此版本号不变但内容变化时仍会更新。

候选版本准备完成后，再复制到现有 Skill 旁的同文件系统暂存目录。只有暂存完整成功，才把当前目录移动为带时间戳的备份并启用候选目录；启用失败则立即把备份移回原路径。单项更新传播所有失败，批量模式分别计数并在任一失败时返回非零退出码。注册表写入失败按部分失败处理，不再输出无条件成功。

## YAML 与 CI

普通本地环境没有 PyYAML 时仍允许 fallback，便于零依赖初步检查；但只要 PyYAML 存在，语法错误必须直接失败，不能再回退。严格模式要求 PyYAML 必须存在。CI 通过 `requirements-check.txt` 固定安装 PyYAML 6.0.3，并设置 `STRICT_SKILL_YAML=1`，保证本地严格复跑与远端使用相同解析路径。

## 测试策略

测试全部使用临时目录和本地 Git 仓库，不修改真实 Agent 配置，也不依赖网络。覆盖合法/非法 YAML、缺少 PyYAML、GitHub 子目录安装参数、旧 registry 迁移、同版本内容更新、第二次更新判定最新、无效 remote、损坏 registry、复制失败保留原目录、批量部分失败等场景。测试由标准库 `unittest` 实现，并接入 `scripts/check.sh`，成为 CI 的必跑步骤。
