# 环境变量与密钥安全

这篇解决一件事：

**让一个会调用 API 的小脚本，能安全地拿到它需要的密钥，又不会把密钥泄漏进 Git 历史或教程里。**

---

## 本篇目标

读完你应该能：解释环境变量是什么、为什么用它存密钥；分清 `.env`（放真实密钥、不进版本库）和 `.env.example`（放占位值、进版本库）；配好 `.gitignore` 让 `.env` 永远不被提交；说出最小权限的 4 条做法；在密钥不小心进了 Git 之后，按顺序完成「撤销 → 查历史 → 清历史 → 强制推送 → 善后」的处置；并解释为什么真实 Token 绝不能写进教程正文或提交历史。示例统一标注 macOS / Linux / Windows 差异，断言处用「截至写作时」。

## 核心概念

### 环境变量是什么

环境变量（environment variable）是操作系统或程序运行时提供的一组「键=值」配置，程序跑起来时能读到，不必写死在代码里。比如程序想找当前用户的家目录，就去读环境变量；想找数据库地址或 API 密钥，也走同一个机制。好处是：**同一份代码**在不同电脑、不同环境（本机 / 测试 / 线上）能读到不同的值，而代码本身一个字都不用改。

在终端里临时设一个环境变量（只对当前这个终端窗口有效）：

```bash
# macOS / Linux / Git Bash（bash / zsh）
export WEATHER_API_KEY="sk-fake-DEMO1234"
echo "$WEATHER_API_KEY"          # 打印出来核对
```

```powershell
# Windows PowerShell
$env:WEATHER_API_KEY = "sk-fake-DEMO1234"
echo $env:WEATHER_API_KEY
```

临时设的变量关掉窗口就没了，也换台电脑就没法复现。所以真实项目几乎都用一个文件来长期保存这些值，这就是 `.env`。

### `.env` 与 `.env.example` 的区别

这两个文件名字很像，职责完全不同，是新手最容易混淆、也最容易因此泄漏密钥的地方：

| 文件 | 里面放什么 | 是否进版本库（Git） | 作用 |
| --- | --- | --- | --- |
| `.env` | **真实**的密钥、Token 真值 | **绝不进** | 只在你本机，程序运行时真正读取 |
| `.env.example` | 只有键名和**占位值**（假值） | **进** | 告诉协作者「这个项目需要哪些变量」 |

- `.env`：一个以 `.` 开头、平时隐藏（见 [项目目录与文件格式入门](./07-项目目录与文件格式入门.md)）的文本文件，按「键=值」逐行存放真实密钥，只在本机使用。
- `.env.example`：仿照 `.env` 的模板，只写键名和占位值，**没有任何真实秘密**，可以放心提交进 Git。

顺带把几个词说清：上面表格里的**密钥**、**Token**、**凭据**都指同一类东西——用来证明身份或调用权限的机密字符串；其中 Token 通常特指一串当作「通行证」的长字符串。它们一旦泄露，就等于把对应权限交了出去，这也是整篇文章要防的事。

一句话记法：`.env.example` 是「表格的表头」，`.env` 是「你自己填好的真实答案」。表头可以公开，答案不能。

### 为什么 `.env` 必须被 `.gitignore` 排除

`.gitignore` 是一个告诉 Git「哪些文件不要纳入版本管理」的清单文件（详见 [Git 入门](./01-Git-入门.md)）。只要 `.env` 没被排除，一次 `git add .` 就可能把真实密钥提交进仓库，再 `git push` 一下就上了远程——接下来几乎不可挽回。

本仓库自己的 `.gitignore` 就做了这件事，作为真实范例：

```text
# Environment
.env
.env.local
**/.env
**/.env.local
```

这四行保证：根目录的、子目录里的、以及带 `.local` 后缀的各种 `.env`，都不会被 Git 跟踪。**你的新项目也应该照抄这几行。** 注意：把文件名写进 `.gitignore` 只能阻止它「被新加入」；如果一个文件**之前已经被提交过**，再补进 `.gitignore` 不会把它从历史里删掉——这正是后面「泄漏处置」要解决的问题。

### 最小权限原则

最小权限（least privilege）的意思是：只给程序或密钥完成当前任务所必需的最小权限，不多给。落到密钥安全上有 4 条做法：

1. **用范围最窄的 Token**。如果脚本只需要「读取」某个接口，就申请只读权限的 Token，不要图省事用「全权限 / 管理员」Token。范围越小，万一泄露被利用的伤害越小。
2. **按环境隔离**。本机调试、测试环境、线上环境各用各的密钥，不要一把钥匙开所有门。线上密钥绝不放进本机的 `.env`。
3. **只放必需的变量**。`.env` 里只放这个项目真正要用的键，别顺手把别的项目的、过期的、用不上的密钥都堆进来。
4. **能过期就过期，不用就撤销**。如果平台支持给 Token 设过期时间就设上；确定不再使用的密钥，立刻去平台撤销，而不是让它一直躺在 `.env` 里。

### 为什么真实 Token 不能写进教程或提交历史

两条硬道理：

- **公开仓库在被持续扫描**。截至写作时，业界普遍现象是：真实密钥一旦被推到公开仓库，自动化爬虫常在极短时间（分钟级）内就抓取并尝试利用，即使你随后删除提交也来不及。所以默认假设「推上去 = 已泄漏」。
- **Git 历史是只增的**。即使你在新提交里删掉了密钥，旧提交里的那份仍然永久留在历史中。后来的人 `git log`、`git blame` 都还能看到。教程正文、截图、日志里的真实 Token 同理：读者会复制粘贴，截图会被转发，等于把权限反复交出去。

因此贯穿全文的规矩：**示例一律用假 Token（如 `sk-fake-DEMO1234`），真实密钥只待在本机的 `.env`。**

## 动手步骤

下面用一个贯穿小示例——「一个会调 API 的小脚本」——把上面的概念连起来。请在自己的练习文件夹里做，不要动本仓库的真实文件。

### 第一步：建项目和小脚本

```bash
mkdir secret-demo
cd secret-demo
python3 --version          # 确认装了 Python 3；Windows 一般敲 python
```

建议先建虚拟环境（见 [开发环境与依赖入门](./08-开发环境与依赖入门.md)），把依赖隔离在项目里：

```bash
# macOS / Linux / Git Bash
python3 -m venv .venv
source .venv/bin/activate
# Windows PowerShell
# .venv\Scripts\Activate.ps1
```

新建 `weather_demo.py`，它调用一个**假**接口并打印结果（接口地址是示例，访问不到也没关系，重点在它需要一个密钥）：

```python
import os
import requests

# 从环境变量读密钥；读不到就用空串，避免直接报错难调试
api_key = os.environ.get("WEATHER_API_KEY", "")
city = "beijing"
url = f"https://demo.example.com/api/forecast?city={city}"

resp = requests.get(url, headers={"Authorization": f"Bearer {api_key}"})
print("状态码：", resp.status_code)
print("返回：", resp.text[:120])
```

注意：密钥是从 `os.environ` 读的，**不是写死在代码里**。这就是环境变量的用法——代码里看不到任何真实秘密。

### 第二步：建 `.env` 放「假」密钥

在项目根目录新建 `.env`（注意以 `.` 开头，是个隐藏文件）：

```text
WEATHER_API_KEY=sk-fake-DEMO1234
```

这里用假 Token 演练。真实场景里，你应当把从平台后台申请到的**真**值填在这里。让脚本自动加载 `.env`，需要一个小库（`python-dotenv`）：

```bash
pip install python-dotenv requests
pip freeze > requirements.txt     # 记录依赖，方便别人复现
```

在 `weather_demo.py` 最上面加两行：

```python
from dotenv import load_dotenv
load_dotenv()          # 读取当前目录的 .env，把里面的键值放进环境变量
```

现在跑 `python3 weather_demo.py`，脚本会自动读到 `.env` 里的密钥。**关键点**：密钥存在 `.env`，代码里干干净净，把代码发给别人也不用担心。

> Node.js 同理：装 `dotenv` 包，在入口最前面写 `require('dotenv').config()`，之后用 `process.env.WEATHER_API_KEY` 读取。很多框架（如 Vite、Next.js）会自动加载 `.env` / `.env.local`，规则略有差异，以各自官方文档为准。

### 第三步：建 `.env.example`

`.env` 是你的私人答案，不能进 Git。但协作者需要知道「这个项目要哪些变量」，所以再建一个**只含占位值**的模板 `.env.example`：

```text
WEATHER_API_KEY=<your-weather-api-key>
```

这里用尖括号占位符 `<your-weather-api-key>` 表示「请在这里填你自己的值」，没有任何真实秘密。这个文件**可以、也应该**提交进 Git。

别人 clone 你的项目后，照着 `.env.example` 复制一份成 `.env`，再填上自己的真值就能跑起来——这就是标准协作流程。

### 第四步：配 `.gitignore` 并验证 `.env` 不进版本库

先初始化 Git（如果还没有），然后确保 `.env` 被忽略：

```bash
git init
```

新建 / 编辑 `.gitignore`，至少包含：

```text
.venv/
.env
.env.local
__pycache__/
```

现在做个**关键验证**——确认 Git 真的不会跟踪 `.env`：

```bash
git add .
git status
```

你应该看到 `.env.example`、`weather_demo.py`、`requirements.txt`、`.gitignore` 在待提交列表里，而 **`.env` 不在其中**。如果 `.env` 还是出现了，说明 `.gitignore` 没写对或写错位置，立即停下排查，**别提交**。

确认无误后提交：

```bash
git commit -m "chore: 初始化密钥安全示例项目"
```

到这一步，你的真实密钥安稳地待在本机的 `.env`，仓库里只有不含秘密的模板和代码。

## 动手步骤（续）：密钥不小心进了 Git 怎么办

这是本篇最重要的演练。请在**一个一次性的练习仓库**里做（就用上面的 `secret-demo`，但别推到任何真实共享仓库），全程用假 Token `sk-fake-DEMO1234`。目的是让你在真出事之前，先把处置流程走熟。

**演练前提**：先确认你的 `.env` 里有假 Token，并且它已被某个提交包含（为了演练，你可以临时把 `.env` 加进一个提交再继续；演练结束后用下面的步骤清除）。

### 第一步：立刻撤销密钥（最重要）

发现密钥可能泄露的第一反应，不是去删文件、不是去清历史，而是**先去签发平台把密钥作废**。因为从它被提交/推送的那一刻起，就要假设已经被人拿走。撤销是唯一能立刻「让那串字符失效」的动作。

- GitHub Token：网页「Settings → Developer settings → Personal access tokens」里 Revoke；或命令行 `gh auth token` 不可撤销旧令牌时，去后台删除。
- 各类 API 平台：登录后台找到对应的 Key/Token，点撤销或删除。

**这一步必须最先做，且不要等历史清理完才做。** 撤销之后，即使旧 Token 还躺在 Git 历史里，它也已经是一串废字符。

### 第二步：确认是否进了提交历史

撤销之后，再回头看历史。用 Git 的「翻找」功能确认那串 Token 出现在哪些提交：

```bash
git log -p --all | grep "sk-fake-DEMO1234"     # 粗略看是否出现过
git log --all -S "sk-fake-DEMO1234" --oneline   # 精确列出「引入/删除」它的提交
```

`git log -S`（俗称 pickaxe）会列出所有让这串文本「新增或消失」的提交。如果列表为空，说明它其实没进历史，虚惊一场；如果非空，进入第三步。

### 第三步：从历史中清除

要真正把密钥从历史里抹掉，需要**改写历史**的工具。截至写作时，Git 官方在 `git filter-branch` 的手册里已明确建议改用更现代的工具，所以下面给两个推荐选项，`filter-branch` 仅作了解、不推荐：

- **首选 `git-filter-repo`**（跨平台，需 Python）：

  ```bash
  pip install git-filter-repo
  # 方式 A：把整个 .env 文件从所有历史里删掉
  git filter-repo --invert-paths --path .env
  # 方式 B：把出现过的那串密钥替换成占位符（更安全，保留文件结构）
  git filter-repo --replace-text <(echo "sk-fake-DEMO1234==>***REMOVED***")
  ```

  > Windows PowerShell 不支持 `<(...)` 进程替换，可先建一个文本文件 `replacements.txt`，内容写 `sk-fake-DEMO1234==>***REMOVED***`，再执行 `git filter-repo --replace-text replacements.txt`。

- **备选 BFG Repo-Cleaner**（需要 Java）：先把仓库做成「纯镜像」(`git clone --mirror`)，再用 `java -jar bfg.jar --replace-text replacements.txt repo.git` 清洗，最后 `git reflog expire --expire=now --all && git gc --prune=now`。

改写历史后，本地旧提交的指针被替换，密钥才真正从历史中消失。

### 第四步：强制推送与协作影响

改写了历史，远程和本地的提交就对不上了，必须强制推送覆盖远程：

```bash
git push --force-with-lease origin <branch-name>
```

优先用 `--force-with-lease` 而不是裸 `--force`：它会在远程被别人新推过时拒绝你，少踩「覆盖别人提交」的坑。

**必须告诉所有协作者**：改写历史后，他们本地还留着旧提交（含密钥）。正确做法是他们**重新 clone**，或至少 `git fetch && git reset --hard origin/<branch-name>`，否则旧的脏历史会在他们一推之后又被带回来。如果仓库已经被 fork 过，旧历史还可能残留在 fork 里——这也是为什么第一步「先撤销密钥」如此关键：清历史是亡羊补牢，撤销才是止血。

### 第五步：善后与复盘

- 给这个接口**重新签发一个新密钥**，放进新的 `.env`（旧的已作废，不能复用）。
- 检查 `.gitignore` 是否真的包含 `.env`，避免再次踩同一个坑。
- 如果平台提供「密钥扫描」或日志审计，看一眼旧密钥在被撤销前有没有异常调用。
- 把这次教训记一笔（比如在团队约定里强调「.env 不进库」），让流程替记忆力兜底。

## 常见错误

- **把 `.env` 当 `.env.example` 提交**：两者名字像、职责相反。提交前看一眼内容——有真值的就是 `.env`，别提交。
- **先提交了 `.env`，后来才加 `.gitignore`**：补进 `.gitignore` 不会删除已提交的历史，得走上面的「清历史」流程。
- **在命令行里直接敲真实 Token**（如 `export API_KEY=真实值`）：会被 `history` 记下。真实值只应待在 `.env` 文件里。
- **把代码连同写死的密钥一起发给别人 / 贴进教程**：等于把权限直接送出去。密钥永远走环境变量。
- **撤销密钥前先去清历史**：顺序反了。先撤销让密钥立刻失效，再慢慢清历史。
- **用了全权限 / 不过期的 Token「图方便」**：违反最小权限，一旦泄露伤害最大。
- **Windows 下用了 `source` 激活虚拟环境**：PowerShell 用 `.venv\Scripts\Activate.ps1`（若被执行策略拦截，见 [开发环境与依赖入门](./08-开发环境与依赖入门.md) 的常见错误），或改用 Git Bash。
- **强制推送覆盖了别人的提交**：用 `--force-with-lease` 而不是裸 `--force`，且改写历史前先和协作者打招呼。

## 自测题 / 验收

1. 用一句话说清 `.env` 和 `.env.example` 各自放什么、谁进版本库。
2. 在一个练习项目里建好 `weather_demo.py`、`.env`、`.env.example`、`.gitignore`，跑通脚本。
3. 执行 `git add . && git status`，确认 `.env` 不在待提交列表、`.env.example` 在。
4. 说出最小权限的 4 条做法，并指出你那个 Token 目前违反了哪一条。
5. 在一次性练习仓库里，用假 Token `sk-fake-DEMO1234` 走一遍「撤销 → 查历史 → 清历史 → 强制推送」全流程（**不要用真实 Token，不要推到共享仓库**）。
6. 解释：为什么「在新提交里删掉密钥」不等于「密钥已经从仓库消失」。
7. 进阶：跑一次 `bash scripts/check.sh`（在本仓库根目录），确认你新增的相对链接都有效。

## 落地行动清单

读到这里，按顺序做这三件事，密钥安全就基本到位：

1. **今天就查**：打开你手头的项目，确认 `.gitignore` 里有 `.env`，且 `.env` 没被提交过（`git log --all -S "你的某个真值前缀"` 查一查）。
2. **换把窄钥匙**：把还在用的「全权限 Token」换成「只读 / 范围最窄」的新 Token，旧的撤销。
3. **留一份模板**：给项目补一个只含占位值的 `.env.example`，让任何人 clone 后都能照着填、安全地跑起来。
