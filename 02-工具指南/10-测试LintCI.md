# 测试、Lint 与 CI 入门

这篇把三件常被混在一起说的事情讲清楚：**测试**（验证代码行为对不对）、**Lint**（静态检查，看代码本身有没有低级错误）、**CI**（持续集成，把检查自动化地跑在每次提交上）。活教材是本仓库刚接入的 `.github/workflows/check.yml`（一个 GitHub Actions 工作流）和它实际调用的 `scripts/check.sh`（本地自检脚本）。读完你会明白一件事：**「检查通过」只代表脚本跑完了、没报错，绝不等于「功能真实可用」**——这是新手最容易踩的认知坑。

---

## 核心概念

### 测试是什么

测试（test）就是**写一小段「检查用的代码」去调用你真正的代码，并预先声明「我期待它返回什么」**。如果实际返回和期待一致，这一条测试就算通过；不一致就算失败。比如你写了一个把两个数相加的函数 `add(a, b)`，测试就是 `assert add(2, 3) == 5`——这里的 `assert` 叫**断言**（一句话：「我断言这一条必须成立，不成立就报错」）。一条断言失败，整个测试套件就会停下来报红。

测试按粒度大致分几层：

| 类型 | 检查什么 | 例子（以本仓库贯穿小项目 `todo.py` 为例） |
| --- | --- | --- |
| 单元测试（unit test） | 单个函数在隔离状态下对不对 | `add("买牛奶")` 之后 `list()` 能列出来这一条 |
| 集成测试 | 几个组件拼起来对不对 | `add` → `done` → 再次 `list` 这条链路走完，状态正确 |
| 端到端测试 | 从用户视角整个流程通不通 | 在真终端里敲 `python3 todo.py add 买牛奶` 看输出 |

零基础阶段先记住一个最小目标：**至少给关键函数写几条单元测试**。Python 里常用 `pytest` 这个工具，写法很直白，把断言写成一个函数它就能自动发现并运行。

为什么需要测试？因为人肉点一遍「好像能用」是靠不住的：今天改了 A，顺手把 B 弄坏了，你不会每次都把所有路径再点一遍。测试就是「把这些手动检查固化成代码，每次改完自动跑一遍」，让回归（改一个地方坏另一个地方）尽早暴露。

### Lint 是什么

Lint（代码静态检查）和测试有个关键差别：**测试要真的把代码跑起来，Lint 不跑代码，只读代码本身找问题**。它回答的是「这段代码本身有没有低级错误或风格隐患」，比如：

- 语法对不对（括号没闭合、缩进错乱）——这种错误运行时一定崩，Lint 能提前抓到；
- 有没有引用一个不存在的文件、变量、链接；
- 风格上是否一致（命名、空格）。

本仓库的 `scripts/check.sh` 就是几个真实的 Lint 凑在一起，特别适合拿来理解这个概念。它分三步检查，正好对应三种 Lint：

| 检查（在 check.sh 里） | 它在 Lint 什么 | 用到的命令 / 脚本 |
| --- | --- | --- |
| 脚本语法检查 | `.sh` 用 `bash -n`、`.py` 用 `python3 -m py_compile`，只编译不执行，看语法有没有错 | `bash -n`、`py_compile` |
| Markdown 相对链接检查 | 扫所有 `.md` 里的行内相对链接，看指向的目标文件真不存在就是断链 | `scripts/check_links.py` |
| Skill 完整性检查 | 每个 `skills/*/SKILL.md` 开头的 frontmatter（文件最前面被 `---` 包起来的一段元数据）必须有 `name` 和 `description` | `scripts/check_skills.py` |

最后两项里出现的 **frontmatter** 需要展开一句：它是 Markdown 文件最顶部用两行 `---` 包起来的一小段结构化配置，写法遵循 **YAML**（一种「键: 值」的配置格式，比 JSON 好读、支持注释）。本仓库每个 Skill 的 `SKILL.md` 顶部都有这么一段，`check_skills.py` 就是去校验它的字段齐不齐。

注意 Lint 和测试的关注点不重叠：Lint 抓不到「你这个加法函数逻辑写错了把 `add(2,3)` 算成 6」，因为语法是对的、链接也是对的——这种**逻辑错误只能靠测试抓**。反过来，测试也抓不到「你引用了一个早被删掉的文件」，因为测试可能根本没覆盖到那条路径。所以两者都要有。

### CI 是什么

CI（持续集成，Continuous Integration）的核心想法一句话：**每次有人提交代码，就自动在干净环境里把「构建 + 测试 + Lint」整套跑一遍，结果对所有人可见**。它的反面是「攒一星期再统一跑一次」，那种方式到发现问题时，早忘了是哪次提交引入的。

GitHub 提供的 CI 服务叫 **GitHub Actions**。你放一个 `.github/workflows/xxx.yml` 文件进仓库，GitHub 就会在它提供的机器（叫 **runner**，一台临时的虚拟机）上按你写的步骤跑。几个术语先认一下，后面读活教材会用到：

- **workflow**（工作流）：一个 `.yml` 文件，描述「在什么时候、跑哪些任务」；
- **job**（作业）：一组按顺序执行的步骤，跑在某台 runner 上；
- **step**（步骤）：job 里的最小单位，可以是「跑一条 shell 命令」或「调用一个别人写好的动作（action）」；
- **触发时机（on）**：什么事件会启动这个 workflow，比如「推送到 main 分支」「有人开了 PR」。

GitHub Actions 的工作流文件本身用的也是 YAML 格式，所以你能看到 `on:`、`jobs:`、`steps:` 这种层级结构。

### 本地门禁 vs 远程门禁

「门禁」是工程里的一个比喻：**在代码合并进主干之前，先过一道检查关，没过就拦下来**。它分两层，本仓库两层都配了，正好做对比：

| 维度 | 本地门禁 | 远程门禁（CI） |
| --- | --- | --- |
| 在哪跑 | 你自己电脑上 | GitHub 的 runner（一台 Ubuntu 虚拟机）上 |
| 什么时候跑 | 你手动敲命令，想跑就跑 | 你 push 或开 PR 时**自动**触发 |
| 代表文件 | `scripts/check.sh` | `.github/workflows/check.yml` |
| 跑得快不快 | 快，秒级到十几秒 | 慢一些，要等 runner 启动，分钟级 |
| 能不能拦住坏代码 | 只能靠你自觉跑 | 能，可设成「CI 不绿就不让合并」 |
| 依赖你的本机环境吗 | 依赖（没装 Python 就跑不了） | 不依赖（runner 由 GitHub 配好环境） |

两层门禁的关系是**互补**而不是替代：本地门禁快、能反复试，适合你边写边查；远程门禁强制、环境干净，保证「就算有人忘了本地跑、就算他本机环境和我不一样」，主干也有一道底线。下面这一句是理解整篇文章的钥匙——

### 「检查通过 ≠ 功能真实可用」（本篇最重要的认知）

本仓库的 `check.sh` 检查的是：脚本语法没错、Markdown 链接不断、Skill 的 frontmatter 字段齐。**这三样全过，也不代表你的 Skill 写得对、能正常工作。** 比如：

- 一个 `todo.py` 把 `add` 函数写成了 `return None`，语法完全正确，`py_compile` 笑眯眯地通过——但功能是坏的；
- 一篇教程链接都对、frontmatter 都齐，但里面的步骤根本跑不通。

这种「检查全绿、功能却坏」的情况之所以常见，是因为 Lint 和 CI 默认只查**容易自动判断的表面问题**（语法、链接、字段），而「功能对不对」往往需要人去理解意图、跑真实流程。所以 CI 全绿只是一个**最低门槛**（连门槛都过不了当然不行），过了之后你还得：自己手跑一遍核心功能、给关键逻辑写测试、最好让另一个人照着你的文档走一遍。这个缺口怎么补，会在「常见错误」和「落地行动清单」里反复强调。

## 动手步骤

下面 5 步都在本仓库根目录操作。命令行基础见 [终端与命令行入门](./06-终端与命令行入门.md)；如果对 `echo $?`、相对路径还不熟，照抄即可。

### 第一步：跑一次本地门禁

在本仓库根目录执行：

```bash
# macOS / Linux / Git Bash
bash scripts/check.sh
# Windows：需在 Git Bash 或 WSL 里运行（PowerShell 没有 bash）
# 也可用 python 的 subprocess，但最省事是装 Git for Windows 自带的 Git Bash
echo $?          # 打印上一条命令的退出码
```

这里出现的**退出码（exit code）**是每条命令结束时回给系统的一个数字：**0 表示成功，非 0 表示失败**。`scripts/check.sh` 末尾会 `exit "$FAIL"`，所以 `echo $?` 看到 `0` 就代表全部通过，看到 `1` 就代表有 error 级失败项。退出码是后面 CI 判断「这次跑算成功还是失败」的唯一依据——CI 不看你的输出文字，只看退出码。

第一次跑通常会看到三段输出：脚本语法检查、Markdown 链接检查、Skill 完整性检查，结尾有一行 `✅ 全部检查通过` 或 `❌ 存在失败项`。

### 第二步：切换严格模式，对齐 CI

注意 `check.sh` 默认是**非严格**的——出于历史原因，仓库里有些旧的 shell 语法问题、旧断链，默认只报 warn（告警，黄字、不阻断），不让你一上来就挂掉。但 CI 跑的是**严格模式**。`.github/workflows/check.yml` 里有这么两行设置了环境变量：

```yaml
env:
  STRICT_LINKS: '1'
  STRICT_SH_SYNTAX: '1'
```

这两个变量把「断链」和「shell 语法错误」从 warn 升级成 error。要在本地复现 CI 的严格判定，这样跑：

```bash
# macOS / Linux / Git Bash
STRICT_LINKS=1 STRICT_SH_SYNTAX=1 bash scripts/check.sh
echo $?
```

> Windows PowerShell 设环境变量的写法不同：`$env:STRICT_LINKS='1'; $env:STRICT_SH_SYNTAX='1'; bash scripts/check.sh`。建议直接用 Git Bash 跑上面那行更省事。

养成习惯：**本地用严格模式跑，对齐 CI，避免「本地通过、CI 红」的尴尬**。

### 第三步：读懂 `.github/workflows/check.yml` 的触发时机

打开 `.github/workflows/check.yml`（就在仓库根目录的 `.github/workflows/` 下），重点看 `on:` 那一段：

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
```

它的意思是：**当你 push 到 main 分支，或有人开指向 main 的 PR 时，这个 workflow 自动触发**。换句话说，你只要往 main 推代码、或开 PR 想合进 main，GitHub 就会在它的 runner 上把 `check.sh`（严格模式）跑一遍，结果挂在那个 commit 或 PR 页面上。

接着往下看 `jobs.check.steps`：先 `actions/checkout@v4`（把代码拉到 runner 上），再 `actions/setup-python@v5`（装个 Python 3），最后 `run: bash scripts/check.sh`（在严格环境变量下跑自检）。这就是一个最简 CI 的全部组成。读 workflow 时，把它当成「一份给机器人看的操作清单」即可。

### 第四步：故意制造一处断链，看本地和 CI 怎么报错

理解 Lint 最好的办法是让它真的抓到一次。在某个练习用的 `.md` 里（**别动本仓库的真实文件**，自己新建一个临时文件试）写一行带链接的文字，链接指向一个根本不存在的文件（比如写成 `链接文字 + (./某个不存在的文件.md)` 这种 Markdown 链接形式）。

然后跑：

```bash
# macOS / Linux / Git Bash
STRICT_LINKS=1 bash scripts/check.sh
echo $?
```

`check_links.py` 会扫到这条链接、发现目标文件不存在、报 error，于是 `check.sh` 退出码变成 1。这正是「门禁拦住坏代码」的现场。修复方法就是要么删掉这条链接、要么把目标补上。修完再跑一次，退出码回到 0。这一步练的就是「Lint 抓到了什么、怎么定位、怎么修」的完整循环。

### 第五步：提交并观察 GitHub 上的 CI 结果

把改动提交并推到一个分支（**别直接推 main**，开 PR 更安全；Git 基础见 [Git 入门](./01-Git-入门.md)，PR 流程见 [GitHub 入门](./02-GitHub-入门.md)）：

```bash
git checkout -b fix/lint-demo
git add .
git commit -m "chore: 演练 Lint 报错与修复"
git push -u origin fix/lint-demo
```

推送后到 GitHub 仓库页面，开个 PR。你会看到 PR 底部出现 `check` 这个检查项在转圈（runner 启动 + 跑 check.sh），几十秒到一两分钟后变成绿色对勾（通过）或红色叉（失败）。点进去能看到每一步的完整日志，和你在本地看到的输出几乎一样。这一步把「本地门禁」和「远程门禁」首尾连起来：本地先过滤掉低级错误，远程再做一次强制、干净的复跑。

## 常见错误

### 以为「CI 全绿 = 功能没问题」

CI 只查语法、链接、字段这些能自动判断的表面问题，逻辑对不对它管不到。CI 绿了之后，还要自己手跑核心流程、给关键函数写测试、最好让人照着文档走一遍。把 CI 当成「最低门槛」而非「充分证明」。

### 本地没跑就推送，等 CI 红了才发现

CI 跑一次要等 runner 启动，分钟级，来回几次很浪费时间。养成习惯：提交前先在本地用**严格模式**跑一遍 `STRICT_LINKS=1 STRICT_SH_SYNTAX=1 bash scripts/check.sh`，过了再推。本地秒级反馈，能省下大量等 CI 的时间。

### 严格模式开关记反了

`check.sh` 默认非严格（只 warn 不阻断），CI 默认严格。如果你本地只跑 `bash scripts/check.sh`，会看到一堆 warn 还以为没事，一推上去 CI 就红。记法：**本地要复现 CI，就带上那两个 `STRICT_*=1` 环境变量**。

### Windows 上直接双击或用 PowerShell 跑 `.sh` 报错

`check.sh` 是 Bash 脚本，PowerShell 和 `cmd` 都不能直接跑。解法：装 Git for Windows，用它自带的 Git Bash 运行；或在 WSL（Windows 里的 Linux 子系统）里跑。命令本身在 macOS / Linux / Git Bash 三处一致。终端基础见 [终端与命令行入门](./06-终端与命令行入门.md)。

### 把告警（warn）当错误，或反过来全忽略

`check.sh` 的输出里 `⚠️` 是 warn（不阻断）、`❌` 是 error（阻断）。新手常犯两种错：一是看到一堆 `⚠️` 就以为天塌了不敢提交（其实非严格模式下 warn 不影响退出码）；二是觉得「反正 warn 不阻断」就长期无视，等切到严格模式那天突然全面报红。正确做法：warn 可以先提交，但心里有数、定期清理。

### 改完代码忘了重跑就提交

最朴素的坑：改了 `.py` 或 `.md`，没重跑 `check.sh` 就 `git commit`，把语法错误或断链直接推进去。对策是把 `bash scripts/check.sh` 设成提交前的固定动作，或更进阶地配一个 Git pre-commit 钩子（hook，提交前自动触发的脚本）自动跑——后者属于进阶，本篇不展开。

## 自测题 / 验收

1. 用一句话分别说清：测试解决什么问题、Lint 解决什么问题、CI 解决什么问题。再指出它们各自抓不到的盲区。
2. 解释退出码的含义：`0` 和非 `0` 分别代表什么？为什么 CI 只看退出码、不看输出文字？
3. 列出「本地门禁」和「远程门禁」至少 3 点差别，并说明为什么两者都要有、不能只留一个。
4. 在本仓库根目录跑 `STRICT_LINKS=1 STRICT_SH_SYNTAX=1 bash scripts/check.sh`，用 `echo $?` 验证退出码确实是 `0`。
5. 打开 `.github/workflows/check.yml`，说出这个 workflow 在哪两种时机自动触发；再在一个 PR 页面上找到 `check` 检查项，点进去看日志。

## 落地行动清单

读到这里，按顺序做这三件事，「检查」这件事就基本到位：

1. **今天就跑**：在本仓库根目录用严格模式跑一次 `STRICT_LINKS=1 STRICT_SH_SYNTAX=1 bash scripts/check.sh`，确认退出码是 `0`；如果有 warn，记下来，挑一个最简单的修掉。
2. **配进流程**：把「提交前本地严格跑一遍 check.sh」设成固定动作；下次开 PR 时，主动去看一眼 GitHub 上的 `check` 检查项日志，把本地输出和远程输出对比一遍。
3. **补一个真测试**：挑你手里一个关键函数（比如 `todo.py` 的 `add`），给它写 2-3 条 `pytest` 单元测试。这一步直接补上「CI 全绿 ≠ 功能可用」的缺口——Lint 和门禁管不到的逻辑错误，靠测试来兜底。
